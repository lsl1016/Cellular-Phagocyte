# 第一部分：Game Server / Tick 系统 PRD

## 2. 模块背景

Game Server 是《吞噬细胞》实时对战的核心服务。匹配系统负责把玩家组织到一起，房间系统负责创建房间并完成入房流程，而 Game Server 负责真正运行一局游戏。

当房间进入 `RUNNING` 状态后，Game Server 需要以固定 Tick 频率推进游戏逻辑，包括接收玩家输入、更新玩家位置、处理食物吞噬、处理玩家吞噬、更新局内排行榜、广播状态快照、判断游戏结束等。

本模块重点解决以下问题：

1. 一局游戏如何被服务端持续推进。
2. 玩家输入如何进入服务端。
3. 服务端如何按固定 Tick 更新游戏状态。
4. 客户端如何收到房间状态快照。
5. 房间内玩家状态如何维护。
6. 服务端如何控制公平性。
7. 游戏何时结束并进入结算。
8. Game Server 如何释放房间资源。

------

## 3. 模块目标

### 3.1 产品目标

| 目标             | 说明                                   |
| ---------------- | -------------------------------------- |
| 支持多人实时对战 | 目标支持单局最多 100 人                |
| 操作反馈流畅     | 玩家移动、分裂、吐球等操作需要及时反馈 |
| 对战状态一致     | 不同客户端看到的核心对战状态应保持一致 |
| 规则公平         | 移动、吞噬、排名等核心逻辑由服务端计算 |
| 排行反馈明确     | 局内排行榜需要周期性更新               |
| 对局节奏稳定     | 对局时长、倒计时、结束条件需要可控     |
| 异常可恢复       | 玩家断线、重连、退出等场景需要可处理   |

### 3.2 技术目标

| 目标         | 说明                                           |
| ------------ | ---------------------------------------------- |
| 服务端权威   | 客户端只上传输入，服务端计算最终状态           |
| Tick 驱动    | Game Server 使用固定 Tick 推进房间逻辑         |
| 房间隔离     | 每个房间维护独立状态，互不影响                 |
| 内存状态管理 | 对局中的玩家、食物、地图状态优先存内存         |
| 广播频率可控 | 游戏逻辑 Tick 与快照广播频率可以分离           |
| 支持性能优化 | 后续支持 AOI、快照压缩、Protobuf、对象池等优化 |
| 可观测       | 关键 Tick 耗时、房间人数、广播大小等需要可监控 |

## 4. Game Server 定位

Game Server 处于房间系统和结算系统之间。

```text
匹配系统
  ↓
房间系统
  ↓
Game Server / Tick 系统
  ↓
结算系统
```

Game Server 的职责不是“保存所有长期数据”，而是“运行正在进行中的对局”。

------

## 5. 核心设计原则

## 5.1 服务端权威

客户端只负责：

```text
1. 采集输入
2. 发送操作
3. 接收快照
4. 本地渲染
5. UI 展示
```

服务端负责：

```text
1. 移动计算
2. 质量变化
3. 碰撞检测
4. 吞噬判定
5. 排名计算
6. 游戏结束判断
7. 结算基础结果生成
```

客户端不能直接决定：

```text
1. 自己的位置
2. 自己的质量
3. 是否吃到食物
4. 是否吞噬玩家
5. 最终排名
6. 奖励结果
```

------

## 5.2 Tick 驱动

实时对战不是普通请求响应模型，而是由服务端按照固定频率推进。

示例：

```text
每 50ms 执行一次房间 Tick
每 100ms 广播一次状态快照
每 1000ms 更新一次局内排行榜
```

Tick 负责统一推进房间中的所有对象状态。

------

## 5.3 房间状态内存化

对局进行中，房间状态主要维护在 Game Server 内存中。

原因：

1. Tick 高频执行，不能每帧访问数据库。
2. 玩家、食物、位置、速度等状态变化频繁。
3. 内存计算延迟低，适合实时对战。
4. 对局结束后再将结果写入持久化存储。

------

## 5.4 输入与状态分离

客户端发送的是输入，不是最终状态。

例如客户端发送：

```text
我要向某个方向移动
我要分裂
我要吐球
```

服务端计算后广播：

```text
你现在的位置
你的质量
房间内其他对象状态
排行榜变化
```

## 6. 用户场景

## 6.1 正常对战场景

### 场景描述

玩家进入房间并 Ready 后，房间进入 RUNNING。玩家通过客户端持续输入方向，服务端按 Tick 更新位置并广播状态快照。

### 流程

```text
房间进入 RUNNING
  ↓
客户端持续发送移动输入
  ↓
Game Server 收集输入
  ↓
Tick 更新玩家位置
  ↓
处理食物吞噬
  ↓
处理玩家吞噬
  ↓
更新排行榜
  ↓
广播状态快照
  ↓
客户端平滑渲染
```

------

## 6.2 玩家分裂场景

### 场景描述

玩家点击“分裂”按钮，客户端发送分裂操作，服务端检查条件后执行分裂。

### 规则

1. 玩家质量达到分裂阈值。
2. 当前分身数量未超过上限。
3. 分裂技能不在冷却中。
4. 房间处于 RUNNING 状态。
5. 分裂结果由服务端计算。

------

## 6.3 玩家吐球场景

### 场景描述

玩家点击“吐球”按钮，客户端发送吐球操作，服务端检查条件后生成吐出物。

### 规则

1. 玩家质量达到吐球阈值。
2. 吐球频率未超过限制。
3. 吐球方向由玩家当前输入方向决定。
4. 吐球会降低玩家质量。
5. 吐出的球体可被玩家吞噬。

------

## 6.4 玩家断线场景

### 场景描述

玩家在对局中 WebSocket 断开。

### 处理规则

1. Game Server 标记玩家为 DISCONNECTED。
2. 短时间保留玩家对象。
3. 玩家对象可继续存在于地图中。
4. 客户端在重连窗口期内可恢复。
5. 超时未恢复则视为退出或死亡，具体规则可配置。

------

## 6.5 游戏结束场景

### 场景描述

达到对局结束条件后，Game Server 停止对局 Tick，冻结房间状态，并进入结算流程。

### 结束条件

MVP 阶段建议：

```text
固定对局时长结束
```

后续可扩展：

1. 剩余玩家数量达到阈值。
2. 某玩家达到目标分数。
3. 特殊玩法目标完成。
4. 房间异常中止。

## 9. Tick 设计

## 9.1 Tick 定义

Tick 是 Game Server 推进房间逻辑的最小时间单位。

每一次 Tick 中，Game Server 会处理当前房间中所有需要更新的状态。

------

## 9.2 推荐 Tick 频率

MVP 阶段推荐：

| 项目         | 建议值        | 说明               |
| ------------ | ------------- | ------------------ |
| 逻辑 Tick    | 20 次 / 秒    | 每 50ms 执行一次   |
| 快照广播     | 10 次 / 秒    | 每 100ms 广播一次  |
| 排行榜更新   | 1 次 / 秒     | 每秒计算并推送一次 |
| 食物补充检查 | 1 次 / 秒     | 保持地图食物数量   |
| 心跳检测     | 5 ~ 10 秒一次 | 检查连接状态       |

------

## 9.3 Tick 执行内容

每个 Tick 主要执行：

```text
1. 读取玩家输入
2. 更新玩家移动方向
3. 计算玩家位置
4. 处理地图边界
5. 处理食物吞噬
6. 处理玩家吞噬
7. 处理分裂 / 吐球状态
8. 更新临时事件
9. 判断游戏结束
10. 根据频率决定是否广播快照
```

------

## 9.4 Tick 执行顺序

推荐顺序：

```text
Tick 开始
  ↓
读取输入队列
  ↓
校验输入合法性
  ↓
更新玩家操作状态
  ↓
计算移动
  ↓
处理边界
  ↓
处理碰撞与吞噬
  ↓
处理对象生成与移除
  ↓
更新排行榜
  ↓
生成事件
  ↓
广播快照
  ↓
判断结束
  ↓
Tick 结束
```

------

## 9.5 Tick 与广播解耦

逻辑 Tick 不一定每次都广播。

例如：

```text
逻辑 Tick：20 次 / 秒
状态广播：10 次 / 秒
```

好处：

1. 降低网络带宽压力。
2. 保持服务端计算精度。
3. 客户端通过插值弥补广播间隔。
4. 排行榜等低频信息不用每帧推送。

## 14. 移动系统设计

## 14.1 移动原则

玩家移动由服务端计算。

客户端只发送方向，服务端根据以下因素计算：

1. 当前质量。
2. 当前半径。
3. 当前方向。
4. 基础速度。
5. 地图边界。
6. 状态效果，后续支持。

------

## 14.2 基础速度模型

推荐初始模型：

```text
radius = sqrt(mass) * radiusFactor
speed = baseSpeed / sqrt(massFactor)
```

实际数值后续通过配置调整。

------

## 14.3 地图边界

服务端需要保证玩家不会越界。

处理方式：

1. 计算新位置。
2. 判断是否超出地图边界。
3. 如果超出边界，将位置修正到边界内。
4. 客户端只展示服务端最终位置。

------

## 15. 碰撞与吞噬概要设计

## 15.1 碰撞对象

需要处理：

1. 玩家球体与食物。
2. 玩家球体与玩家球体。
3. 玩家球体与吐出物。
4. 玩家球体与刺球，后续支持。

## 15.2 食物吞噬

基础规则：

```text
玩家球体与食物距离满足条件
  ↓
食物被移除
  ↓
玩家质量增加
  ↓
生成 FOOD_EATEN 事件
```

------

## 15.3 玩家吞噬

基础规则：

```text
大球质量 > 小球质量 * 吞噬倍率
并且
双方距离满足吞噬条件
  ↓
大球吞噬小球
  ↓
大球质量增加
  ↓
小球或玩家死亡
  ↓
生成 PLAYER_EATEN 事件
```

详细碰撞算法后续在“碰撞系统设计”中展开。

## 19. 断线与重连概要设计

## 19.1 断线处理

当 WebSocket 断开：

```text

2. 记录 disconnectTime
3. 保留玩家对象一段时间
4. 广播玩家断线状态，是否广播可配置
```

## 19.2 重连处理

当玩家重新连接：

```text
1. 校验 userId、roomId、token
2. 查找房间实例
3. 恢复玩家连接
4. 下发当前房间快照
5. 玩家状态恢复 PLAYING
```

## 29. 总结

Game Server / Tick 系统是《吞噬细胞》实时对战的核心。它在房间进入 RUNNING 后接管对局，通过固定 Tick 持续推进房间状态。

核心链路如下：

```text
房间开始
  ↓
启动 Tick
  ↓
读取输入
  ↓
更新移动
  ↓
处理吞噬
  ↓
更新排行榜
  ↓
广播快照
  ↓
判断结束
  ↓
进入结算
```

当前阶段应优先保证：

1. 服务端权威计算。
2. 房间状态内存维护。
3. Tick 稳定执行。
4. 输入只作为操作意图。
5. 快照按固定频率广播。
6. 游戏结束后能正确进入结算。
7. 房间资源能够释放。

MVP 阶段不需要一次性实现复杂 AOI、预测补偿、增量快照和多 GameServer 高可用。应先跑通完整实时对战闭环，再逐步优化性能和体验。
