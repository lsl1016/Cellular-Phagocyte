# 实时多人对战游戏技术选型文档

## 1. 文档目的

本文档用于明确实时多人对战游戏项目的核心技术栈选型，说明客户端、网络通信、通信协议、服务端、存储与部署方案的选择依据、适用边界、实现方式及后续演进方向。

本项目目标是实现一款类似“球球大作战”的 2D 实时多人在线对战游戏，核心能力包括：

- 玩家匹配进入游戏
- 单局多人实时对战
- 玩家移动、分裂、吞噬等操作
- 服务端权威状态同步
- 局内排行榜
- 断线重连
- 一局游戏结算
- 战绩与排行榜持久化

------

## 2. 总体技术选型

| 层级           | 技术选型                                      | 说明                                                         |
| -------------- | --------------------------------------------- | ------------------------------------------------------------ |
| 客户端         | Cocos Creator 3.x + TypeScript                | 用于开发 2D 游戏客户端，负责场景、渲染、输入、UI、状态表现   |
| 网络通信       | WebSocket                                     | 用于客户端与服务端之间的实时双向通信                         |

## 3. 客户端技术选型

### 3.1 选型结论

客户端选用：

```text
Cocos Creator 3.x + TypeScript
```

### 3.2 选择原因

本项目属于 2D 实时多人对战游戏，客户端需要处理游戏场景、玩家对象、地图、食物、刺球、技能表现、排行榜 UI、结算 UI 等内容。

Cocos Creator 适合此类 2D 游戏客户端开发，能够提供较完整的游戏开发能力，包括：

- 场景管理
- 节点管理
- 2D 渲染
- 资源管理
- UI 面板
- 动画与特效
- 输入事件处理
- 对象池
- H5 与移动端构建

相比普通 Web 前端方案，Cocos Creator 更符合游戏客户端的开发模型。相比 Unity，Cocos Creator 在 2D、H5、移动端轻量游戏方向上更轻量，工程复杂度更低。

Cocos Creator 文档中也提供了 WebSocket 相关能力说明，WebSocket 传输可以使用字符串或二进制数据，这能够支持前期 JSON 通信以及后期 Protobuf 二进制协议演进。

### 3.3 客户端职责

客户端主要负责以下内容：

```text
1. 游戏大厅展示
2. 匹配状态展示
3. WebSocket 连接建立与维护
4. 玩家输入采集
5. 本地预测与插值渲染
6. 服务端快照接收与表现
7. 玩家、食物、刺球等对象渲染
8. 局内排行榜展示
9. 网络状态提示
10. 游戏结算页面展示
```

### 3.4 客户端不负责的内容

客户端不负责最终游戏结果裁决，包括：

```text
1. 最终坐标
2. 最终质量
3. 是否吞噬成功
4. 最终排名
5. 奖励数量
6. 战绩写入
7. 排行榜最终分数
```

上述数据必须由服务端计算并下发，客户端只负责表现。

## 4. 网络通信技术选型

### 4.1 选型结论

网络通信选用：

```text
WebSocket
```

### 4.2 选择原因

本项目需要客户端与服务端之间进行持续的双向通信。

普通 HTTP 请求适合登录、查询配置、查询战绩、查询排行榜等低频请求，但不适合实时对战中的高频状态同步。WebSocket 在连接建立后可以保持长连接，客户端可以持续发送输入，服务端也可以持续推送状态快照，适合实时多人对战场景。

### 4.3 WebSocket 适用场景

本项目中 WebSocket 用于：

```text
1. 玩家进入房间后的连接建立
2. 玩家移动输入上报
3. 分裂、吐球等操作上报
4. 服务端状态快照推送
5. 局内排行榜推送
6. 断线检测与重连恢复
7. 结算结果推送
```

### 4.4 HTTP 与 WebSocket 的职责划分

| 通信方式  | 使用场景                                                     |
| --------- | ------------------------------------------------------------ |
| HTTP      | 登录、鉴权、开始匹配、查询用户信息、查询战绩、查询全服排行榜 |
| WebSocket | 房间内实时对战、输入上报、快照同步、局内排行榜、结算推送     |

### 4.5 WebSocket 连接流程

```text
1. 客户端通过 HTTP 请求开始匹配
2. 匹配成功后服务端返回 roomId、serverId、wsUrl、token
3. 客户端使用 wsUrl 建立 WebSocket 连接
4. 连接建立后发送认证消息
5. 服务端校验 token、roomId、userId
6. 校验通过后将连接绑定到玩家会话
7. 客户端发送 ready 消息
8. 房间进入对战状态
```

## 5. 通信协议技术选型

### 5.1 选型结论

协议采用两阶段演进：

```text
第一阶段：JSON
第二阶段：Protobuf
```

### 5.2 第一阶段选择 JSON 的原因

项目初期优先使用 JSON。

原因：

```text
1. 可读性强
2. 调试方便
3. 前后端联调成本低
4. 协议变更灵活
5. 适合快速验证匹配、房间、同步、结算流程
```

第一阶段的重点是跑通完整业务链路，不应过早引入二进制协议带来的调试成本。

### 5.3 第二阶段升级 Protobuf 的原因

当项目进入性能优化阶段后，协议升级为 Protobuf。

Protocol Buffers 是一种语言无关、平台无关、可扩展的结构化数据序列化机制，官方文档也说明它相比 JSON 更小、更快，并且可以生成不同语言的代码绑定。

升级 Protobuf 的原因：

```text
1. 减少消息体积
2. 降低高频同步时的网络带宽压力
3. 提高协议结构约束
4. 提高多语言协作能力
5. 适合 Go 服务端与 TypeScript 客户端之间维护统一协议
```

### 5.4 协议消息分类

客户端发送消息：

```text
AUTH            连接认证
READY           加载完成
MOVE            移动输入
SPLIT           分裂操作
EJECT           吐球操作
PING            心跳检测
RECONNECT       断线重连
```

服务端发送消息：

```text
AUTH_RESULT     认证结果
ROOM_SNAPSHOT   房间状态快照
RANK_UPDATE     局内排行榜更新
PLAYER_JOIN     玩家加入
PLAYER_LEAVE    玩家离开
PLAYER_DEAD     玩家死亡
ERROR           错误消息
SETTLEMENT      结算结果
PONG            心跳响应
```

### 5.5 JSON 示例

客户端移动输入：

```json
{
  "type": "MOVE",
  "seq": 1001,
  "direction": 1.57,
  "clientTime": 1710000000000
}
```

服务端状态快照：

```json
{
  "type": "ROOM_SNAPSHOT",
  "seq": 3001,
  "serverTime": 1710000000050,
  "players": [
    {
      "userId": "10001",
      "x": 120.5,
      "y": 88.2,
      "mass": 35,
      "radius": 18
    }
  ],
  "foods": [],
  "rankTopN": [
    {
      "userId": "10001",
      "score": 3500,
      "rank": 1
    }
  ]
}
```

## 6. 服务端技术选型

### 6.1 选型结论

服务端选用：

```text
Go + WebSocket + Redis + MySQL
```

### 6.2 选择 Go 的原因

实时多人对战服务端具有以下特点：

```text
1. 长连接数量较多
2. 消息收发频繁
3. 房间状态主要维护在内存中
4. 需要固定 Tick 推进游戏逻辑
5. 需要并发处理多个房间
6. 需要较低的资源消耗
```

Go 的 goroutine、channel、定时器和较轻量的并发模型适合实现房间循环、输入队列、消息广播和连接管理。

### 6.3 WebSocket 服务端实现

Go 服务端可以使用成熟的 WebSocket 实现。Gorilla WebSocket 是 Go 的 WebSocket 协议实现，文档说明其 API 稳定，并通过 Autobahn 测试套件。

服务端 WebSocket 层主要负责：

```text
1. 连接升级
2. 鉴权校验
3. 用户连接绑定
4. 心跳检测
5. 消息读取
6. 消息写入
7. 断线处理
8. 消息路由到房间
```

### 6.4 服务端核心模块

## 7. Redis 技术选型

### 7.1 选型结论

Redis 用于缓存、队列、会话与排行榜等实时数据场景。

### 7.2 使用场景

Redis 在本项目中主要用于：

```text
1. 匹配队列
2. 玩家匹配状态
3. WebSocket 会话状态
4. 房间路由信息
5. 断线重连临时状态
6. 局内排行榜缓存
7. 全服排行榜缓存
8. 分布式锁或幂等标记
```

### 7.3 排行榜场景

Redis Sorted Set 适合排行榜场景。Redis 官方文档在 Sorted Set 使用场景中明确提到 Leaderboards，并说明可以用于维护大型在线游戏中的高分有序列表。

排行榜可使用如下结构：

```text
rank:daily:{date}
rank:weekly:{week}
rank:season:{seasonId}
```

常见操作：

```text
ZADD rank:daily:2026-06-28 score userId
ZREVRANGE rank:daily:2026-06-28 0 99 WITHSCORES
ZRANK rank:daily:2026-06-28 userId
```

### 7.4 Redis 数据边界

Redis 不作为最终持久化数据源。

以下数据不能只存 Redis：

```text
1. 用户资产
2. 战绩记录
3. 结算记录
4. 充值或付费相关数据
5. 任务奖励最终结果
```

这些数据必须落 MySQL。

## 8. MySQL 技术选型

### 8.1 选型结论

MySQL 用于存储关系型、强一致要求较高、需要长期保留的数据。

### 8.2 使用场景

MySQL 在本项目中主要用于：

```text
1. 用户基础信息
2. 用户资产
3. 游戏战绩
4. 单局结算记录
5. 奖励发放记录
6. 排行榜历史快照
7. 用户登录记录
8. 配置版本记录
```

### 8.3 推荐核心表

```text
users
user_assets
game_records
game_record_players
settlement_records
rank_snapshots
login_records
```

### 8.4 结算幂等设计

结算写库必须保证幂等。

推荐唯一约束：

```text
room_id + user_id
```

或：

```text
game_id + user_id
```

用于防止同一局游戏重复结算、重复发放奖励。

## 9. 部署技术选型

### 9.1 选型结论

部署方案：

```text
Go 服务端 Docker 化
客户端构建 H5 / 移动端包
```

### 9.2 服务端部署方式

服务端使用 Docker 构建镜像，推荐本地开发阶段使用 Docker Compose 启动：

```text
game-api
game-match
game-server
game-settlement
redis
mysql
```

部署方式：

```text
1. 每个服务独立构建 Docker 镜像
2. 使用环境变量注入配置
3. Redis、MySQL 使用独立容器或外部托管服务
4. 日志输出到 stdout
5. 由容器平台或日志系统采集日志
```

### 9.3 客户端部署方式

客户端根据目标平台构建：

```text
1. H5 包
2. Android 包
3. iOS 包
4. 小游戏平台包
```

第一阶段建议优先构建 H5，方便快速测试多人实时对战流程。

## 11. 实时对战核心流程

```text
1. 玩家点击开始游戏
2. 客户端通过 HTTP 请求进入匹配
3. API Server 校验用户身份与版本
4. Match Server 将玩家加入匹配队列
5. 匹配成功后 Room Coordinator 创建房间
6. Room Coordinator 分配 Game Server
7. 客户端建立 WebSocket 连接
8. 玩家发送 ready
9. Game Server 启动房间 Tick 循环
10. 客户端持续发送输入
11. Game Server 计算移动、碰撞、吞噬
12. Game Server 广播房间状态快照
13. 客户端进行插值渲染
14. Game Server 更新局内排行榜
15. 达到结束条件后进入结算
16. Settlement Server 计算奖励和排名
17. 写入 MySQL 战绩与结算记录
18. 更新 Redis 全服排行榜
19. Game Server 推送结算结果
20. 客户端展示结算页面
```

## 12. 性能与扩展设计

### 12.1 客户端性能关注点

```text
1. 对象池复用
2. 视野裁剪
3. 快照缓冲
4. 插值渲染

6. 食物对象批量渲染
7. 减少频繁节点创建销毁
```

### 12.2 服务端性能关注点

服务端需要重点关注：

```text
1. 房间 Tick 频率
2. 广播频率
3. 单房间玩家数量
4. 输入消息限流
5. AOI 视野同步
6. 快照体积
7. 连接心跳
8. 房间内存释放
```

### 12.3 推荐频率

```text
服务端 Tick：20 次 / 秒
状态快照广播：10 次 / 秒
局内排行榜广播：1 次 / 秒
心跳检测：5 ~ 10 秒一次
```

## 14. 选型风险与应对方案

| 风险                       | 说明                               | 应对方案                              |
| -------------------------- | ---------------------------------- | ------------------------------------- |
| WebSocket 在弱网下延迟波动 | 移动网络环境不稳定                 | 增加心跳、重连、快照恢复、插值渲染    |
| JSON 高频同步包体较大      | 单局 100 人时快照体积可能增大      | 后续升级 Protobuf，并做 AOI 过滤      |
| 客户端对象数量较多         | 食物、玩家分身、特效会增加渲染压力 | 对象池、视野裁剪、低频 UI 刷新        |
| 服务端房间 Tick 压力       | 多房间同时运行会消耗 CPU           | 限制单房间人数、优化 Tick、房间分片   |
| 结算重复执行               | 断线或重试可能导致重复发奖励       | 使用 roomId + userId 唯一约束保证幂等 |
| Redis 数据丢失             | Redis 不适合作为最终持久化来源     | 关键数据必须写入 MySQL                |
| 客户端作弊                 | 客户端可能篡改坐标、质量、结算数据 | 服务端权威计算，客户端只上传输入      |

## 15. 最终选型结论

本项目最终技术选型如下：

```text
客户端：
Cocos Creator 3.x + TypeScript

网络：
WebSocket

协议：
JSON 起步，Protobuf 进阶

服务端：
Go + WebSocket + Redis + MySQL

部署：
Go 服务端 Docker 化
客户端构建 H5 / 移动端包
```

该方案适合 2D 实时多人对战游戏开发，能够较好地支撑匹配、房间、实时同步、排行榜、断线重连和结算等核心能力。

前期使用 JSON 与单体/模块化 Go 服务快速跑通核心流程；中后期通过 Protobuf、AOI、多 GameServer、房间分片、监控压测等方式逐步提升性能和工程化能力。
