## 1. 文档信息

| 项目         | 内容                                         |
| ------------ | -------------------------------------------- |
| 产品名称     | 实时多人对战球球类游戏                       |
| 产品类型     | 2D 休闲竞技 / 多人实时对战                   |
| 客户端形态   | H5 / 移动端                                  |

## 2. 产品背景

本项目是一款 2D 休闲竞技类实时多人对战游戏。玩家进入游戏后，通过匹配系统加入一局对战，在地图中控制自己的球体移动，通过吞噬食物或其他玩家逐渐变大，并根据局内表现获得排名和结算奖励。

产品希望重点验证以下能力：

1. 多人实时对战体验
2. 玩家匹配与房间分配
3. 单局内玩家成长与对抗
4. 局内实时排行榜
5. 对局结束后的排名结算
6. 弱网场景下的断线重连
7. H5 与移动端的可玩性

本项目整体定位为轻量休闲竞技游戏，核心体验应保持简单、直接、低学习成本。

------

## 3. 产品目标

### 3.1 核心目标

| 目标         | 说明                                           |
| ------------ | ---------------------------------------------- |
| 快速进入游戏 | 玩家可以从大厅快速点击开始匹配并进入对局       |
| 实时对战流畅 | 玩家移动、吞噬、分裂等操作需要有较好的实时反馈 |
| 对局规则清晰 | 玩家能够理解如何变强、如何获得排名             |
| 排行反馈明确 | 局内排行榜实时反馈玩家当前表现                 |
| 结算结果完整 | 对局结束后展示排名、得分、奖励、战绩           |
| 支持多人同局 | 目标支持单局 100 人同时在线对战                |
| 支持多端发布 | 客户端支持 H5 构建，并预留移动端构建能力       |

### 3.2 非目标

当前阶段不重点建设以下内容：

1. 复杂社交系统
2. 复杂商城系统
3. 复杂皮肤装扮系统
4. 公会 / 战队系统
5. 语音聊天系统
6. 赛事系统
7. 复杂商业化系统

这些内容可作为后续版本扩展。

## 4. 用户角色

### 4.1 普通玩家

普通玩家是本产品的核心用户。主要行为包括：

1. 登录游戏
2. 查看大厅
3. 点击开始匹配
4. 进入实时对战
5. 操作球体移动、分裂、吐球
6. 查看局内排行榜
7. 查看对局结算
8. 查看历史战绩和排行榜

### 4.2 游客玩家

游客玩家可快速进入游戏体验基础玩法，但部分数据可能不做长期保存。

游客玩家能力：

1. 快速进入游戏
2. 参与匹配和对局
3. 查看本局结算

限制：

1. 不支持长期战绩保存
2. 不支持资产累计
3. 不支持跨设备恢复数据

### 4.3 注册玩家

注册玩家支持完整数据保存。

注册玩家能力：

1. 保存用户资料
2. 保存历史战绩
3. 累计奖励和资产
4. 参与全服排行榜
5. 后续支持皮肤、成就、任务等扩展功能

## 5. 核心玩法概述

### 5.1 玩法简介

玩家控制一个或多个球体在地图中移动。玩家可以通过吞噬地图中的食物增加质量，也可以在满足条件时吞噬比自己小的其他玩家。球体质量越大，体积越大，移动速度越慢。

对局过程中，玩家需要在成长、追击、躲避、分裂、合体之间做出操作决策，最终根据得分、质量、吞噬数量、存活时间等因素进行排名和结算。

### 5.2 核心循环

```text
进入大厅
  ↓
点击开始游戏
  ↓
进入匹配
  ↓
匹配成功进入房间
  ↓
实时对战
  ↓
成长 / 吞噬 / 躲避 / 排名变化
  ↓
游戏结束
  ↓
展示结算
  ↓
返回大厅
```

### 5.3 局内成长方式

玩家可以通过以下方式提升自身表现：

| 成长方式   | 说明                                     |
| ---------- | ---------------------------------------- |
| 吞噬食物   | 地图中分布基础食物，吞噬后增加质量       |
| 吞噬玩家   | 当自身满足吞噬条件时，可吞噬其他较小玩家 |
| 吃特殊物体 | 后续可加入刺球、能量球等特殊对象         |
| 存活时间   | 存活时间越长，结算表现越好               |
| 操作技巧   | 合理使用分裂、吐球、躲避等操作提升排名   |

## 7. 核心用户流程

### 7.1 进入游戏流程

```text
打开客户端
  ↓
加载资源
  ↓
进入登录页 / 游客入口
  ↓
登录成功
  ↓
进入游戏大厅
```

### 7.2 匹配进入对局流程

```text
玩家点击开始游戏
  ↓
客户端发送开始匹配请求
  ↓
服务端校验用户状态
  ↓
玩家进入匹配队列
  ↓
匹配成功
  ↓
服务端分配房间和 Game Server
  ↓
客户端收到 roomId 和 WebSocket 地址
  ↓
客户端建立 WebSocket 连接
  ↓
玩家加载完成并发送 Ready
  ↓
对局开始
```

### 7.3 对局中流程

```text
玩家持续输入移动方向
  ↓
客户端发送输入消息
  ↓
服务端计算玩家位置和游戏状态
  ↓
服务端广播状态快照
  ↓
客户端平滑渲染游戏画面
  ↓
玩家吞噬食物或其他玩家
  ↓
局内排行榜更新
```

### 7.4 结算流程

```text
达到游戏结束条件
  ↓
服务端冻结本局状态
  ↓
计算最终排名
  ↓
计算玩家奖励
  ↓
写入战绩和结算记录
  ↓
更新排行榜
  ↓
客户端收到结算结果
  ↓
展示结算页面
  ↓
玩家返回大厅
```

## 8. 功能需求

## 8.1 登录与用户身份

### 8.1.1 游客登录

用户可以选择游客身份快速进入游戏。

要求：

1. 不强制注册
2. 自动生成临时用户身份
3. 支持参与普通匹配
4. 本局结算正常展示
5. 长期数据可不保存或仅本地保存

### 8.1.2 注册用户登录

用户可以通过账号方式登录。

要求：

1. 登录后进入大厅
2. 用户信息可持久化
3. 战绩可保存
4. 奖励可累计
5. 可参与全服排行榜

------

## 8.2 游戏大厅

### 8.2.1 页面目标

游戏大厅是玩家进入核心玩法前的主界面。

### 8.2.2 页面内容

大厅需要展示：

1. 玩家昵称
2. 玩家头像
3. 当前段位或等级，初期可不做
4. 开始游戏按钮
5. 排行榜入口
6. 战绩入口
7. 设置入口
8. 网络状态提示

### 8.2.3 主要操作

| 操作       | 说明                                   |
| ---------- | -------------------------------------- |
| 开始游戏   | 进入匹配流程                           |
| 查看排行榜 | 查看全服或好友排行，初期可只做全服排行 |
| 查看战绩   | 查看历史对局记录                       |
| 设置       | 调整音效、画质、操作方式等             |

------

## 8.3 匹配系统

### 8.3.1 功能目标

匹配系统负责将玩家分配到合适的对局房间中。

### 8.3.2 匹配入口

玩家在大厅点击“开始游戏”后进入匹配状态。

### 8.3.3 匹配状态

匹配过程包含以下状态：

| 状态       | 说明                       |
| ---------- | -------------------------- |
| 未匹配     | 玩家尚未点击开始           |
| 匹配中     | 玩家已进入匹配队列         |
| 匹配成功   | 服务端已分配房间           |
| 进入房间中 | 客户端正在连接 Game Server |
| 匹配失败   | 匹配超时或服务异常         |
| 取消匹配   | 玩家主动取消               |

### 8.3.4 匹配规则

MVP 阶段可以采用简单匹配规则：

1. 按游戏模式匹配
2. 人数达到阈值后创建房间
3. 超过等待时间后允许较少人数开局
4. 后续支持段位、延迟、地区等维度

### 8.3.5 匹配超时

当玩家等待时间超过阈值时，应给出提示：

1. 继续等待
2. 取消匹配
3. 允许机器人补位，后续版本支持

------

## 8.4 房间与对局

### 8.4.1 房间说明

房间是一局游戏的运行容器。玩家匹配成功后会进入某个房间。

### 8.4.2 房间状态

| 状态      | 说明         |
| --------- | ------------ |
| CREATED   | 房间已创建   |
| WAITING   | 等待玩家进入 |
| LOADING   | 玩家加载中   |
| RUNNING   | 对局进行中   |
| SETTLING  | 结算中       |
| FINISHED  | 对局已结束   |
| DESTROYED | 房间已销毁   |

### 8.4.3 房间人数

目标支持：

```text
单局最多 100 人
```

MVP 阶段可先支持较小人数，例如：

```text
10 ~ 30 人
```

后续通过性能优化和同步优化扩展到 100 人。

------

## 8.5 实时对战

### 8.5.1 玩家移动

玩家通过触控、鼠标或虚拟摇杆控制球体移动方向。

要求：

1. 移动反馈需要连续、平滑
2. 球体不能移动出地图边界
3. 移动速度受球体质量影响
4. 客户端只上传输入，不直接决定最终位置

### 8.5.2 食物吞噬

地图上存在食物对象。

要求：

1. 玩家接触食物后可吞噬
2. 吞噬后玩家质量增加
3. 食物被吞噬后从地图移除
4. 服务端定期补充食物

### 8.5.3 玩家吞噬

玩家之间可以互相吞噬。

要求：

1. 大球可以吞噬小球
2. 吞噬条件由服务端判断
3. 被吞噬玩家进入死亡或重新出生状态，具体规则按玩法设计确定
4. 吞噬成功后攻击方质量增加

### 8.5.4 分裂操作

玩家可执行分裂操作，用于追击或逃脱。

要求：

1. 玩家质量达到阈值后才可分裂
2. 分裂方向根据玩家输入决定
3. 分裂后玩家控制多个球体
4. 分裂存在冷却时间
5. 分裂结果由服务端计算

### 8.5.5 吐球操作

玩家可执行吐球操作，用于喂养、减速调整或战术操作。

要求：

1. 玩家质量达到阈值后可吐球
2. 吐出的球体可被自己或其他玩家吞噬
3. 吐球会降低自身质量
4. 吐球存在频率限制
5. 吐球结果由服务端计算

### 8.5.6 刺球机制

刺球作为地图特殊对象，可在后续版本加入。

可能规则：

1. 大球接触刺球后发生分裂
2. 小球可以躲避刺球
3. 刺球可用于反制大球
4. 刺球刷新位置由服务端控制

------

## 8.6 局内排行榜

### 8.6.1 功能目标

局内排行榜用于展示当前对局中玩家的实时排名。

### 8.6.2 排名依据

可按以下因素计算：

1. 当前质量
2. 当前得分
3. 吞噬数量
4. 存活时间

MVP 阶段建议优先按当前质量或得分排名。

### 8.6.3 展示规则

1. 展示 Top 10 玩家
2. 当前玩家即使不在 Top 10，也应展示自身排名
3. 排行榜低频刷新，避免频繁跳动
4. 排名变化需要有明显反馈

### 8.6.4 更新频率

推荐：

```text
1 秒更新一次
```

当排名变化明显时，也可以即时推送。

------

## 8.7 断线重连

### 8.7.1 功能目标

减少玩家因网络波动导致的对局中断。

### 8.7.2 断线处理

当客户端连接断开后：

1. 服务端标记玩家为断线状态
2. 短时间保留玩家状态
3. 客户端展示重连中提示
4. 超过保留时间后视为退出或死亡

### 8.7.3 重连恢复

当玩家重新连接后：

1. 客户端携带用户身份和房间信息请求重连
2. 服务端校验玩家是否仍在房间
3. 校验成功后返回当前房间快照
4. 客户端恢复对局画面

### 8.7.4 保留时间

建议初始设置：

```text
15 ~ 30 秒
```

------

## 8.8 游戏结算

### 8.8.1 结算触发条件

对局可通过以下条件结束：

1. 达到固定对局时长
2. 房间剩余玩家数量达到结束条件
3. 服务器主动结束异常房间
4. 特殊玩法目标达成

MVP 阶段建议使用固定对局时长，例如：

```text
3 ~ 5 分钟
```

### 8.8.2 结算内容

结算页面展示：

1. 最终排名
2. 最终得分
3. 最大质量
4. 吞噬玩家数量
5. 吞噬食物数量
6. 存活时间
7. 获得金币
8. 获得经验
9. 是否刷新个人最佳
10. 返回大厅按钮
11. 再来一局按钮

### 8.8.3 奖励规则

奖励可由以下因素决定：

1. 最终排名
2. 得分
3. 吞噬数量
4. 存活时间
5. 是否完成任务，后续支持

MVP 阶段奖励规则应保持简单，优先支持金币或经验。

------

## 8.9 战绩系统

### 8.9.1 功能目标

战绩系统用于记录玩家历史对局表现。

### 8.9.2 战绩内容

每局战绩记录：

1. 对局 ID
2. 对局时间
3. 玩家 ID
4. 最终排名
5. 最终得分
6. 最大质量
7. 吞噬玩家数
8. 吞噬食物数
9. 存活时间
10. 奖励结果

### 8.9.3 战绩入口

玩家可从大厅进入战绩页面查看历史记录。

------

## 8.10 全服排行榜

### 8.10.1 功能目标

全服排行榜用于展示玩家在全服范围内的长期表现。

### 8.10.2 排行榜类型

初期支持：

1. 日榜
2. 周榜
3. 总榜，后续支持

### 8.10.3 排名依据

可选择：

1. 历史最高分
2. 累计积分
3. 胜场数
4. 平均排名

MVP 阶段建议优先使用历史最高分或累计积分。

## 10. 游戏规则

## 10.1 基础规则

1. 玩家出生时拥有初始质量
2. 地图中存在随机食物
3. 玩家吞噬食物后增加质量
4. 玩家质量越大，球体半径越大
5. 玩家质量越大，移动速度越慢
6. 玩家可以吞噬比自己小的玩家
7. 玩家被吞噬后进入死亡或重新出生状态
8. 对局结束后按排名结算

## 10.2 吞噬规则

吞噬需要满足：

1. 攻击方质量大于被吞噬方
2. 双方距离满足吞噬条件
3. 被吞噬方未处于保护状态
4. 服务端判定吞噬是否成功

## 10.3 分裂规则

1. 玩家质量达到阈值后可分裂
2. 分裂后形成多个球体
3. 分裂球体向指定方向移动
4. 分裂存在冷却时间
5. 分裂后需要一定时间才能合体，后续支持

## 10.4 吐球规则

1. 玩家质量达到阈值后可吐球
2. 吐球会减少自身质量
3. 吐出的球体可以被玩家吞噬
4. 吐球存在频率限制

## 10.5 排名规则

MVP 阶段建议按当前得分排名。

得分可由以下因素组成：

1. 当前质量
2. 吞噬玩家数量
3. 吞噬食物数量
4. 存活时间

## 11. 非功能需求

## 11.1 性能需求

| 指标         | 目标                              |
| ------------ | --------------------------------- |
| 单局人数     | 目标 100 人                       |
| 客户端帧率   | 尽量保持 30 FPS 以上，目标 60 FPS |
| 状态同步延迟 | 普通网络环境下应尽量保持可接受    |
| 匹配耗时     | 正常情况下尽量控制在数秒内        |
| 排行榜刷新   | 局内排行榜约 1 秒刷新一次         |

## 11.2 可用性需求

1. 匹配失败需要可重试
2. 连接断开需要提示
3. 支持自动重连
4. 重连失败需要回到大厅或结算页
5. 服务异常时需要明确提示，不应长期卡死

## 11.3 安全与公平性需求

1. 客户端只上传玩家输入
2. 服务端计算最终状态
3. 服务端判断吞噬、死亡、排名、奖励
4. 客户端不能直接决定结算结果
5. 服务端需要对异常输入进行限制

## 11.4 兼容性需求

1. H5 版本支持主流浏览器
2. 移动端需要支持触控操作
3. 不同屏幕尺寸下 UI 需要适配
4. 横屏或竖屏模式需在产品阶段确定

## 12. 技术实现概述

### 12.1 总体技术选型

| 网络通信 | WebSocket                                  |
| 初期协议 | JSON                                       |
| 后续协议 | Protobuf                                   |
| 服务端   | Go                                         |
| 缓存     | Redis                                      |
| 数据库   | MySQL                                      |
| 部署     | 服务端 Docker 化，客户端构建 H5 / 移动端包 |

### 12.2 客户端实现方向

客户端主要负责：

1. 游戏场景展示
2. 玩家输入采集
3. WebSocket 通信
4. 服务端状态快照接收
5. 本地平滑渲染
6. UI 页面展示
7. 网络异常提示
8. 结算结果展示

客户端不负责最终游戏状态裁决。

### 12.3 服务端实现方向

服务端主要负责：

1. 用户身份校验
2. 匹配队列管理
3. 房间创建
4. 玩家连接管理
5. 房间 Tick 循环
6. 移动、吞噬、分裂等规则计算
7. 局内排行榜计算
8. 断线重连状态维护
9. 游戏结算
10. 战绩和排行榜写入

### 12.4 数据存储方向

Redis 用于：

1. 匹配队列
2. 玩家会话
3. 重连状态
4. 排行榜缓存

MySQL 用于：

1. 用户信息
2. 用户资产
3. 战绩记录
4. 结算记录

## 15. 风险与应对

| 风险                    | 说明                               | 应对                               |
| ----------------------- | ---------------------------------- | ---------------------------------- |
| 单局 100 人带来同步压力 | 玩家和对象数量较多，快照可能较大   | 后续引入 AOI、快照压缩、Protobuf   |
| 客户端渲染压力较大      | 食物、玩家分身、特效会增加对象数量 | 使用对象池、视野裁剪、分层渲染     |
| 网络不稳定影响体验      | 移动端网络可能出现延迟和断线       | 增加心跳、自动重连、快照恢复       |
| 客户端作弊              | 客户端可能伪造坐标或结算           | 服务端权威计算，客户端只上传输入   |
| 匹配等待时间过长        | 在线人数不足时影响体验             | 超时扩圈、机器人补位、快速开局     |
| 结算重复执行            | 重连、重试可能导致重复发奖励       | 服务端做结算幂等控制               |
| 版本范围膨胀            | 玩法和系统容易不断扩展             | MVP 聚焦完整闭环，扩展功能分期建设 |

## 16. 总结

本产品是一款面向 H5 / 移动端的 2D 实时多人对战游戏，核心体验围绕匹配、实时移动、吞噬成长、局内排名和一局结算展开。

当前阶段产品建设重点不是复杂商业化和社交体系，而是优先跑通完整的多人实时对战闭环：

```text
大厅 → 匹配 → 入房 → 对战 → 排行 → 结算 → 返回大厅
```

技术上采用 Cocos Creator 3.x + TypeScript 作为客户端，Go 作为服务端，WebSocket 作为实时通信方式，JSON 作为初期协议，后续升级 Protobuf。Redis 用于实时缓存和排行榜，MySQL 用于最终持久化。

后续详细设计将围绕匹配系统、房间系统、实时同步、排行榜、断线重连和结算系统分别展开。
