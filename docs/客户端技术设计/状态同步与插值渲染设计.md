# 2. 设计目标

状态同步与插值渲染系统的目标，是让客户端根据服务端下发的权威状态，稳定、平滑地展示对战画面。

它主要解决以下问题：

```text
客户端如何接收服务端快照？
快照数据如何进入本地状态？
玩家和食物如何创建、更新、删除？
网络快照不是每帧到达，画面如何保持平滑？
快照乱序、延迟、丢失时如何处理？
自己和其他玩家是否使用同一套渲染策略？
MVP 阶段做到什么程度，后续如何优化？
```

MVP 阶段优先保证：

1. 能接收 `ROOM_SNAPSHOT`。
2. 能维护本地 `BattleState`。
3. 能根据快照创建玩家球体和食物。
4. 能根据快照更新位置、半径、质量、状态。
5. 能删除已消失对象。
6. 能用轻量插值减少画面跳动。
7. 能处理快照乱序和重复。
8. 能支撑服务端 10 次 / 秒快照同步。

------

# 3. 核心设计原则

## 3.1 服务端权威

客户端展示以服务端快照为准。

客户端不能把本地预测结果当作最终状态。

客户端可以做：

```text
平滑显示
插值渲染
短暂本地过渡动画
```

客户端不能做：

```text
确认碰撞
确认吞噬
确认死亡
确认分数
确认结算
```

------

## 3.2 快照驱动画面

对战画面由快照驱动。

核心链路：

```text
WebSocket 收到 ROOM_SNAPSHOT
  ↓
MessageDispatcher 分发
  ↓
SnapshotReceiver 处理
  ↓
BattleState 更新
  ↓
RenderSystem 插值更新
  ↓
EntityManager 更新 View
```

------

## 3.3 渲染频率与快照频率解耦

服务端快照推荐：

```text
10 次 / 秒
```

客户端渲染推荐：

```text
30 FPS ~ 60 FPS
```

也就是说：

```text
服务端每 100ms 给一次状态
客户端每 16ms ~ 33ms 渲染一帧
```

因此不能只在收到快照时更新画面，否则画面会一卡一卡。
需要用插值让画面在两个快照之间平滑过渡。

------

## 3.4 MVP 先轻量插值，后续再做完整 SnapshotBuffer

MVP 阶段可以先做简单插值：

```text
displayPosition = lerp(displayPosition, targetPosition, factor)
```

后续再升级为：

```text
SnapshotBuffer
  ↓
固定插值延迟
  ↓
按 serverTime 在两个快照之间插值
```

这样先保证实现简单，再逐步增强网络表现。

# 6. 快照接收与校验

## 6.1 接收流程

```text
WsMessageDispatcher 收到 ROOM_SNAPSHOT
  ↓
SnapshotReceiver.handleSnapshot(message)
  ↓
校验 roomId
  ↓
校验 seq / tickSeq
  ↓
校验数据结构
  ↓
更新 BattleState
  ↓
通知 RenderSystem
```

------

## 6.2 快照合法性校验

需要校验：

1. `roomId` 是否等于当前房间。
2. `seq` 是否大于上一次处理的快照序号。
3. `tickSeq` 是否大于等于上一次 tickSeq。
4. `players` 是否为数组。
5. `foods` 是否为数组。
6. 坐标是否为数字。
7. 半径和质量是否为非负数。

------

## 6.3 旧快照处理

如果收到旧快照：

```text
snapshot.seq <= lastSnapshotSeq
```

处理：

1. 丢弃。
2. 记录 debug 日志。
3. 不更新 BattleState。

------

## 6.4 非当前房间快照

如果收到其他房间快照：

```text
snapshot.roomId != currentRoomId
```

处理：

1. 丢弃。
2. 记录 warn 日志。
3. 不影响当前对局。

------

# 7. BattleState 更新设计

## 7.1 全量快照更新

MVP 阶段使用全量快照。

处理方式：

```text
以本次快照为准
  ↓
更新 players
  ↓
更新 balls
  ↓
更新 foods
  ↓
更新 ejectedMass
  ↓
更新 viruses
  ↓
处理 events
```

------

## 7.2 对象映射

为了高效更新，需要使用 Map 结构。

```text
playersById: Map<userId, PlayerState>
ballsById: Map<ballId, BallState>
foodsById: Map<foodId, FoodState>
```

这样可以快速判断：

1. 新对象。
2. 已存在对象。
3. 已删除对象。

------

## 7.3 StateReconciler

`StateReconciler` 负责对比上一帧状态和新快照。

输出：

```text
addedEntities
updatedEntities
removedEntities
```

例如：

```text
新增食物 f_100
更新玩家球 b_10001_1
删除食物 f_88
```

# 8. 实体生命周期设计

## 8.1 生命周期状态

| 状态     | 说明           |
| -------- | -------------- |
| CREATED  | 新创建         |
| ACTIVE   | 正常显示       |
| UPDATING | 正在更新       |
| REMOVING | 准备移除       |
| RECYCLED | 已回收到对象池 |

------

## 8.2 新增对象

当快照中出现本地不存在的对象：

```text
EntityManager.createEntity()
  ↓
ObjectPoolManager.get()
  ↓
初始化 View
  ↓
挂到对应 Layer
  ↓
状态 ACTIVE
```

------

## 8.3 更新对象

当对象已存在：

```text
更新 targetPosition
更新 targetRadius
更新 mass
更新 nickname
更新 alive
```

注意：

```text
不要直接瞬移到 targetPosition
而是交给 InterpolationSystem 平滑到目标位置
```

------

## 8.4 删除对象

当对象在新快照中不存在：

```text
标记 REMOVING
  ↓
可选播放消失动画
  ↓
回收到对象池
```

MVP 可直接回收。

后续可以：

1. 食物被吃时缩小消失。
2. 玩家死亡时播放吞噬特效。
3. 吐出物消失时淡出。

# 9. 插值渲染设计

## 9.1 为什么需要插值

服务端快照 10 次 / 秒：

```text
每 100ms 更新一次状态
```

客户端渲染 60 FPS：

```text
每 16.67ms 渲染一次
```

如果客户端每次收到快照后直接更新位置，玩家球体会出现跳动。
插值用于在两个快照之间平滑过渡。

------

## 9.2 MVP 简化插值

MVP 推荐使用目标插值。

每个实体维护：

```text
displayX
displayY
targetX
targetY
displayRadius
targetRadius
```

每帧更新：

```text
displayX = lerp(displayX, targetX, positionLerpFactor)
displayY = lerp(displayY, targetY, positionLerpFactor)
displayRadius = lerp(displayRadius, targetRadius, radiusLerpFactor)
```

推荐：

```text
positionLerpFactor = 0.2 ~ 0.35
radiusLerpFactor = 0.2 ~ 0.35
```

------

## 9.3 MVP 插值优点

1. 实现简单。
2. 不依赖复杂时间轴。
3. 适合快速验证。
4. 对轻量实时游戏足够可用。
5. 调试成本低。

------

## 9.4 MVP 插值缺点

1. 网络波动大时可能有拖尾感。
2. 无法严格按服务端时间回放。
3. 快照间隔不稳定时表现不够准确。
4. 大幅度位置变化时可能追不上目标。

因此后续需要升级为 SnapshotBuffer 插值。

------

# 10. SnapshotBuffer 设计，P1

## 10.1 设计目标

SnapshotBuffer 用于保存最近几帧服务端快照。

```text
SnapshotBuffer
├── snapshot_1
├── snapshot_2
├── snapshot_3
└── snapshot_n
```

客户端渲染时不直接渲染最新快照，而是渲染稍微滞后的时间点。

------

## 10.2 插值延迟

推荐：

```text
interpolationDelayMs = 100 ~ 200ms
```

渲染时间：

```text
renderTime = estimatedServerTime - interpolationDelayMs
```

然后在 SnapshotBuffer 中找到：

```text
snapshotA.serverTime <= renderTime <= snapshotB.serverTime
```

进行插值。

------

## 10.3 时间插值公式

```text
alpha = (renderTime - snapshotA.serverTime) / (snapshotB.serverTime - snapshotA.serverTime)
```

位置：

```text
x = lerp(snapshotA.x, snapshotB.x, alpha)
y = lerp(snapshotA.y, snapshotB.y, alpha)
radius = lerp(snapshotA.radius, snapshotB.radius, alpha)
```

------

## 10.4 SnapshotBuffer 优点

1. 画面更平滑。
2. 网络抖动更稳定。
3. 快照间隔不稳定时表现更好。
4. 更适合正式版本。

------

## 10.5 SnapshotBuffer 当前阶段策略

MVP 阶段可以先保留类名和接口，但内部先用简化实现。

后续 P1 再完善。

# 11. 自己角色与其他玩家处理

## 11.1 MVP 策略

MVP 阶段自己和其他玩家都使用服务端快照驱动。

也就是说：

```text
自己移动也以服务端下发位置为准
```

客户端只负责发送 MOVE，不做复杂预测。

------

## 11.2 后续本地预测

后续可对自己角色做轻量预测：

```text
客户端根据输入先移动自己
  ↓
服务端快照到达后校正
```

优点：

1. 操作响应更快。
2. 手感更好。

缺点：

1. 需要处理校正。
2. 需要处理预测误差。
3. 实现复杂度上升。

当前阶段先不实现。

1. 食物不存在则直接消失。
2. 玩家死亡则直接隐藏。
3. 吞噬玩家事件用于显示提示。
4. 分裂 / 吐球事件可后置。

# 13. 快照丢失与网络抖动处理

## 13.1 快照 seq 不连续

如果收到：

```text
snapshot.seq > lastSnapshotSeq + 1
```

说明中间可能丢了消息。

MVP 处理：

1. 接受最新快照。
2. 记录 debug / warn。
3. 继续渲染。

因为 MVP 是全量快照，所以丢一帧问题不大。

------

## 13.2 长时间未收到快照

如果超过一定时间没有快照：

```text
now - lastSnapshotReceiveTime > 1000ms
```

处理：

1. 显示网络不稳定。
2. 暂停或继续轻量插值到目标。
3. 等待心跳判断是否断线。
4. 进入重连流程，P1。

------

## 13.3 快照突然大幅跳变

原因可能是：

1. 服务端校正。
2. 玩家被吞噬。
3. 重连恢复。
4. 网络延迟导致状态跳变。

处理策略：

| 情况           | 处理               |
| -------------- | ------------------ |
| 普通小距离变化 | 插值               |
| 大距离变化     | 直接瞬移或快速追踪 |
| 重连恢复       | 清空状态后重建     |
| 死亡 / 消失    | 直接移除或播放特效 |

推荐阈值：

```text
distance > 500 时直接设置到目标位置
```

避免长距离慢慢追导致位置严重落后。

# 14. AOI 场景预留

## 14.1 AOI 快照类型

后续服务端可能下发：

```text
AOI_FULL_SNAPSHOT
AOI_DELTA
```

MVP 当前使用：

```text
FULL
```

------

## 14.2 对象离开视野

AOI 模式下，对象消失不一定代表死亡，可能只是离开视野。

因此后续需要区分：

| 类型    | 含义       |
| ------- | ---------- |
| left    | 离开视野   |
| deleted | 对象被删除 |
| dead    | 玩家死亡   |

MVP 全量快照可暂不区分。

# 16. 与 EntityManager 的关系

## 16.1 EntityManager 职责

EntityManager 负责：

1. 根据状态创建 View。
2. 根据状态更新 View。
3. 回收消失对象。
4. 维护 id 到 View 的映射。

```text
ballViews: Map<ballId, PlayerBallView>
foodViews: Map<foodId, FoodView>
```

------

## 16.2 RenderSystem 职责

RenderSystem 每帧执行：

```text
for each active entity:
    InterpolationSystem.update(entity, dt)
    entity.view.applyDisplayState()
```

------

## 16.3 View 职责

View 只负责表现：

1. 设置位置。
2. 设置大小。
3. 设置颜色。
4. 设置昵称。
5. 播放简单动画。

View 不负责快照解析和业务规则。

------

# 17. 与 CameraController 的关系

## 17.1 自己中心点计算

MVP 单球体：

```text
cameraTarget = selfBall.position
```

多球体：

```text
cameraTarget = average(selfBalls.position)
```

更准确的后续方案：

```text
cameraTarget = boundingBoxCenter(selfBalls)
```

------

## 17.2 相机更新时机

RenderSystem 更新实体位置后：

```text
更新 self displayPosition
  ↓
CameraController 跟随 self displayPosition
```

这样镜头跟随的是平滑后的显示位置，而不是跳变的目标位置。

------

# 18. 性能设计

## 18.1 性能压力来源

状态同步和插值渲染的压力主要来自：

1. 快照解析。
2. 大量实体 Map 对比。
3. 食物对象创建和删除。
4. 每帧插值更新。
5. 文本节点刷新。
6. UI 高频更新。

------

## 18.2 MVP 优化策略

| 策略          | 说明                 |
| ------------- | -------------------- |
| Map 存储实体  | 快速查找             |
| 对象池        | 减少创建销毁         |
| 文本少刷新    | 昵称和质量不要每帧改 |
| HUD 限频      | 排行榜 1 秒更新      |
| 食物轻量 View | 食物节点结构简单     |
| 快照校验轻量  | 不做过度深拷贝       |
| 可见性裁剪    | 视野外对象隐藏       |

------

## 18.3 快照处理频率

如果服务端快照频率为 10/s，客户端每秒处理 10 次快照。
每次快照尽量只做：

1. 数据校验。
2. Map 对比。
3. target 值更新。
4. 增删对象。

不要在快照处理函数里做复杂动画。

------

# 19. 异常处理设计

## 19.1 快照解析失败

处理：

1. 记录错误日志。
2. 丢弃该消息。
3. 不影响当前画面。
4. 连续失败多次可断开连接。

------

## 19.2 自己球体丢失

如果快照中自己没有 active ball：

1. 判断自己是否死亡。
2. 如果 alive=false，输入状态切换 DEAD。
3. HUD 显示已淘汰。
4. 等待 GAME_END / SETTLEMENT_RESULT。

------

## 19.3 对象池取对象失败

处理：

1. 尝试新建对象。
2. 如果新建也失败，记录 error。
3. 跳过该对象渲染。
4. 不让整个场景崩溃。

------

## 19.4 快照数据异常

例如半径为负数、坐标不是数字。

处理：

1. 跳过异常对象。
2. 记录 warn。
3. 继续处理其他对象。

# 23. 总结

状态同步与插值渲染的核心链路是：

```text
ROOM_SNAPSHOT
  ↓
SnapshotReceiver 校验
  ↓
BattleState 更新
  ↓
StateReconciler 对比实体变化
  ↓
EntityManager 创建 / 更新 / 删除 View
  ↓
InterpolationSystem 平滑显示
  ↓
CameraController 跟随自己
  ↓
HUD 更新
```

MVP 阶段重点做好：

1. 全量快照接收。
2. 快照乱序丢弃。
3. 玩家和食物实体同步。
4. 新增、更新、删除对象。
5. 目标插值渲染。
6. 大距离校正。
7. 自己球体识别。
8. 镜头跟随平滑位置。
9. HUD 与排行榜更新。
10. 网络异常时不崩溃。

先用简单可靠的目标插值把画面跑顺，后续再逐步升级 SnapshotBuffer、AOI 增量同步、Protobuf 和客户端预测。
