# 2. 设计目标

对战场景渲染模块的目标，是把服务端同步过来的对局状态，稳定地表现成玩家可交互、可观察、可结算的一局游戏画面。

它主要解决以下问题：

```text
地图怎么展示？
玩家球体怎么展示？
食物怎么展示？
多个实体怎么高效更新？
镜头怎么跟随自己？
排行榜和 HUD 怎么叠加显示？
快照同步过来后如何更新画面？
H5 环境下如何控制性能？
```

------

## 2.1 MVP 目标

MVP 阶段优先做到：

1. 能展示地图边界和基础背景。
2. 能展示自己和其他玩家球体。
3. 能展示食物。
4. 能根据快照更新实体位置和大小。
5. 能展示局内 HUD 和排行榜。
6. 能让镜头跟随自己。
7. 能支撑 100 人一局的基础渲染。
8. 能在 H5 横屏环境下稳定运行。

------

## 2.2 当前阶段不追求的目标

当前阶段先不要做过深的高阶渲染能力。

暂不实现：

```text
复杂粒子特效
高级后处理
真实 3D 表现
复杂骨骼动画
回放渲染
观战视角系统
复杂遮挡系统
多地图动态光照
复杂天气和环境系统
```

------

# 3. 渲染设计原则

## 3.1 服务端权威，客户端表现

客户端渲染层不负责决定游戏结果，只负责表现。

客户端不负责：

1. 碰撞判定。
2. 吞噬判定。
3. 最终位置合法性。
4. 质量变化是否合法。
5. 排名计算。
6. 结算计算。

客户端负责：

1. 把状态渲染出来。
2. 播放动画和表现。
3. 展示 UI。
4. 让画面尽量平滑。

------

## 3.2 分层渲染

对战场景必须按层组织，避免 UI、地图、实体混杂。

基本原则：

```text
地图和实体分层
实体和特效分层
游戏世界和 UI 分层
对战对象和大厅对象分离
```

------

## 3.3 数据驱动渲染

所有实体表现都由状态驱动。

流程为：

```text
WebSocket 快照
  ↓
GameState / BattleState
  ↓
RenderSystem
  ↓
EntityManager
  ↓
View 更新
```

渲染层不直接依赖网络消息细节，而是依赖统一状态模型。

------

## 3.4 高频对象必须复用

对战场景里食物、球体、吐出物数量较多，不能频繁创建销毁节点。

原则：

1. 使用对象池。
2. 尽量复用节点。
3. 删除对象优先回收到池。
4. 避免每帧 new 对象。
5. 避免频繁创建组件。

------

# 5. 坐标系与地图设计

## 5.1 世界坐标系

服务端快照中的位置使用统一世界坐标。

例如：

```text
地图宽：10000
地图高：10000
左下角：(0, 0)
右上角：(10000, 10000)
```

客户端渲染时也采用同一套世界坐标，避免额外转换复杂度。

------

## 5.2 地图边界展示

MVP 阶段地图边界可简化为：

1. 纯色或渐变背景。
2. 边界线。
3. 四周限制区域。
4. 可选网格背景。

视觉目标：

```text
让玩家知道地图范围
让玩家感觉有空间感
不使用过重背景影响性能
```

------

## 5.3 地图内容

MVP 地图不做复杂地形。

只保留：

| 元素     | 说明               |
| -------- | ------------------ |
| 地图背景 | 对战主底图         |
| 边界框   | 告知活动区域       |
| 网格背景 | 可选，增强空间参照 |
| 食物散点 | 主要可交互元素     |
| 玩家球体 | 主体               |
| 吐出物   | P1                 |
| 刺球     | P1                 |

------

# 6. 摄像机设计

## 6.1 镜头职责

对战相机负责：

1. 跟随当前玩家中心。
2. 保持玩家处于视觉中心区域。
3. 根据玩家体积缩放视野。
4. 限制相机不越出地图边界。

------

## 6.2 镜头跟随规则

MVP 推荐：

```text
相机中心跟随自己球体中心
```

如果玩家分裂为多个球：

```text
相机跟随所有自己球体的包围盒中心
```

------

## 6.3 缩放规则

球越大，视野需要越远。

推荐规则：

1. 玩家体积越大，camera zoom 越小。
2. 玩家体积越小，camera zoom 越大。
3. 设置最小缩放和最大缩放阈值。

例如：

| 状态 | 视野策略 |
| ---- | -------- |
| 小球 | 镜头更近 |
| 中球 | 正常视野 |
| 大球 | 镜头拉远 |

------

## 6.4 镜头边界限制

当玩家靠近地图边界时，相机不能继续移动到地图外。

处理方式：

```text
计算目标相机位置
  ↓
结合当前 zoom 计算可见区域
  ↓
将相机位置 clamp 到地图范围内
```

------

## 6.5 镜头平滑

MVP 可以先做轻量平滑：

```text
cameraPosition = lerp(current, target, factor)
```

目标：

1. 避免镜头抖动。
2. 避免快照更新时突然跳动。
3. 不引入太重的跟随延迟。

------

# 7. 实体渲染设计

## 7.1 实体分类

对战场景主要实体：

| 实体类型    | 说明               | MVP 是否需要 |
| ----------- | ------------------ | ------------ |
| PlayerBall  | 玩家球体           | 需要         |
| Food        | 食物               | 需要         |
| EjectedMass | 吐出物             | 可后置       |
| Virus       | 刺球               | 可后置       |
| Effect      | 吞噬/分裂/死亡特效 | 可后置或简化 |

------

## 7.2 实体表现结构

每类实体由三部分组成：

```text
状态数据
  ↓
View 组件
  ↓
渲染节点
```

例如 PlayerBall：

```text
PlayerBallState
  ↓
PlayerBallView
  ↓
Node + Sprite + Label + Effect
```

------

# 8. 玩家球体渲染设计

## 8.1 玩家球体需要展示的信息

| 信息            | 说明                   |
| --------------- | ---------------------- |
| 球体外观        | 主体圆球               |
| 球体颜色 / 皮肤 | MVP 可用纯色或简单皮肤 |
| 玩家昵称        | 显示在球体上方或中间   |
| 质量 / 分数     | 可显示，MVP 可选       |
| 是否自己        | 自己和别人要有视觉区分 |
| 存活状态        | 死亡后隐藏或淡出       |

------

## 8.2 节点结构建议

```text
PlayerBallNode
├── BodySprite
├── NameLabel
├── MassLabel，可选
├── Outline，自身高亮可选
└── EffectAnchor
```

------

## 8.3 外观策略

MVP 建议：

1. 使用圆形 Sprite。
2. 使用纯色或少量预设皮肤。
3. 自己的球体边缘高亮。
4. 昵称常显。
5. 质量值可根据球体大小决定是否显示。

------

## 8.4 多球体玩家

后续支持分裂后，一个玩家会有多个 ball。

因此渲染结构上不要假设：

```text
1 个玩家 = 1 个球体
```

而应设计为：

```text
1 个玩家 = N 个球体
```

即：

```text
PlayerEntity
├── userId
├── nickname
└── balls[]
```

这样后续支持分裂时不用重构渲染架构。

------

## 8.5 自己的球体视觉强调

自己是操作主体，需要更容易识别。

可用方式：

1. 更亮描边。
2. 底部淡光圈。
3. 镜头始终围绕自己。
4. 自己名称颜色不同。

MVP 建议只做：

```text
描边 + 名称颜色区分
```

------

# 9. 食物渲染设计

## 9.1 食物特点

食物数量较多，单体简单，是性能敏感对象。

特点：

1. 数量多。
2. 尺寸小。
3. 频繁生成和消失。
4. 表现简单。

------

## 9.2 食物表现

MVP 建议：

1. 单个圆点 Sprite。
2. 多种预设颜色。
3. 不显示文本。
4. 支持被吞噬时播放简单缩放消失动画，可后置。

------

## 9.3 节点结构

```text
FoodNode
└── FoodSprite
```

保持轻量，不挂多余组件。

------

## 9.4 数量控制

MVP 阶段虽然逻辑上可以有较多食物，但渲染上建议控制同屏数量。

控制方式：

1. 只渲染视野内食物。
2. 视野外食物不创建节点。
3. 后续配合 AOI。
4. 当前若使用全量快照，也优先只更新可见对象。

------

# 10. 吐出物渲染设计

## 10.1 吐出物定位

吐出物是中间态实体，数量通常少于食物，多于玩家球。

它需要展示：

1. 基础圆球。
2. 有方向感的移动感。
3. 被吞噬或被再次吃掉后消失。

------

## 10.2 MVP 策略

吐出物可以作为 P1：

| 阶段     | 策略                               |
| -------- | ---------------------------------- |
| MVP 初版 | 协议预留，渲染可暂不实现或极简实现 |
| P1       | 增加独立层和对象池                 |
| 后续     | 增加吐出动画和轨迹表现             |

------

# 11. 刺球渲染设计

## 11.1 刺球定位

刺球用于增加玩法复杂度，但当前阶段不是必做。

------

## 11.2 当前建议

| 阶段 | 策略                 |
| ---- | -------------------- |
| MVP  | 不做                 |
| P1   | 支持静态刺球渲染     |
| P2   | 支持刺球触发分裂表现 |

------

# 12. 特效渲染设计

## 12.1 特效类型

后续可支持：

| 特效       | 说明                       |
| ---------- | -------------------------- |
| 吞噬特效   | 吃到食物或玩家             |
| 分裂特效   | 分裂瞬间                   |
| 吐球特效   | 吐出动作反馈               |
| 死亡特效   | 玩家被吞噬                 |
| 重生特效   | 若后续支持复活             |
| 高排名特效 | 排名第一时光效，可后续支持 |

------

## 12.2 MVP 建议

MVP 只做极简特效：

1. 球体缩放变化。
2. 吞噬后简单闪动。
3. 被吞噬对象直接消失或淡出。
4. 不做复杂粒子系统。

------

# 13. HUD 与 UI 渲染设计

## 13.1 HUD 组成

对战页 HUD 建议包含：

| 元素            | 说明          | MVP 是否需要 |
| --------------- | ------------- | ------------ |
| 剩余时间        | 对局倒计时    | 需要         |
| 当前排名        | 自己当前排名  | 需要         |
| 当前分数 / 质量 | 当前成长值    | 需要         |
| 局内排行榜      | Top N         | 需要         |
| 虚拟摇杆        | 输入控制      | 需要         |
| 分裂按钮        | 操作按钮      | 可预留       |
| 吐球按钮        | 操作按钮      | 可预留       |
| 网络状态        | 延迟/断线状态 | 可后置       |
| 小地图          | 位置辅助      | 后续支持     |

------

## 13.2 HUD 分层

UI 必须和世界层分离。

```text
WorldRoot 负责地图和实体
UIRoot 负责 HUD 和交互
```

这样镜头移动不会影响 UI。

------

## 13.3 排行榜设计

排行榜建议显示：

1. Top 5 或 Top 10。
2. 玩家昵称。
3. 当前分数。
4. 自己名次单独展示。

刷新频率不需要太高，建议：

```text
1 秒刷新一次
```

------

## 13.4 摇杆与操作按钮

UI 层中：

| 区域 | 内容                  |
| ---- | --------------------- |
| 左下 | 虚拟摇杆              |
| 右下 | 分裂 / 吐球按钮       |
| 右上 | 局内排行榜            |
| 上中 | 倒计时 / 当前分数     |
| 中间 | 重连提示 / 结算中提示 |

------

# 14. 渲染更新流程

## 14.1 主流程

```text
收到 ROOM_SNAPSHOT
  ↓
BattleState 更新
  ↓
RenderSystem 对比当前实体
  ↓
创建 / 更新 / 删除实体
  ↓
EntityManager 下发到各 View
  ↓
CameraController 更新镜头
  ↓
HUD 更新
```

------

## 14.2 创建 / 更新 / 删除策略

### 创建

当快照中有本地不存在的对象：

```text
从对象池取节点
  ↓
初始化 View
  ↓
挂到对应 Layer
```

### 更新

对象已存在：

```text
更新位置
更新半径
更新名称
更新状态
```

### 删除

快照中不存在了：

```text
停止显示
  ↓
回收到对象池
```

------

## 14.3 更新优先级

推荐优先级：

1. 自己的球体。
2. 其他玩家球体。
3. 食物。
4. 吐出物。
5. 特效。
6. 调试元素。

确保主体验对象优先被更新。

------

# 15. 插值与平滑策略

## 15.1 MVP 策略

MVP 阶段可以先直接用快照值更新位置，再做轻量平滑。

例如：

```text
displayPos = lerp(displayPos, snapshotPos, factor)
```

目标：

1. 避免硬跳。
2. 减少网络离散感。
3. 实现简单。

------

## 15.2 后续增强

后续可引入：

1. SnapshotBuffer。
2. 固定渲染延迟。
3. 插值系统。
4. 增量快照配合。
5. 自己角色弱预测。

但当前阶段先不要引入复杂预测回滚。

------

# 16. 对象池设计

## 16.1 对象池适用对象

必须对象池化的对象：

| 对象            | 原因                   |
| --------------- | ---------------------- |
| FoodNode        | 数量多、创建销毁频繁   |
| PlayerBallNode  | 分裂和死亡时会频繁变化 |
| EjectedMassNode | 中频对象               |
| EffectNode      | 特效节点短生命周期     |

------

## 16.2 对象池管理器

建议统一由 `ObjectPoolManager` 管理。

```text
ObjectPoolManager
├── playerBallPool
├── foodPool
├── ejectedMassPool
└── effectPool
```

------

## 16.3 池化流程

```text
需要对象
  ↓
先从对象池获取
  ↓
没有则实例化
  ↓
使用完成后 reset
  ↓
回收进对象池
```

------

## 16.4 回收前清理内容

回收前要清理：

1. 位置。
2. 缩放。
3. 文本。
4. 动画状态。
5. 特效状态。
6. 事件监听。
7. 引用状态。

避免脏状态污染下一次复用。

------

# 17. 视野裁剪与可见性控制

## 17.1 MVP 裁剪策略

MVP 即使服务端先发全量快照，客户端渲染也应只展示视野内对象。

基本策略：

```text
对象在相机可见范围内 → 显示
对象在相机可见范围外 → 隐藏或不创建
```

------

## 17.2 可见范围计算

根据相机中心和当前缩放，可算出可视矩形：

```text
visibleRect = cameraWorldRect + margin
```

加入一定 margin，避免对象刚进边缘时频繁显示隐藏。

------

## 17.3 后续与 AOI 配合

后续服务端支持 AOI 后：

```text
客户端收到的本来就是附近对象
  ↓
客户端继续做轻量视野裁剪
```

这样网络层和渲染层共同降低负担。

------

# 18. 资源管理设计

## 18.1 对战场景资源内容

| 资源类型   | 内容                             |
| ---------- | -------------------------------- |
| 地图资源   | 背景图、边界图                   |
| 实体预制体 | 玩家球、食物、吐出物             |
| UI 预制体  | HUD、排行榜、摇杆、按钮          |
| 字体资源   | 名称、HUD 文字                   |
| 音效资源   | 吃食物、吞噬、按钮点击，后续可加 |

------

## 18.2 加载策略

推荐：

1. BootScene 加载全局通用资源。
2. 进入 GameScene 前预加载对战资源。
3. 进入对战中尽量不做大资源同步加载。
4. 结算页资源可提前一并加载或按需加载。

------

## 18.3 释放策略

离开 GameScene 后：

1. 清空 BattleState。
2. 清理 EntityManager。
3. 回收对象池中实体。
4. 保留可复用的常驻资源。
5. 大型临时资源可释放。

------

# 19. 与其他模块的关系

## 19.1 与网络层关系

网络层负责：

1. 收到 ROOM_SNAPSHOT。
2. 收到 RANK_UPDATE。
3. 收到 GAME_END。
4. 收到 SETTLEMENT_RESULT。

渲染层不直接解析原始 socket 字符串。

------

## 19.2 与状态层关系

状态层负责：

1. 保存权威状态。
2. 统一数据结构。
3. 维护玩家、食物、吐出物等集合。

渲染层从状态层取数据更新画面。

------

## 19.3 与输入层关系

输入层负责：

1. 采集摇杆方向。
2. 管理分裂 / 吐球按钮。
3. 发送输入消息。

渲染层负责显示输入 UI，不负责协议发送。

------

## 19.4 与结算层关系

当 GAME_END 后：

1. 渲染层停止输入。
2. HUD 进入结束态。
3. 等待结算消息。
4. 切换到 SettlementScene。

------

# 20. 性能设计

## 20.1 性能目标

H5 场景下建议目标：

| 项目       | 目标                                 |
| ---------- | ------------------------------------ |
| 帧率目标   | 30 FPS 起步，理想 60 FPS             |
| 同屏玩家   | 100 人逻辑支持，实际同屏依赖视野范围 |
| 食物数量   | 视野内可控                           |
| 排行榜刷新 | 1 秒一次                             |
| 快照频率   | 10 次 / 秒                           |
| 输入频率   | 20 次 / 秒                           |

------

## 20.2 性能优化重点

优先级从高到低：

1. 对象池。
2. 只渲染可见对象。
3. 控制节点数量。
4. 降低 UI 高频刷新。
5. 降低复杂特效。
6. 简化文本显示数量。
7. 镜头和插值逻辑保持轻量。

------

## 20.3 文本性能控制

昵称和质量值会增加性能开销。

建议：

1. 昵称始终显示。
2. 质量值可只给自己显示，或大球显示。
3. 远处对象可不显示质量文本。
4. 同屏文本数量控制。

------

# 21. 异常处理设计

## 21.1 快照为空

如果收到空快照：

1. 不报错崩溃。
2. 记录日志。
3. 保持当前状态或等待下一帧。

------

## 21.2 自己对象不存在

如果快照中没有找到自己的球体：

1. 可能已死亡。
2. 标记自己状态为死亡。
3. HUD 提示已淘汰。
4. 等待 GAME_END 或结算结果。

------

## 21.3 资源加载失败

如果某个预制体加载失败：

1. 记录错误日志。
2. 使用兜底样式。
3. 不影响整个场景崩溃。

------

## 21.4 WebSocket 断开

渲染层表现：

1. 冻结操作按钮。
2. 弹出重连遮罩。
3. 暂停快照驱动更新。
4. 根据重连结果恢复或退出。

# 24. 总结

对战场景渲染模块的核心任务，是把服务端状态稳定、清晰、可控地表现出来。

MVP 阶段的渲染主链路可以概括为：

```text
ROOM_SNAPSHOT
  ↓
BattleState
  ↓
RenderSystem
  ↓
EntityManager
  ↓
Player / Food / HUD 渲染
  ↓
Camera 跟随
  ↓
玩家完成一局对战
```

当前最重要的是先把以下内容做稳：

1. 地图背景和边界。
2. 玩家球体渲染。
3. 食物渲染。
4. 实体对象池。
5. 镜头跟随与缩放。
6. HUD 与排行榜。
7. 基于快照的创建、更新、删除。
8. H5 环境下的基础性能控制。

先把“能看、能玩、能结束一局”的表现链路做好，后续再逐步增强插值、AOI、特效、吐球、分裂和更复杂的视觉效果。
