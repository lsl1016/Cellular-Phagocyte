# 2. 设计背景

《吞噬细胞》客户端是一个 H5 实时多人对战客户端。玩家从打开页面到完成一局游戏，会经过：

```text
启动
  ↓
登录
  ↓
大厅
  ↓
匹配
  ↓
WebSocket 入房
  ↓
对战
  ↓
状态同步
  ↓
断线重连
  ↓
结算
  ↓
返回大厅
```

客户端运行环境复杂，可能出现：

| 问题     | 需要日志定位的信息                              |
| ------ | -------------------------------------- |
| 页面打不开  | 资源加载状态、启动阶段、浏览器信息                      |
| 登录失败   | 接口状态、错误码、traceId                       |
| 匹配失败   | matchId、接口响应、匹配状态                      |
| 入房失败   | roomId、wsUrl、enterToken 状态、错误码         |
| 对战卡顿   | FPS、实体数量、快照大小、渲染耗时                     |
| 摇杆没反应  | 输入状态、是否处于 PLAYING、WebSocket 状态         |
| 画面不同步  | snapshotSeq、tickSeq、快照延迟、丢包情况          |
| 断线重连失败 | reconnectToken、attempt、reason          |
| 结算页没出来 | GAME_END、SETTLEMENT_RESULT、HTTP 查询结算结果 |
| 浏览器卡死  | 节点数量、JSON 解析耗时、快照应用耗时                  |

所以客户端日志需要覆盖 **业务链路日志 + 网络日志 + 对战日志 + 性能日志 + 错误日志**。

# 3. 设计目标

## 3.1 核心目标

| 目标     | 说明                                     |
| ------ | -------------------------------------- |
| 支持本地调试 | 开发环境可以在浏览器控制台查看详细日志                    |
| 支持问题定位 | 能通过 userId、roomId、matchId、traceId 定位问题 |
| 支持网络排查 | 记录 HTTP、WebSocket、心跳、重连状态              |
| 支持对战排查 | 记录快照、输入、状态同步、结算关键事件                    |
| 支持性能观察 | 记录 FPS、实体数量、快照大小、处理耗时                  |
| 支持日志分级 | DEBUG / INFO / WARN / ERROR            |
| 支持日志采样 | 高频日志不能全量输出                             |
| 支持后续上报 | 后续可以把客户端异常日志上报到服务端                     |
| 不影响性能  | 日志系统本身不能导致客户端卡顿                        |

# 5. 日志级别设计

## 5.1 日志级别

| 级别    | 使用场景                        |
| ----- | --------------------------- |
| DEBUG | 调试信息，高频状态，开发环境使用            |
| INFO  | 正常业务流程，如登录成功、匹配成功、入房成功      |
| WARN  | 可恢复异常，如网络波动、快照乱序、重连失败一次     |
| ERROR | 明确错误，如登录失败、入房失败、快照解析失败、结算失败 |

---

## 5.2 环境默认级别

| 环境        | 默认级别         | 说明          |
| --------- | ------------ | ----------- |
| local     | DEBUG        | 本地开发，输出详细日志 |
| dev       | DEBUG / INFO | 联调环境，可较详细   |
| test      | INFO         | 测试环境，减少高频日志 |
| prod      | WARN         | 生产环境默认只输出异常 |
| prod 故障排查 | INFO         | 临时开启，谨慎使用   |

---

## 5.3 高频日志控制

以下日志默认不要在生产环境输出：

```text
MOVE 发送
ROOM_SNAPSHOT 收到
FoodView 更新
RenderSystem 每帧更新
Joystick move
Heartbeat ping / pong
```

这些只能在开发环境或采样模式下输出。

# 6. 统一日志结构

## 6.1 基础字段

客户端日志推荐统一结构：

```json
{
  "timestamp": 1710000000000,
  "level": "info",
  "event": "ws_connected",
  "message": "websocket connected",
  "traceId": "trace_xxx",
  "userId": "10001",
  "roomId": "r_90001",
  "matchId": "m_10001",
  "scene": "GameScene",
  "clientVersion": "1.0.0",
  "platform": "h5"
}
```

---

## 6.2 字段说明

| 字段              | 是否必填 | 说明                          |
| --------------- | ---- | --------------------------- |
| timestamp       | 是    | 客户端时间戳，毫秒                   |
| level           | 是    | debug / info / warn / error |
| event           | 是    | 日志事件名                       |
| message         | 是    | 日志说明                        |
| traceId         | 否    | 链路 ID                       |
| userId          | 否    | 当前玩家 ID                     |
| roomId          | 否    | 当前房间 ID                     |
| matchId         | 否    | 当前匹配 ID                     |
| scene           | 否    | 当前场景                        |
| clientVersion   | 是    | 客户端版本                       |
| protocolVersion | 否    | 协议版本                        |
| platform        | 是    | h5 / webview / mini-game    |
| data            | 否    | 扩展字段                        |

# 7. TraceId 设计

## 7.1 HTTP TraceId

客户端发起 HTTP 请求时生成或透传 `traceId`：

```http
X-Trace-Id: trace_xxx
```

HTTP 请求日志和服务端日志都带同一个 traceId。

流程：

```text
客户端点击开始匹配
  ↓
生成 traceId
  ↓
POST /api/match/start
  ↓
客户端日志记录 traceId
  ↓
服务端日志记录 traceId
```

---

## 7.2 WebSocket TraceId

WebSocket 消息也可以携带 traceId：

```json
{
  "type": "MOVE",
  "seq": 1001,
  "traceId": "trace_xxx",
  "roomId": "r_90001",
  "data": {}
}
```

建议：

| 消息            | traceId 策略     |
| ------------- | -------------- |
| ENTER_ROOM    | 必须携带           |
| READY         | 建议携带           |
| MOVE          | 可以携带，但不用于每条排查  |
| SPLIT / EJECT | 建议携带           |
| RECONNECT     | 必须携带           |
| ERROR         | 服务端返回原 traceId |

---

## 7.3 日志链路定位

通过 traceId 可以串联：

```text
客户端按钮点击
  ↓
HTTP 请求
  ↓
服务端接口日志
  ↓
匹配成功
  ↓
客户端进入 GameScene
  ↓
WebSocket 入房
```

通过 roomId 可以串联：

```text
入房
  ↓
对战
  ↓
快照
  ↓
排行榜
  ↓
结算
```

# 9. 性能日志设计

## 9.1 需要采集的性能指标

| 指标                  | 说明            |
| ------------------- | ------------- |
| fps                 | 当前帧率          |
| frameCostMs         | 单帧耗时          |
| snapshotSizeBytes   | 快照包体大小        |
| jsonParseCostMs     | JSON 解析耗时     |
| snapshotApplyCostMs | 快照应用耗时        |
| visiblePlayerCount  | 当前渲染玩家数       |
| visibleFoodCount    | 当前渲染食物数       |
| ballViewCount       | 球体节点数         |
| foodViewCount       | 食物节点数         |
| labelCount          | 文本节点数，粗略统计    |
| wsLatencyMs         | WebSocket RTT |
| reconnectCount      | 当前重连次数        |
| memoryEstimate      | 浏览器支持时采集，后续支持 |

---

## 9.2 慢操作阈值

| 项目            |            建议阈值 |
| ------------- | --------------: |
| JSON 解析耗时     |           > 3ms |
| 快照应用耗时        |           > 5ms |
| 单帧耗时          |          > 33ms |
| FPS 过低        |            < 25 |
| 快照包体大小        | > 50KB，MVP 可先观察 |
| 可见食物数量        |           > 500 |
| 可见玩家数量        |            > 50 |
| WebSocket RTT |         > 200ms |
| 资源加载耗时        |        > 3000ms |

# 10. 高频日志采样策略

## 10.1 必须采样的日志

以下日志不能全量输出：

| event               | 原因       |
| ------------------- | -------- |
| move_send           | 每秒约 20 次 |
| snapshot_received   | 每秒约 10 次 |
| ws_send             | 可能高频     |
| ws_message_received | 可能高频     |
| heartbeat_ping      | 固定周期     |
| heartbeat_pong      | 固定周期     |
| object_pool_recycle | 实体频繁变化   |
| food_view_update    | 高频更新     |
| render_update       | 每帧触发     |

---

## 10.2 推荐采样率

| 日志            | local |  dev | prod |
| ------------- | ----: | ---: | ---: |
| MOVE          |   10% |   1% |   0% |
| ROOM_SNAPSHOT |   10% |   1% |   0% |
| PING / PONG   |  100% |  10% |   0% |
| ObjectPool    |   10% |   1% |   0% |
| RenderUpdate  |    0% |   0% |   0% |
| 慢操作           |  100% | 100% | 100% |
| ERROR         |  100% | 100% | 100% |
| WARN          |  100% | 100% | 100% |

---

## 10.3 采样原则

```text
正常高频日志采样
异常日志不采样
慢操作日志不采样
关键业务状态变化不采样
```

# 11. 日志脱敏设计

客户端不能输出敏感信息。

## 11.1 禁止输出

```text
完整 accessToken
完整 enterToken
完整 reconnectToken
手机号
邮箱
身份证
支付信息
精确设备唯一标识
```

---

## 11.2 Token 输出策略

不输出原文，输出 hash 或尾部脱敏。

示例：

```json
{
  "accessTokenHash": "token_hash_xxx"
}
```

或者：

```json
{
  "reconnectTokenMasked": "****abcd"
}
```

---

## 11.3 URL 脱敏

HTTP 日志中避免输出完整 query 中的敏感参数。

推荐：

```text
/api/match/status
```

而不是：

```text
/api/match/status?token=xxx&secret=xxx
```

# 14. 客户端日志上报设计，P1

## 14.1 上报接口

后续可以增加：

```http
POST /api/client-logs
```

请求：

```json
{
  "userId": "10001",
  "clientVersion": "1.0.0",
  "platform": "h5",
  "logs": []
}
```

---

## 14.2 上报时机

| 时机         | 说明                 |
| ---------- | ------------------ |
| ERROR 立即上报 | 严重错误               |
| WARN 批量上报  | 网络异常、慢操作           |
| 对局结束上报     | 汇总本局性能日志           |
| 页面关闭前尽力上报  | 不保证成功              |
| 定时上报       | 每 10 ~ 30 秒一次，后续支持 |

---

## 14.3 上报策略

```text
本地缓存
  ↓
达到数量阈值
  ↓
批量上报
  ↓
成功后清理
  ↓
失败保留部分
```

推荐：

| 配置                   |    建议 |
| -------------------- | ----: |
| maxBufferSize        | 100 条 |
| reportBatchSize      |  20 条 |
| reportIntervalMs     | 10000 |
| maxPayloadSize       |  64KB |
| errorImmediateReport |  true |

---

## 14.4 上报限制

避免日志上报影响游戏：

1. 不在每帧上报。
2. 不同步阻塞主流程。
3. 不上传大对象。
4. 不上传完整快照。
5. 不上传 Token。
6. 网络差时降低上报频率。
7. 对战关键阶段减少非必要上报。

# 21. 总结

客户端日志系统的核心目标是：

```text
让客户端问题可以被定位，
但不能让日志本身影响客户端性能。
```

MVP 阶段优先做好：

1. 统一 Logger。
2. 统一日志结构。
3. 日志级别控制。
4. 高频日志采样。
5. 启动、登录、匹配、入房、对战、结算关键日志。
6. HTTP / WebSocket 网络日志。
7. 快照异常和慢快照日志。
8. FPS、快照大小、实体数量等基础性能日志。
9. Token 脱敏。
10. 生产环境关闭高频 debug 日志。

推荐实施路线：

```text
先本地控制台日志
  ↓
再接开发环境性能面板
  ↓
再做本地缓存
  ↓
最后做客户端日志批量上报
```

当前阶段不要一开始就做复杂日志平台，先把客户端关键链路日志打准、打少、打有用。
