下面给出一份 **客户端实施过程中的性能优化建议**，重点围绕 **Cocos Creator 3.x + TypeScript + H5 横屏实时对战** 来写。核心原则是：**不要等项目做完再优化，而是在每个阶段都设置性能约束和验收指标。**

# 《吞噬细胞》客户端实施过程中的性能优化建议

## 1. 总体原则

客户端性能优化不要只放在最后做。这个项目是 H5 实时多人游戏，性能风险会随着功能增加快速放大，尤其是：

```text
实体数量增加
快照包体增加
节点数量增加
文本数量增加
对象频繁创建销毁
移动端浏览器性能不稳定
```

所以建议从第一版代码开始就遵守几条原则：

```text
不渲染全地图对象
不频繁创建销毁节点
不每帧刷新所有 UI
不在快照处理里做重逻辑
不让 View 层处理业务规则
不让 JSON 快照无限膨胀
```

---

# 2. 阶段一：项目骨架阶段的优化建议

这个阶段主要做目录、场景、基础类、UI 框架。虽然还没进入对战，但这里已经要打好性能基础。

## 2.1 场景拆分要清晰

不要把所有页面都堆到一个 Cocos Scene 里。

推荐：

```text
BootScene
LoginScene
LobbyScene
MatchScene
GameScene
SettlementScene
```

原因：

| 设计点                | 原因           | 影响                         |
| ------------------ | ------------ | -------------------------- |
| 场景拆分               | 不同阶段资源和逻辑不同  | 避免大厅资源和对战资源长期共存            |
| GameScene 独立       | 对战场景最重       | 方便进入对战前预加载，退出后释放           |
| SettlementScene 独立 | 结算页不需要保留对战对象 | 对局结束后可清理 BattleState 和实体节点 |

---

## 2.2 不要过早加载所有资源

启动时不要一次性加载所有图片、音效、预制体。

推荐：

```text
BootScene：加载基础资源
LobbyScene：加载大厅资源
进入 GameScene 前：加载对战资源
SettlementScene：加载结算资源
```

不推荐：

```text
启动时加载所有大厅、对战、结算、任务、排行榜、商城资源
```

影响：

1. 首屏加载变慢。
2. H5 内存占用变高。
3. 移动端容易白屏或卡顿。
4. 后续资源变多后包体压力更明显。

---

## 2.3 UIManager 不要重复创建通用面板

例如：

```text
LoadingPanel
ToastPanel
ConfirmDialog
ReconnectPanel
```

这些面板建议复用，不要每次打开都重新加载和销毁。

推荐：

```text
第一次打开时创建
后续 show / hide
退出场景时按需释放
```

这样可以减少：

```text
Prefab instantiate
节点销毁
GC
UI 闪烁
```

---

# 3. 阶段二：页面闭环阶段的优化建议

这个阶段会做登录、大厅、匹配、结算等页面。

## 3.1 大厅页不要过度复杂

大厅页可以做得好看，但 MVP 不要一开始就做很多动态元素。

暂时控制：

| 元素       | 建议       |
| -------- | -------- |
| 背景       | 静态图或轻量动画 |
| 角色展示     | 一个主球体即可  |
| 粒子特效     | 初版不做     |
| 复杂入口动画   | 初版少做     |
| 活动入口     | 可先占位     |
| 皮肤、商城、好友 | 暂不实现     |

原因：

```text
大厅不是性能最重的地方，但它是玩家长期停留页面。
如果大厅页资源过重，会影响首屏体验。
```

---

## 3.2 横屏适配要尽早做

不要等页面做完再适配横屏。

建议统一设计基准：

```text
1920 x 1080
```

并约束 UI：

| 区域   | 锚点   |
| ---- | ---- |
| 用户信息 | 左上   |
| 资产栏  | 顶部   |
| 入口按钮 | 左右两侧 |
| 开始游戏 | 中下   |
| 底部导航 | 底部拉伸 |
| 摇杆   | 左下   |
| 技能按钮 | 右下   |

如果早期不做适配，后期会出现：

1. 按钮超出屏幕。
2. 刘海屏遮挡。
3. 不同手机比例下 UI 错位。
4. GameScene 操作区不好用。

---

# 4. 阶段三：网络接入阶段的优化建议

这个阶段会接 HTTP、WebSocket、协议、快照。

## 4.1 HTTP 和 WebSocket 要分清

普通业务走 HTTP：

```text
登录
匹配
战绩
排行榜
任务
结算查询
```

实时对战走 WebSocket：

```text
入房
Ready
MOVE
ROOM_SNAPSHOT
RANK_UPDATE
GAME_END
SETTLEMENT_RESULT
```

不要把所有东西都塞进 WebSocket，也不要用 HTTP 轮询模拟实时对战。

影响：

| 错误做法             | 影响          |
| ---------------- | ----------- |
| HTTP 高频轮询位置      | 延迟高，服务端压力大  |
| WebSocket 承载所有业务 | 协议复杂，排查困难   |
| 快照里带大量非对战字段      | 包体膨胀，前端解析变慢 |

---

## 4.2 JSON 快照字段必须克制

MVP 用 JSON 可以，但快照字段要少。

推荐快照里只放：

```json
{
  "ballId": "b1",
  "userId": "10001",
  "x": 1200,
  "y": 800,
  "radius": 36,
  "mass": 200
}
```

不要在每个快照反复带：

```json
{
  "nickname": "xxx",
  "avatar": "xxx",
  "level": 12,
  "skinName": "xxx",
  "title": "xxx",
  "profile": {}
}
```

昵称、皮肤、头像这类低频数据可以在入房时下发一次，客户端缓存。

影响：

| 设计点        | 原因               | 影响   |
| ---------- | ---------------- | ---- |
| 快照字段精简     | 降低 JSON.parse 压力 | 前端更稳 |
| 低频数据单独下发   | 避免重复传输           | 降低带宽 |
| 高频数据只放必要字段 | 减少包体             | 降低延迟 |

---

## 4.3 快照频率不要太高

推荐：

```text
服务端 Tick：20 次 / 秒
快照广播：10 次 / 秒
客户端渲染：30 ~ 60 FPS
MOVE 发送：20 次 / 秒
排行榜刷新：1 次 / 秒
```

不要一开始就：

```text
快照 30 次 / 秒
MOVE 60 次 / 秒
排行榜 10 次 / 秒
```

原因：

1. H5 JSON 解析压力大。
2. WebSocket 包数量增加。
3. 主线程更容易被打满。
4. 移动端功耗更高。

---

# 5. 阶段四：对战场景开发阶段的优化建议

这是客户端性能风险最大的阶段。

## 5.1 不要渲染全地图对象

即使服务端地图中有几千个食物，客户端也不能全部创建节点。

推荐：

```text
只渲染视野范围内对象
```

MVP 如果服务端还没做 AOI，客户端也要做基础裁剪：

```text
根据相机可视范围 + margin
判断对象是否需要显示
```

例如：

```text
visibleRect = cameraWorldRect + 额外边距
对象在 visibleRect 内 → 显示
对象在 visibleRect 外 → 隐藏或不创建
```

影响：

| 设计点         | 原因        | 影响     |
| ----------- | --------- | ------ |
| 只渲染可见对象     | 浏览器渲染能力有限 | 降低节点数量 |
| 视野外对象隐藏     | 避免无效绘制    | 提升 FPS |
| 后续配合服务端 AOI | 网络和渲染一起减压 | 支撑百人房间 |

---

## 5.2 食物必须轻量

FoodView 不要复杂。

推荐结构：

```text
FoodNode
└── Sprite
```

不推荐：

```text
FoodNode
├── Sprite
├── Label
├── Animation
├── Particle
├── 多个子节点
└── 复杂脚本
```

食物数量多，是最容易拖垮前端的对象。

MVP 建议：

| 项目   | 策略           |
| ---- | ------------ |
| 食物外观 | 单个圆点 Sprite  |
| 食物颜色 | 预设颜色         |
| 食物文本 | 不显示          |
| 食物动画 | 初版不做或极简      |
| 食物脚本 | 只负责显示和 reset |

---

## 5.3 玩家球体也要控制文本

玩家球体可以显示昵称，但要控制数量和刷新频率。

建议：

| 内容     | 策略         |
| ------ | ---------- |
| 自己昵称   | 显示         |
| 其他玩家昵称 | 显示，但只显示视野内 |
| 自己质量   | 显示         |
| 其他玩家质量 | 可不显示       |
| 称号     | 不做         |
| 头像     | 不做         |
| 复杂装饰   | 后续再做       |

文本渲染比普通 Sprite 更重。
尤其是多人同屏时，几十个 Label 会明显增加压力。

---

## 5.4 对象池必须从第一版实现

对战场景中这些对象必须池化：

```text
PlayerBallView
FoodView
EjectedMassView
EffectView
```

正确流程：

```text
需要对象
  ↓
从对象池取
  ↓
没有再 instantiate
  ↓
使用完成后 reset
  ↓
回收到对象池
```

不要：

```text
每次创建都 instantiate
每次消失都 destroy
```

影响：

| 设计点        | 原因       | 影响     |
| ---------- | -------- | ------ |
| 对象池        | 降低创建销毁成本 | 减少卡顿   |
| reset 清理状态 | 防止脏数据复用  | 降低 bug |
| 分类型池化      | 不同实体结构不同 | 管理清晰   |

---

## 5.5 回收对象时必须 reset

对象池复用时一定要清理旧状态。

需要清理：

```text
位置
缩放
颜色
透明度
昵称
质量文本
动画状态
事件监听
targetPosition
displayPosition
isSelf 标记
```

否则会出现：

1. 食物颜色错乱。
2. 玩家昵称残留。
3. 自己高亮出现在别人身上。
4. 已删除对象重新出现时位置异常。
5. 旧事件监听重复触发。

---

# 6. 阶段五：状态同步与插值阶段的优化建议

## 6.1 快照处理不要做重逻辑

收到 `ROOM_SNAPSHOT` 时，只做：

```text
校验
更新 BattleState
计算 added / updated / removed
更新实体 target 值
```

不要在快照处理函数里做：

```text
复杂动画
大量 UI 刷新
复杂排序
大规模节点创建销毁
复杂路径计算
```

原因：

```text
快照每秒 10 次，如果每次处理太重，主线程会周期性卡顿。
```

---

## 6.2 display 和 target 分离

每个实体建议维护：

```text
targetX
targetY
targetRadius

displayX
displayY
displayRadius
```

快照只更新 target：

```text
targetX = snapshot.x
targetY = snapshot.y
```

每帧渲染时更新 display：

```text
displayX = lerp(displayX, targetX, factor)
displayY = lerp(displayY, targetY, factor)
```

这样可以减少快照跳变导致的画面抖动。

---

## 6.3 大距离变化直接校正

如果距离差太大，不要慢慢插值。

例如：

```text
distance > 500
```

直接设置：

```text
displayPosition = targetPosition
```

原因：

1. 可能是重连恢复。
2. 可能是服务端校正。
3. 可能是玩家被吞噬或重生。
4. 如果还慢慢追，会产生严重位置延迟。

---

## 6.4 排行榜不要跟随快照刷新

排行榜用 `RANK_UPDATE`，建议：

```text
1 次 / 秒
```

不要每个 `ROOM_SNAPSHOT` 都重新排序和刷新排行榜。

影响：

| 错误做法        | 问题      |
| ----------- | ------- |
| 每帧刷新排行榜 UI  | UI 重排频繁 |
| 每个快照更新排行榜   | 文本刷新过多  |
| 客户端自己排序全员排名 | 无意义且耗性能 |

排行榜应由服务端算好后下发。

---

# 7. 阶段六：输入系统开发阶段的优化建议

## 7.1 MOVE 不要每帧发送

客户端渲染可以 60 FPS，但 MOVE 不需要 60 次 / 秒。

推荐：

```text
MOVE 每 50ms 发送一次
每秒 20 次
```

不要：

```text
每帧发送 MOVE
```

影响：

1. WebSocket 消息数量增加。
2. 服务端输入处理压力增加。
3. 网络抖动更明显。
4. 移动端耗电更高。

---

## 7.2 摇杆移动只更新必要 UI

摇杆拖动时只更新：

```text
摇杆 handle 位置
currentDirection
```

不要每次拖动都触发：

```text
复杂事件广播
大量日志
UI 全量刷新
网络立即发送
```

MOVE 发送交给 `MoveInputSender` 定时器统一处理。

---

## 7.3 高频输入日志默认关闭

MOVE 是高频消息，不要默认打印。

不推荐：

```ts
console.log("move:" + x + "," + y);
```

推荐调试时采样：

```ts
logger.debug("move send", {
  x,
  y,
  seq,
});
```

生产环境关闭 MOVE debug 日志。

这点很重要，不然浏览器控制台输出也会拖慢游戏。

---

# 8. 阶段七：断线重连阶段的优化建议

## 8.1 重连时不要保留旧实体继续硬跑

断线重连成功后，收到 `ROOM_RECOVER_SNAPSHOT`，应全量重建。

流程：

```text
停止输入
清空 BattleState
清空 SnapshotBuffer
EntityManager.clearAll()
应用恢复快照
重建实体
恢复输入
```

不要用旧状态继续拼接。

原因：

1. 断线期间服务端状态已经变化。
2. 玩家可能已死亡。
3. 食物和玩家位置可能变化很大。
4. 旧状态继续插值会造成画面错误。

---

## 8.2 切后台时要停止输入

H5 页面切后台时，浏览器定时器可能降频。

监听：

```text
visibilitychange
blur
pagehide
```

处理：

```text
停止 MOVE
摇杆归零
输入禁用
恢复前检查 WebSocket
```

否则玩家切后台后，可能出现：

1. 服务端仍收到旧方向。
2. 玩家持续移动。
3. 回来后画面大幅跳变。
4. WebSocket 已断但 UI 还以为正常。

---

# 9. 阶段八：资源与包体优化建议

## 9.1 图片资源控制尺寸

不要直接把超大图塞进 H5 包。

建议：

| 资源    | 建议         |
| ----- | ---------- |
| 大厅背景  | 控制尺寸，压缩    |
| 对战地图  | 可平铺或使用简单纹理 |
| UI 图标 | 合理打包       |
| 球体资源  | 小图或程序化颜色   |
| 食物资源  | 轻量圆点图      |

影响：

1. 首屏加载速度。
2. H5 包体大小。
3. 移动端内存。
4. 低端机加载稳定性。

---

## 9.2 resources 目录不要乱放

Cocos 的 `resources` 目录会影响动态加载和包体管理。
不要把所有资源都放进去。

只放需要运行时动态加载的资源，例如：

```text
动态 UI 预制体
实体预制体
配置文件
后续皮肤资源
```

不需要动态加载的资源，直接随场景引用即可。

---

## 9.3 音效初版可以少做

音效也会占资源和内存。

MVP 可以只做：

```text
按钮点击音效
结算音效
吞噬音效
```

不要一开始就加大量背景音乐、复杂音效包。

---

# 10. 阶段九：Cocos 节点优化建议

## 10.1 控制节点数量

节点越多，更新和渲染越重。

重点控制：

```text
FoodNode 数量
PlayerBallNode 数量
Label 数量
EffectNode 数量
UI 节点层级
```

MVP 建议：

| 对象   | 控制策略     |
| ---- | -------- |
| 食物   | 只渲染视野内   |
| 玩家   | 只渲染视野内   |
| 昵称   | 只对可见玩家显示 |
| 质量文本 | 只显示自己或大球 |
| 特效   | 少量、短生命周期 |
| UI   | 不频繁重建    |

---

## 10.2 UI 层级不要过深

不推荐：

```text
Panel
└── Node
    └── Node
        └── Node
            └── Button
                └── Label
```

层级过深会增加查找、布局和渲染压力。

建议：

```text
结构清晰
层级适中
重要节点提前绑定引用
不要运行时频繁 find
```

---

## 10.3 不要每帧查找节点

不要在 update 里写：

```ts
this.node.getChildByName("xxx");
```

也不要频繁：

```ts
find("Canvas/UIRoot/GameHUD/xxx");
```

推荐：

```text
onLoad / init 时绑定引用
后续直接使用缓存引用
```

---

# 11. 阶段十：代码层面的优化建议

## 11.1 避免高频创建临时对象

在 update、快照处理、插值处理中不要频繁创建临时对象。

不推荐：

```ts
const pos = { x: data.x, y: data.y };
```

如果每帧、每实体都创建，会增加 GC 压力。

建议：

1. 复用 Vec2。
2. 复用临时对象。
3. 对高频路径减少对象分配。
4. 避免频繁数组 map / filter / reduce 生成新数组。

---

## 11.2 高频循环里不要做复杂操作

例如：

```text
for each food
  创建新对象
  格式化字符串
  刷新文本
  查找节点
  打日志
```

这些都要避免。

高频循环只做必要计算：

```text
位置插值
大小更新
可见性判断
```

---

## 11.3 日志要分级

生产环境默认：

```text
INFO / WARN / ERROR
```

关闭：

```text
MOVE debug
snapshot debug
food update debug
每帧渲染 debug
```

否则浏览器控制台会成为性能杀手。

---

# 12. 性能监控建议

## 12.1 客户端需要内置性能面板，开发环境启用

建议开发期显示：

| 指标                  | 说明         |
| ------------------- | ---------- |
| FPS                 | 当前帧率       |
| WebSocket RTT       | 网络延迟       |
| snapshotSeq         | 最新快照序号     |
| tickSeq             | 最新服务端 Tick |
| visiblePlayers      | 当前渲染玩家数    |
| visibleFoods        | 当前渲染食物数    |
| totalNodes          | 当前节点数，粗略   |
| snapshotSize        | 快照包体大小     |
| parseCostMs         | JSON 解析耗时  |
| snapshotApplyCostMs | 快照应用耗时     |
| renderCostMs        | 渲染更新耗时     |

开发时非常有用。

---

## 12.2 每阶段都要压测

不要等全部开发完再压测。

建议阶段性压测：

| 阶段             | 压测目标     |
| -------------- | -------- |
| 对战空场景          | FPS 是否稳定 |
| 1000 食物本地渲染    | 食物渲染上限   |
| 30 玩家 + 500 食物 | MVP 基准   |
| 50 玩家 + 800 食物 | P1 目标    |
| 100 玩家 + AOI   | 后续目标     |
| 弱网模拟           | 插值和重连表现  |
| 移动端浏览器         | 真实设备表现   |

---

# 13. 推荐 MVP 性能约束

第一版不要直接追求百人极限。建议先定 MVP 性能约束：

| 指标       |             MVP 建议 |
| -------- | -----------------: |
| 单局人数     |       20 ~ 30 人先验证 |
| 后续目标     |              100 人 |
| 服务端快照    |           10 次 / 秒 |
| MOVE 发送  |           20 次 / 秒 |
| 前端目标 FPS |          30 FPS 起步 |
| 视野内食物    |          200 ~ 500 |
| 视野内玩家    |            20 ~ 50 |
| 排行榜刷新    |            1 次 / 秒 |
| 食物对象     |              必须对象池 |
| 玩家对象     |              必须对象池 |
| 协议       |            JSON 起步 |
| 后续协议     |           Protobuf |
| 同步策略     | MVP 全量，后续 AOI + 增量 |

---

# 14. 优化优先级建议

如果出现卡顿，按这个顺序查：

## 14.1 第一优先级：节点数量

先看：

```text
FoodNode 数量
PlayerBallNode 数量
Label 数量
EffectNode 数量
```

节点过多是最常见原因。

---

## 14.2 第二优先级：对象创建销毁

看是否存在：

```text
频繁 instantiate
频繁 destroy
每个快照大量新建对象
每帧创建临时对象
```

优先用对象池解决。

---

## 14.3 第三优先级：快照包体和 JSON 解析

看：

```text
snapshotSize
JSON.parse 耗时
每秒快照数量
快照字段是否冗余
```

如果包体大，先减少字段，再考虑 Protobuf。

---

## 14.4 第四优先级：UI 文本刷新

看：

```text
排行榜是否频繁刷新
昵称是否频繁 set string
质量文本是否每帧刷新
Toast 是否重复创建
```

文本刷新是隐藏性能点。

---

## 14.5 第五优先级：插值和 update 逻辑

看：

```text
RenderSystem.update 耗时
InterpolationSystem 是否遍历过多对象
VisibleCulling 是否每帧全量计算太重
```

---

# 15. 实施过程中的性能红线

开发时可以明确几条红线：

```text
禁止在 update 中频繁 find 节点
禁止在 update 中大量 new 对象
禁止食物频繁 instantiate / destroy
禁止快照里重复发送低频用户信息
禁止每帧刷新排行榜
禁止 MOVE 每帧发送
禁止默认打印高频 debug 日志
禁止客户端渲染全地图食物
禁止 View 层直接处理 WebSocket 原始消息
```

这些红线要早期写进团队开发规范里。

---

# 16. 推荐落地顺序

客户端性能优化建议按这个顺序落地：

```text
第一步：对象池
第二步：视野裁剪
第三步：快照字段精简
第四步：MOVE / 快照 / 排行榜限频
第五步：display / target 插值
第六步：文本刷新控制
第七步：性能面板
第八步：真实移动端测试
第九步：服务端 AOI
第十步：Protobuf
```

注意：**AOI 和 Protobuf 很重要，但不一定是第一天就做。**
第一天最该做的是：对象池、限频、节点控制、快照字段克制。

---

# 17. 总结

客户端性能优化要贯穿整个实施过程，而不是最后补救。

对《吞噬细胞》来说，最重要的优化方向是：

```text
只渲染视野内对象
食物和球体全部对象池化
控制快照频率和包体大小
MOVE 输入限频
排行榜和 HUD 限频刷新
减少 Label 数量
避免高频创建临时对象
GameScene 退出时彻底清理状态和节点
开发期内置性能面板
移动端真机持续测试
```

总结：

```text
H5 客户端性能优化的核心不是“最后调一下帧率”，
而是从第一版实现开始，就控制节点数量、对象生命周期、快照包体和高频逻辑。
```
