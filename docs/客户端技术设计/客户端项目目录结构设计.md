# 2. 设计目标

客户端项目目录结构需要解决以下问题：

```text
场景文件放在哪里？
脚本文件怎么分层？
网络代码放在哪里？
协议类型放在哪里？
对战逻辑放在哪里？
UI 面板放在哪里？
实体预制体放在哪里？
资源和配置如何管理？
后续模块增加时如何避免目录混乱？
```

MVP 阶段目标：

1. 目录结构清晰。
2. 页面、网络、协议、对战、UI 分层明确。
3. 每个模块职责单一。
4. 便于后续扩展排行榜、战绩、任务、商城等模块。
5. 便于多人协作开发。
6. 便于后续接入小游戏平台和移动端发布。
7. 避免所有脚本都堆在一个目录里。

# 4. assets 目录总览

`assets` 是 Cocos Creator 最核心的资源目录。

建议结构：

```text
assets/
├── scenes/
├── scripts/
├── prefabs/
├── textures/
├── audio/
├── fonts/
├── animations/
├── effects/
├── configs/
└── resources/
```

| 目录       | 职责                          |
| ---------- | ----------------------------- |
| scenes     | Cocos 场景文件                |
| scripts    | TypeScript 脚本               |
| prefabs    | UI、实体、特效预制体          |
| textures   | 图片资源                      |
| audio      | 音效和背景音乐                |
| fonts      | 字体资源                      |
| animations | 动画资源                      |
| effects    | 粒子、材质、Shader 等表现资源 |
| configs    | 客户端配置文件                |
| resources  | Cocos 动态加载资源            |

## 5.2 场景职责

------

## 5.3 场景命名规范

统一使用：

```text
模块名 + Scene
```

例如：

```text
BootScene
LoginScene
LobbyScene
GameScene
SettlementScene
```

不要使用：

```text
scene1
main
test
newscene
```

## 8.2 common 职责

`common` 目录只放通用能力，不放具体业务。

可以放：

1. 事件总线。
2. 日志工具。
3. 本地存储。
4. 数学工具。
5. 时间工具。
6. 对象池基础类。
7. 错误码。
8. 通用常量。

不应该放：

1. 登录业务。
2. 匹配业务。
3. 对战业务。
4. UI 页面逻辑。
5. WebSocket 具体消息处理。

## 14.3 EntityView 设计原则

EntityView 只做表现。

可以做：

1. 设置位置。
2. 设置半径。
3. 设置颜色。
4. 设置昵称。
5. 播放简单动画。
6. 回收前 reset。

不应该做：

1. 解析 WebSocket 消息。
2. 判断碰撞。
3. 修改 BattleState。
4. 发送网络请求。
5. 控制场景跳转。

## 16.3 场景跳转原则

业务模块不要直接调用 Cocos 原生场景切换。

推荐：

```text
业务模块
  ↓
SceneRouter
  ↓
Cocos director.loadScene
```

好处：

1. 场景跳转统一管理。
2. 可以统一加 Loading。
3. 可以记录当前场景。
4. 可以控制参数传递。
5. 可以防止重复跳转。

# 21. resources 动态资源目录设计

Cocos 中 `resources` 目录可用于运行时动态加载。

## 21.1 推荐结构

```text
assets/resources/
├── prefabs/
├── textures/
├── configs/
└── audio/
```

------

## 21.2 使用原则

不要把所有资源都丢进 `resources`。

只放需要运行时动态加载的资源，例如：

1. 动态 UI 预制体。
2. 动态实体预制体。
3. 运行时配置。
4. 后续可选皮肤资源。

原因：

```text
resources 下资源会被打包进构建结果
资源过多会影响包体和加载性能
```

```text

SceneRouter.ts
```

不推荐：

```text
battle_manager.ts
player-ball-view.ts
httpclient.ts
```

类名和文件名保持一致：


## 25.3 方法命名


## 25.4 常量命名

# 26. 模块依赖规范

## 26.1 推荐依赖方向

```text
scene
  ↓
modules
  ↓
network / protocol
  ↓
common

battle
  ↓
network / protocol / entity / common

ui
  ↓
modules / battle / common
```

------

## 26.2 禁止依赖

避免以下依赖：

```text
common 依赖 modules
protocol 依赖 ui
network 依赖具体 UI 面板
entity 直接调用 HTTP 接口
View 直接切换 Scene
```

------

## 26.3 正确做法

如果 UI 需要发起匹配：

```text
LobbyPanel
  ↓
LobbyManager / MatchManager
  ↓
ApiService
  ↓
HttpClient
```

不要：

```text
LobbyPanel 直接 new HttpClient
```

如果玩家球体需要更新：

```text
ROOM_SNAPSHOT
  ↓
SnapshotReceiver
  ↓
BattleState
  ↓
EntityManager
  ↓
PlayerBallView
```

不要：

```text
PlayerBallView 直接解析 WebSocket 消息
```

# 31. 总结

客户端项目目录结构可以按以下主线组织：

```text
scenes：场景文件
scripts/app：应用入口和全局上下文
scripts/common：通用工具
scripts/network：HTTP 和 WebSocket
scripts/protocol：协议定义和编解码
scripts/modules：登录、大厅、匹配、结算等业务模块
scripts/battle：对战核心逻辑
scripts/entity：实体表现 View
scripts/ui：UI 面板
scripts/scene：场景控制器
prefabs：UI 和实体预制体
textures：图片资源
configs：配置文件
```

MVP 阶段先不要建立太多未来模块。
优先保证这条链路的目录和代码清晰：

```text
启动
  ↓
登录
  ↓
大厅
  ↓
匹配
  ↓
WebSocket 入房
  ↓
对战渲染
  ↓
结算
```

只要目录结构能支撑这条主链路，后续再扩展排行榜、战绩、任务、皮肤、商城时，就不会把项目堆成一团。
