# 2. 设计目标

客户端网络层负责封装所有与服务端的通信能力。

它要解决两个问题：

```text
普通业务请求怎么发？
实时对战消息怎么收发？
```

普通业务请求使用 HTTP，例如：

```text
登录
查询用户资料
开始匹配
取消匹配
查询战绩
查询排行榜
查询任务
查询结算
```

实时对战通信使用 WebSocket，例如：

```text
入房
Ready
移动输入
分裂
吐球
房间快照
局内排行榜
游戏结束
结算结果
心跳
重连
```

# 4. HTTP 与 WebSocket 职责划分

## 4.1 HTTP 适用场景

HTTP 用于请求-响应型业务。

| 业务         | 接口                               |
| ------------ | ---------------------------------- |
| 游客登录     | `POST /api/auth/guest-login`       |
| 查询我的资料 | `GET /api/users/me`                |
| 查询我的资产 | `GET /api/assets/me`               |
| 开始匹配     | `POST /api/match/start`            |
| 取消匹配     | `POST /api/match/cancel`           |
| 查询匹配状态 | `GET /api/match/status`            |
| 查询结算结果 | `GET /api/settlements/{roomId}/me` |
| 查询战绩     | `GET /api/records`                 |
| 查询排行榜   | `GET /api/ranks`                   |
| 查询任务     | `GET /api/tasks`                   |

------

## 4.2 WebSocket 适用场景

WebSocket 用于实时对战。

| 业务       | 消息                              |
| ---------- | --------------------------------- |
| 入房认证   | ENTER_ROOM                        |
| 客户端准备 | READY                             |
| 游戏开始   | GAME_START                        |
| 移动输入   | MOVE                              |
| 分裂       | SPLIT                             |
| 吐球       | EJECT                             |
| 房间快照   | ROOM_SNAPSHOT                     |
| 局内排行榜 | RANK_UPDATE                       |
| 游戏结束   | GAME_END                          |
| 结算结果   | SETTLEMENT_RESULT                 |
| 心跳       | PING / PONG                       |
| 重连       | RECONNECT / ROOM_RECOVER_SNAPSHOT |

------

## 4.3 使用原则

```text
能用 HTTP 的普通业务，不放 WebSocket。
需要实时推送的对战消息，使用 WebSocket。
```

原因：

1. HTTP 更适合普通接口。
2. WebSocket 更适合高频实时消息。
3. 职责分离后更容易排查问题。
4. 登录、匹配、战绩、排行榜不需要保持实时连接。
5. 对战输入和快照不能依赖 HTTP 轮询。

# 5. 网络层核心模块

## 5.1 HttpClient

### 职责

`HttpClient` 是 HTTP 请求的底层封装。

负责：

1. 统一 baseUrl。
2. 统一请求头。
3. 自动携带 accessToken。
4. 统一处理 JSON。
5. 统一处理超时。
6. 统一处理错误码。
7. 统一处理登录失效。
8. 输出请求日志。

------

### 核心能力

| 能力       | 说明                       |
| ---------- | -------------------------- |
| get        | 发送 GET 请求              |
| post       | 发送 POST 请求             |
| put        | 发送 PUT 请求，后续支持    |
| delete     | 发送 DELETE 请求，后续支持 |
| request    | 通用请求方法               |
| setToken   | 设置 accessToken           |
| clearToken | 清除 accessToken           |
| setBaseUrl | 设置服务端地址             |

------

## 5.2 ApiService

### 职责

`ApiService` 是业务接口封装层。

它不直接关心请求细节，只暴露业务方法。

示例：

```text
AuthApi.guestLogin()
UserApi.getMe()
MatchApi.startMatch()
MatchApi.cancelMatch()
SettlementApi.getMySettlement()
RecordApi.getRecords()
RankApi.getRanks()
TaskApi.getTasks()
```

------

### 设计原则

```text
业务模块不直接调用 HttpClient。
业务模块调用 ApiService。
```

好处：

1. 接口集中管理。
2. 路径变更时影响范围小。
3. 请求参数和响应结构更清晰。
4. 方便 Mock 数据。
5. 方便后续生成 API SDK。

------

## 5.3 WsClient

### 职责

`WsClient` 是 WebSocket 底层封装。

负责：

1. 建立 WebSocket 连接。
2. 关闭连接。
3. 发送消息。
4. 接收消息。
5. 连接状态维护。
6. 错误处理。
7. 心跳配合。
8. 重连配合。

------

### 连接状态

| 状态          | 说明     |
| ------------- | -------- |
| IDLE          | 未连接   |
| CONNECTING    | 正在连接 |
| CONNECTED     | 已连接   |
| AUTHENTICATED | 已认证   |
| CLOSED        | 已关闭   |
| ERROR         | 连接异常 |
| RECONNECTING  | 正在重连 |

------

## 5.4 WsMessageDispatcher

### 职责

`WsMessageDispatcher` 负责把收到的 WebSocket 消息分发给对应业务模块。

```text
WsClient 收到消息
  ↓
MessageCodec 解码
  ↓
WsMessageDispatcher 根据 type 分发
  ↓
BattleManager / RankPanel / SettlementManager 处理
```

------

### 消息分发原则

1. `WsClient` 只负责收发，不处理业务。
2. `Dispatcher` 只负责分发，不做复杂业务。
3. 具体业务逻辑由对应模块处理。
4. 同一个消息类型可以注册多个监听器。
5. 场景销毁时必须取消监听，避免重复回调。

------

## 5.5 MessageCodec

### 职责

`MessageCodec` 负责消息编码和解码。

MVP 使用 JSON：

```text
对象
  ↓
JSON.stringify
  ↓
WebSocket send
```

接收：

```text
WebSocket message
  ↓
JSON.parse
  ↓
协议对象
```

后续升级 Protobuf 时，只需要替换 `MessageCodec`，业务层尽量不改。

------

## 5.6 HeartbeatClient

### 职责

`HeartbeatClient` 负责心跳。

负责：

1. 定时发送 PING。
2. 接收 PONG。
3. 计算网络延迟。
4. 判断心跳超时。
5. 通知 WsClient 连接异常。

------

### MVP 心跳策略

| 配置                | 建议值 |
| ------------------- | ------ |
| heartbeatIntervalMs | 5000   |
| heartbeatTimeoutMs  | 15000  |
| maxMissedHeartbeat  | 3      |

流程：

```text
每 5 秒发送一次 PING
  ↓
服务端返回 PONG
  ↓
记录 rtt
  ↓
连续 3 次未收到 PONG
  ↓
判定连接异常
```

------

## 5.7 ReconnectClient

### 职责

`ReconnectClient` 负责断线重连。

MVP 可以先做简化版本，P1 完善。

负责：

1. 监听 WebSocket 断开。
2. 展示重连状态。
3. 按退避策略重连。
4. 发送 RECONNECT。
5. 等待恢复快照。
6. 重连失败后返回大厅或查询结算。

------

## 5.8 NetworkState

### 职责

`NetworkState` 保存当前网络状态。

包含：

```text
httpAvailable
wsState
latencyMs
lastPingTime
lastPongTime
reconnectAttempt
isReconnecting
lastErrorCode
lastErrorMessage
```

用途：

1. UI 展示网络状态。
2. GameScene 判断是否允许发送输入。
3. ReconnectPanel 展示重连状态。
4. 日志记录网络异常。

------

## 5.9 NetworkErrorHandler

### 职责

统一处理网络错误。

包括：

1. HTTP 超时。
2. HTTP 业务错误码。
3. Token 失效。
4. WebSocket 断开。
5. WebSocket 消息解析失败。
6. 重连失败。
7. 结算查询失败。

------

# 6. HTTP 请求设计

## 6.1 请求格式

HTTP 请求统一带：

```http
Authorization: Bearer access_token_xxx
Content-Type: application/json
X-Client-Version: 1.0.0
X-Trace-Id: trace_xxx
```

------

## 6.2 响应格式

统一响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

错误响应：

```json
{
  "code": 50001,
  "message": "未登录",
  "data": null
}
```

------

## 6.3 HTTP 请求流程

```text
业务模块调用 ApiService
  ↓
ApiService 调用 HttpClient
  ↓
HttpClient 拼接 baseUrl
  ↓
加入 Authorization
  ↓
加入 X-Trace-Id
  ↓
发送请求
  ↓
解析响应
  ↓
判断 code
  ↓
返回 data 或抛出错误
```

------

## 6.4 HTTP 超时设置

| 场景         | 超时时间 |
| ------------ | -------- |
| 登录         | 5 秒     |
| 普通查询     | 5 秒     |
| 开始匹配     | 5 秒     |
| 查询结算     | 8 秒     |
| 资源配置接口 | 10 秒    |

MVP 推荐默认：

```text
timeoutMs = 5000
```

------

## 6.5 Token 失效处理

当接口返回：

```text
50001 未登录
50002 Token 无效
50003 Token 过期
```

客户端处理：

```text
清理 accessToken
  ↓
关闭 WebSocket
  ↓
清理本地用户状态
  ↓
跳转 LoginScene
```

------

# 7. WebSocket 连接设计

## 7.1 连接建立时机

WebSocket 不在大厅建立。

推荐：

```text
匹配成功
  ↓
获得 wsUrl / roomId / enterToken
  ↓
进入 GameScene
  ↓
建立 WebSocket
```

原因：

1. 大厅不需要实时对战连接。
2. 减少长连接资源占用。
3. 只有进入房间后才需要 WebSocket。
4. 连接生命周期和 GameScene 一致，更容易管理。

------

## 7.2 WebSocket 连接流程

```text
进入 GameScene
  ↓
WsClient.connect(wsUrl)
  ↓
连接成功
  ↓
发送 ENTER_ROOM
  ↓
收到 ENTER_ROOM_RESULT
  ↓
加载资源完成后发送 READY
  ↓
收到 GAME_START
  ↓
开始发送 MOVE
```

------

## 7.3 连接关闭时机

以下情况关闭 WebSocket：

1. 对局结束且进入结算页。
2. 玩家返回大厅。
3. 重连时旧连接被替换。
4. Token 失效。
5. 客户端主动退出对局。
6. 服务端通知房间销毁。

------

# 9. 消息序号设计

## 9.1 客户端 seq

客户端发送的每条 WebSocket 消息都带 `seq`。

用途：

1. 日志排查。
2. 服务端输入去重，后续支持。
3. 判断消息顺序。
4. 计算请求响应关系。

------

## 9.2 服务端 seq

服务端下发消息也带 `seq`。

用途：

1. 客户端判断快照是否连续。
2. 丢弃旧消息。
3. 日志排查。
4. 断线重连时上报最后处理的快照序号。

------

## 9.3 快照序号

快照中建议包含：

```text
seq
tickSeq
serverTime
```

区别：

| 字段       | 说明                  |
| ---------- | --------------------- |
| seq        | WebSocket 消息序号    |
| tickSeq    | Game Server Tick 序号 |
| serverTime | 服务端时间            |

------

# 10. 消息发送频率设计

## 10.1 MOVE 发送频率

客户端渲染可以是 60 FPS，但 MOVE 不需要每帧发送。

推荐：

| 配置          | 建议值     |
| ------------- | ---------- |
| MOVE 发送频率 | 20 次 / 秒 |
| MOVE 间隔     | 50ms       |

也就是：

```text
每 50ms 发送一次当前摇杆方向
```

------

## 10.2 SPLIT / EJECT 发送频率

SPLIT：

```text
点击一次发送一次
```

EJECT：

```text
按住时可连续发送，但需要客户端节流
```

MVP 推荐：

| 操作  | 客户端限制      |
| ----- | --------------- |
| SPLIT | 1 秒内最多 1 次 |
| EJECT | 150ms 发送一次  |

服务端仍必须做最终限频校验。

------

## 10.3 心跳发送频率

```text
每 5 秒发送一次 PING
```

------

# 11. 消息分发设计

## 11.1 注册监听

业务模块注册自己关心的消息类型。

```text
BattleManager 监听：
ENTER_ROOM_RESULT
GAME_START
ROOM_SNAPSHOT
GAME_END

RankPanel 监听：
RANK_UPDATE

SettlementManager 监听：
SETTLEMENT_RESULT

ReconnectClient 监听：
PONG
ROOM_RECOVER_SNAPSHOT
```

------

## 11.2 取消监听

场景销毁时必须取消监听。

例如 GameScene 退出时：

```text
取消 ROOM_SNAPSHOT 监听
取消 RANK_UPDATE 监听
取消 GAME_END 监听
取消 SETTLEMENT_RESULT 监听
```

避免：

1. 重复处理消息。
2. 旧场景收到新消息。
3. 内存泄漏。
4. UI 已销毁仍被访问。

# 12. 心跳设计

## 12.1 PING

```json
{
  "type": "PING",
  "seq": 9001,
  "clientTime": 1710000000000,
  "data": {
    "roomId": "r_90001"
  }
}
```

------

## 12.2 PONG

```json
{
  "type": "PONG",
  "seq": 9001,
  "serverTime": 1710000000050,
  "data": {
    "roomId": "r_90001"
  }
}
```

------

## 12.3 延迟计算

客户端收到 PONG 后：

```text
rtt = now - clientTime
latency = rtt / 2
```

UI 可以展示：

```text
延迟：42ms
```

MVP 可以先不展示，但建议保存到 NetworkState。

# 13. 断线重连设计

## 13.1 MVP 简化策略

MVP 阶段可以先简化：

```text
WebSocket 断开
  ↓
显示连接断开
  ↓
尝试重连 3 次
  ↓
成功则恢复
  ↓
失败则返回大厅或查询结算
```

------

## 13.2 完整重连流程

```text
WebSocket 断开
  ↓
停止发送 MOVE
  ↓
展示 ReconnectPanel
  ↓
读取 roomId / reconnectToken
  ↓
重新连接 wsUrl
  ↓
发送 RECONNECT
  ↓
收到 RECONNECT_RESULT
  ↓
收到 ROOM_RECOVER_SNAPSHOT
  ↓
清空本地状态
```

# 20. 总结

客户端网络层是连接客户端页面和服务端能力的基础模块。

MVP 阶段需要先完成：

```text
HTTP 请求封装
  ↓
游客登录
  ↓
开始匹配
  ↓
WebSocket 入房
  ↓
发送 MOVE
  ↓
接收 ROOM_SNAPSHOT
  ↓
接收 RANK_UPDATE
  ↓
接收 SETTLEMENT_RESULT
```

核心设计原则：

1. HTTP 负责普通业务。
2. WebSocket 负责实时对战。
3. WsClient 只负责连接和收发。
4. Dispatcher 负责消息分发。
5. 业务模块处理具体逻辑。
6. 客户端只发送输入意图，不上传权威状态。
7. 网络异常必须有明确 UI 反馈。
8. MVP 先用 JSON，后续再升级 Protobuf。

当前阶段先把网络层主链路打通，不要过早加入复杂预测、回滚、压缩和跨服恢复。
