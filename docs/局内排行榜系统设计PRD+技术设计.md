# 第一部分：局内排行榜系统 PRD

## 2. 模块背景

《吞噬细胞》是一款实时多人吞噬竞技游戏。玩家在对局中通过吞噬食物、吞噬玩家、分裂追击、吐球调整等方式不断变化质量和得分。

局内排行榜用于实时反馈玩家当前对局表现，让玩家知道：

1. 当前谁最强。
2. 自己当前排第几。
3. 自己距离前几名还有多大差距。
4. 吞噬或被吞噬后排名如何变化。
5. 对局结束前是否需要主动进攻或保守生存。

局内排行榜不是全服排行榜，它只在当前房间、当前对局内有效。对局结束后，局内排行榜结果会作为结算排名的重要依据。

------

## 3. 模块目标

### 3.1 产品目标

| 目标         | 说明                                       |
| ------------ | ------------------------------------------ |
| 实时反馈表现 | 玩家能看到自己当前分数和排名               |
| 增强竞技感   | Top N 排行让玩家有追赶目标                 |
| 促进对抗     | 排名变化促使玩家主动吞噬、躲避或追击       |
| 支持百人对局 | 单局 100 人时仍能清晰展示排名              |
| 结算结果一致 | 局内排名口径应与结算排名保持一致或明确差异 |
| 展示简洁     | 对战中排行榜不能遮挡核心操作区域           |
| 变化可感知   | 排名上升、下降需要有适度反馈               |

### 3.2 技术目标

| 目标           | 说明                                   |
| -------------- | -------------------------------------- |
| 服务端权威计算 | 排名由服务端计算，客户端只展示         |
| 低频推送       | 排行榜不需要每个 Tick 都计算和推送     |
| 排名口径清晰   | 分数、质量、吞噬数、存活等权重明确     |
| 支持 Top N     | 服务端下发局内前 N 名                  |
| 支持自身排名   | 即使玩家不在 Top N，也需要看到自身排名 |
| 支持死亡玩家   | 玩家死亡后仍可参与最终排名             |
| 支持结算衔接   | 对局结束时输出最终排名数据             |
| 可观测         | 监控排行榜计算耗时、推送次数、玩家数   |

------

## 4. 模块定位

局内排行榜系统位于 Game Server 内部，由服务端根据房间状态计算。

```text
RoomState
  ↓
PlayerStats / PlayerState
  ↓
RankSystem
  ↓
RankState
  ↓
RANK_UPDATE
  ↓
客户端排行榜 UI
```

局内排行榜系统不负责全服排行榜，也不负责发放奖励。它只负责当前房间内的实时排名和最终对局排名数据输出。

------

## 5. 核心设计原则

## 5.1 服务端权威

排行榜由服务端计算，客户端不自行计算最终排名。

客户端可以展示：

```text
当前得分
Top N 排名
自身排名
排名变化动画
```

客户端不能决定：

```text
最终排名
最终得分
是否进入结算奖励
排行榜积分变化
```

------

## 5.2 排行榜低频更新

Game Server 的逻辑 Tick 可以是 20 次 / 秒，但排行榜不需要每次 Tick 都更新。

推荐：

```text
局内排行榜 1 秒更新一次
```

原因：

1. 减少服务端排序压力。
2. 减少 WebSocket 推送量。
3. 避免 UI 频繁跳动。
4. 让玩家更容易理解排名变化。

------

## 5.3 当前排名与最终排名保持一致

MVP 阶段建议：

```text
局内实时排名口径 = 结算最终排名口径
```

这样玩家在局内看到的排名与结算结果一致，降低理解成本。

如果后续引入更复杂结算，例如击杀数、存活时间、任务加成，需要在结算页明确展示原因。

------

## 5.4 Top N + 自身排名

局内排行榜不应展示 100 名完整列表。

推荐展示：

```text
Top 10 + 当前玩家自身排名
```

如果当前玩家在 Top 10 内，自身排名可以高亮展示；如果不在 Top 10 内，则在排行榜底部单独展示“我的排名”。

# 6. 用户场景

## 6.1 玩家吞噬食物后排名上升

### 场景描述

玩家持续吞噬食物，质量增加，得分上升，排名可能上升。

### 产品表现

1. 玩家得分增加。
2. 排行榜中玩家名次上升。
3. 自身排名区域更新。
4. 可选展示“排名上升”动画。

------

## 6.2 玩家吞噬其他玩家后排名大幅上升

### 场景描述

玩家吞噬一个高质量玩家后，质量和得分快速提升。

### 产品表现

1. 吞噬事件播放。
2. 玩家球体变大。
3. 得分明显增加。
4. 排名可能快速上升。
5. 排行榜中高亮当前玩家变化。

------

## 6.3 玩家被吞噬后排名冻结或下降

### 场景描述

玩家被其他玩家吞噬后死亡。

### 产品表现

1. 玩家状态变为死亡。
2. 排行榜中该玩家可以消失、置灰或保留最终位置，规则可配置。
3. 当前玩家进入死亡等待或结算等待状态。
4. 对局结束后按最终规则结算排名。

------

## 6.4 当前玩家不在 Top 10

### 场景描述

单局 100 人时，当前玩家可能不在前 10。

### 产品表现

1. 右侧排行榜展示 Top 10。
2. 底部展示“我的排名：第 25 名”。
3. 展示当前得分。
4. 可展示距离上一名差距，后续支持。

------

## 6.5 对局结束时生成最终排名

### 场景描述

达到对局结束条件后，Game Server 冻结房间状态并生成最终排名。

### 产品表现

1. 局内排行榜停止刷新。
2. 结算系统使用最终排名。
3. 客户端进入结算页。
4. 结算页展示最终名次、得分、奖励。

------

# 8. 排名口径设计

## 8.1 MVP 推荐口径

MVP 阶段建议使用简单口径：

```text
score = currentTotalMass
```

即玩家当前所有球体质量总和作为当前得分。

原因：

1. 简单直观。
2. 玩家容易理解。
3. 与核心玩法强相关。
4. 服务端计算成本低。
5. 结算一致性好。

------

## 8.2 完整版本口径

后续可扩展为综合得分：

```text
score = currentMassScore
      + eatPlayerScore
      + eatFoodScore
      + aliveTimeScore
      + bonusScore
```

示例：

| 得分项           | 说明         |
| ---------------- | ------------ |
| currentMassScore | 当前总质量   |
| eatPlayerScore   | 吞噬玩家加分 |
| eatFoodScore     | 吞噬食物加分 |
| aliveTimeScore   | 存活时间加分 |
| bonusScore       | 模式特殊加分 |

------

## 8.3 不同口径对产品体验的影响

| 口径         | 优点                   | 风险                           |
| ------------ | ---------------------- | ------------------------------ |
| 当前质量     | 直观，实时变化明显     | 被吞噬后分数可能归零或大幅下降 |
| 历史最高质量 | 鼓励进攻，不怕后期被吞 | 当前强弱感不明显               |
| 综合得分     | 更公平，可考虑多维表现 | 玩家理解成本更高               |
| 最终存活排名 | 生存目标明确           | 可能鼓励保守躲藏               |

MVP 推荐使用：

```text
当前质量排名
```

后续根据玩法体验再决定是否改为综合分数。

------

## 8.4 死亡玩家排名口径

MVP 推荐：

```text
玩家死亡后，最终排名按照死亡时的得分和死亡时间决定
```

处理规则：

1. 死亡玩家不再参与实时 Top 10 竞争。
2. 死亡玩家保留死亡时得分。
3. 最终排名中，存活玩家优先于死亡玩家。
4. 死亡玩家之间按死亡时得分排序。
5. 如果得分相同，存活时间更长者排名更高。

也可以简化为：

```text
对局结束时按最终得分排序
```

MVP 如果死亡后不复活，建议保留死亡时得分用于结算。

# 12. 排名计算流程

## 12.1 Tick 中的位置

排行榜不需要每 Tick 都执行。

推荐在 Game Server 中使用独立频率控制：

```text
if now - lastRankUpdateTime >= rankUpdateInterval:
    updateRank()
```

------

## 12.2 实时排名计算流程

```text
1. 获取房间内所有玩家
2. 过滤无效玩家
3. 读取玩家当前状态和统计数据
4. 计算每个玩家 score
5. 按 score 降序排序
6. score 相同则按存活时间、吞噬玩家数等排序
7. 生成完整 rankItems
8. 生成 topN
9. 生成每个玩家 selfRank
10. 更新 RankState
11. 广播 RANK_UPDATE
```

------

## 12.3 排序规则

MVP 排序规则：

```text
score 降序
```

如果 score 相同：

```text
1. eatPlayerCount 多者靠前
2. aliveSeconds 长者靠前
3. userId 较小或进入房间较早者靠前
```

推荐排序优先级：

| 优先级 | 字段           | 排序 |
| ------ | -------------- | ---- |
| 1      | score          | 降序 |
| 2      | eatPlayerCount | 降序 |
| 3      | aliveSeconds   | 降序 |
| 4      | joinOrder      | 升序 |

------

## 12.4 死亡玩家处理

如果 MVP 死亡后不复活，建议：

实时榜：

```text
只展示存活玩家 Top N
```

最终榜：

```text
存活玩家排在死亡玩家前面
死亡玩家按死亡时得分和存活时间排序
```

如果产品希望“死亡后也有排名”，则实时榜中可保留死亡玩家并置灰。

# 13. 分数计算设计

## 13.1 MVP 分数公式

```text
score = currentTotalMass
```

currentTotalMass：

```text
currentTotalMass = sum(player.balls.mass)
```

------

## 13.2 综合分数公式，后续支持

```text
score = currentTotalMass
      + eatPlayerCount * eatPlayerScore
      + eatFoodCount * eatFoodScore
      + aliveSeconds * aliveScorePerSecond
```

示例配置：

```json
{
  "rank": {
    "eatPlayerScore": 50,
    "eatFoodScore": 1,
    "aliveScorePerSecond": 0.5
  }
}
```

------

## 13.3 分数更新时机

分数可在以下时机更新：

1. 玩家吞噬食物。
2. 玩家吞噬吐出物。
3. 玩家吞噬其他玩家。
4. 玩家分裂。
5. 玩家吐球。
6. 玩家死亡。
7. 排行榜周期计算。

MVP 推荐：

```text
每秒统一计算当前分数和排名
```

这样实现简单，也避免频繁排序。

# 14. RANK_UPDATE 消息设计

## 14.1 广播型消息

服务端可以向所有玩家广播相同的 Top N，同时为每个玩家附带不同的 selfRank。

如果协议简单，可以每个玩家单独发送：

```json
{
  "type": "RANK_UPDATE",
  "seq": 4001,
  "serverTime": 1710000001000,
  "data": {
    "roomId": "r_90001",
    "rankSeq": 100,
    "topN": [
      {
        "rank": 1,
        "userId": "10001",
        "nickname": "吞噬细胞",
        "score": 2560,
        "alive": true
      },
      {
        "rank": 2,
        "userId": "10002",
        "nickname": "绿巨人",
        "score": 1980,
        "alive": true
      }
    ],
    "selfRank": {
      "rank": 1,
      "total": 100,
      "score": 2560,
      "alive": true,
      "changed": 2
    }
  }
}
```

------

## 14.2 排名变化字段

changed 表示相比上一次排名变化。

```text
changed = lastRank - currentRank
```

例如：

| lastRank | currentRank | changed |
| -------- | ----------- | ------- |
| 5        | 3           | +2      |
| 3        | 5           | -2      |
| 3        | 3           | 0       |

------

## 14.3 推送频率

推荐：

```text
rankUpdateIntervalMs = 1000
```

如果对局人数较多，可以调整为：

```text
1500ms ~ 2000ms
```

4. 当前玩家高亮。
5. 死亡状态，后续支持。

示例：

```text
1 吞噬细胞 2560
2 绿巨人     1980
3 暴走红球   1620
```

## 15.3 我的排名区域

如果当前玩家不在 Top N：

```text
我的排名：25 / 100
当前得分：580
```

如果当前玩家在 Top N：

```text
我的排名：1 / 100
当前得分：2560
```

## 15.4 排名变化动画

MVP 可先不做动画。

完整版本可支持：

1. 数字闪动。
2. 上升 / 下降箭头。
3. 当前玩家进入前十提示。
4. 第一名变化全局广播，谨慎使用，避免打扰。

# 16. 与其他系统关系

## 16.1 与碰撞与吞噬系统

碰撞与吞噬系统影响：

1. 当前质量。
2. 当前得分。
3. 吞噬食物数量。
4. 吞噬玩家数量。
5. 玩家死亡状态。

排行榜系统读取这些数据进行排名。

------

## 16.2 与分裂与吐球系统

分裂与吐球会影响：

1. 玩家球体数量。
2. 当前总质量。
3. 移动速度。
4. 吐球后质量减少。
5. 排名可能下降。

排行榜系统按玩家总质量或综合得分计算，不按单个球体计算。

------

## 16.3 与 AOI 系统

局内排行榜不受 AOI 过滤。

原因：

1. 排行榜是全局信息。
2. 数据量小。
3. 玩家需要知道全局排名。
4. 即使玩家不在视野内，也可以出现在排行榜上。

------

## 16.4 与状态同步系统

排行榜通过独立消息推送：

```text
RANK_UPDATE
```

不建议将排行榜完整塞进高频 ROOM_SNAPSHOT。

原因：

1. 排行榜更新频率较低。
2. 逻辑上是 UI 数据，不是地图状态。
3. 可以独立控制推送频率。
4. 降低快照包体。

------

## 16.5 与结算系统

对局结束时，RankSystem 输出最终排名数据给结算系统。

```text
RankSystem
  ↓
FinalRankList
  ↓
SettlementSystem
```

结算系统基于最终排名计算：

1. 奖励。
2. 战绩。
3. 经验。
4. 金币。
5. 全服积分，后续支持。

------

# 17. 最终排名设计

## 17.1 最终排名生成时机

当 Game Server 判断游戏结束：

```text
1. 停止核心输入
2. 冻结房间状态
3. RankSystem 执行最终排名计算
4. 输出 FinalRankList
5. 交给结算系统
```

------

## 17.2 最终排名口径

MVP 推荐：

```text
finalScore = finalTotalMass
```

如果玩家已经死亡：

```text
finalScore = deathScore
```

排序建议：

```text
1. 存活玩家优先
2. finalScore 高者靠前
3. eatPlayerCount 多者靠前
4. aliveSeconds 长者靠前
```

------

# 18. 性能设计

## 18.1 性能压力

单局 100 人排行榜压力不大，但需要避免不必要的高频排序。

压力来源：

1. 每秒排序全部玩家。
2. 每个玩家单独生成 selfRank。
3. 给所有玩家推送排行榜消息。
4. 频繁 UI 更新导致客户端开销。

------

## 18.2 MVP 策略

MVP 阶段：

1. 每秒计算一次。
2. 玩家数最多 100。
3. 使用内存排序。
4. 推送 Top 10 + selfRank。
5. 客户端简单更新 UI。

------

## 18.3 优化策略

后续可优化：

1. 排名变化不大时减少推送。
2. 只在得分变化后更新。
3. 使用缓存 RankState。
4. Top N 与 selfRank 分离。
5. Protobuf 减少消息大小。
6. 客户端节流 UI 更新。

# 23. 安全与校验

## 23.1 服务端校验

排行榜计算前需要校验：

1. 房间是否存在。
2. 房间是否处于 RUNNING 或 SETTLING。
3. 玩家状态是否有效。
4. 玩家质量是否为合法数值。
5. 玩家统计数据是否完整。
6. 排名配置是否存在。
7. 最终排名是否只生成一次。

------

## 23.2 反作弊原则

| 风险               | 防护                                        |
| ------------------ | ------------------------------------------- |
| 客户端伪造得分     | 得分由服务端计算                            |
| 客户端伪造排名     | 排名由服务端推送                            |
| 客户端伪造吞噬数   | 吞噬统计由服务端记录                        |
| 客户端伪造结算名次 | 最终排名由 Game Server 输出                 |
| 重复结算           | 结算系统做幂等，RankSystem 只输出一次最终榜 |

# 26. 总结

局内排行榜系统是《吞噬细胞》中强化竞技反馈的重要模块。它让玩家在对局中持续知道自己的表现，并为最终结算提供排名依据。

核心链路如下：

```text
玩家质量 / 统计变化
  ↓
ScoreCalculator 计算得分
  ↓
RankSystem 排序
  ↓
生成 Top N + selfRank
  ↓
RANK_UPDATE 推送客户端
  ↓
对局结束生成 FinalRankList
  ↓
结算系统使用最终排名
```

MVP 阶段应优先保证：

1. 服务端计算排名。
2. 每秒低频推送。
3. 展示 Top 10。
4. 展示当前玩家自身排名。
5. 当前玩家高亮。
6. 对局结束能生成最终排名。
7. 最终排名能衔接结算系统。

当前阶段不要过早设计复杂积分、段位、赛季、全服榜。
