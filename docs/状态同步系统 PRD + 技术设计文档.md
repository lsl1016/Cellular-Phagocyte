# 第一部分：状态同步系统 PRD

## 2. 模块背景

《吞噬细胞》是一款 2D 实时多人对战游戏。玩家在同一房间中持续移动、吞噬、分裂、吐球，服务端需要不断计算房间状态，并将结果同步给所有客户端。

状态同步系统的核心目标是：

```text
服务端负责计算真实状态
客户端负责接收状态并平滑展示
```

客户端不能自己决定最终位置、质量、排名和吞噬结果，只能根据服务端下发的权威状态进行展示。

状态同步系统需要解决以下问题：

1. 服务端多久同步一次状态。
2. 每次同步哪些对象。
3. 同步全量状态还是增量状态。
4. 客户端收到状态后如何平滑渲染。
5. 网络延迟、抖动、丢包时如何处理。
6. 单局 100 人时如何降低同步压力。
7. 后续如何接入 AOI 视野同步。
8. 状态同步如何与 Tick、排行榜、断线重连协作。

------

## 3. 模块目标

### 3.1 产品目标

| 目标         | 说明                               |
| ------------ | ---------------------------------- |
| 画面连续     | 玩家和其他对象移动需要尽量平滑     |
| 状态可信     | 客户端展示的核心结果以服务端为准   |
| 延迟可接受   | 普通网络下操作反馈不能明显迟钝     |
| 排行及时     | 局内排行榜应能周期性更新           |
| 事件明确     | 吞噬、死亡、分裂等事件需要明确展示 |
| 弱网可恢复   | 短时间延迟或断线后能够恢复当前状态 |
| 支持百人同局 | 状态同步需要能支撑单局 100 人目标  |

### 3.2 技术目标

| 目标             | 说明                                       |
| ---------------- | ------------------------------------------ |
| 快照频率可配置   | 不同类型消息采用不同同步频率               |
| Tick 与广播解耦  | 服务端逻辑 Tick 不等于广播频率             |
| 支持全量快照     | MVP 阶段优先实现全量快照                   |
| 支持增量同步     | 后续通过增量降低带宽                       |
| 支持 AOI 接入    | 后续按玩家视野范围过滤对象                 |
| 支持客户端插值   | 客户端通过快照缓冲平滑展示                 |
| 支持序号和时间戳 | 便于乱序、延迟、过期包处理                 |
| 可观测           | 需要监控快照大小、广播耗时、同步延迟等指标 |

------

## 4. 状态同步系统定位

状态同步系统处于 Game Server 和客户端渲染之间。

```text
Game Server Tick
  ↓
房间权威状态
  ↓
状态同步系统
  ↓
WebSocket
  ↓
Cocos Client
  ↓
客户端插值渲染
```

状态同步系统不是游戏规则计算模块，它不负责判断是否吞噬成功，也不负责计算奖励。它负责把已经计算好的服务端状态，以合适的频率和格式发送给客户端。

------

## 5. 核心设计原则

## 5.1 服务端权威

服务端是权威状态来源。

客户端发送：

```text
移动方向
分裂请求
吐球请求
心跳
```

服务端下发：

```text
玩家位置
玩家质量
玩家分身
食物状态
事件结果
排行榜
游戏时间
结算触发
```

------

## 5.2 Tick 与同步频率分离

服务端 Tick 负责计算，状态同步负责广播。

推荐初始频率：

| 类型            | 推荐频率      | 说明                   |
| --------------- | ------------- | ---------------------- |
| 服务端逻辑 Tick | 20 次 / 秒    | 每 50ms 计算一次       |
| 房间快照广播    | 10 次 / 秒    | 每 100ms 广播一次      |
| 局内排行榜      | 1 次 / 秒     | 每秒推送一次           |
| 食物补充信息    | 1 ~ 2 次 / 秒 | 可随快照或增量事件下发 |
| 心跳 Ping/Pong  | 5 ~ 10 秒一次 | 连接检测               |
| 结算结果        | 事件触发      | 游戏结束时推送         |

------

## 5.3 先全量，后增量

MVP 阶段优先采用全量快照，降低开发复杂度。

```text
MVP：全量快照
  ↓
优化阶段：关键对象增量同步
  ↓
性能阶段：AOI + 增量 + Protobuf
```

原因：

1. 全量快照调试简单。
2. 客户端恢复状态容易。
3. 断线重连更方便。
4. 适合先跑通完整链路。

------

## 5.4 客户端平滑展示

客户端不应收到位置后立即硬跳。

客户端应该维护快照缓冲区，通过插值显示对象位置。

```text
收到快照 A
收到快照 B
客户端渲染 A 与 B 之间的过渡状态
```

这样可以缓解网络抖动带来的画面跳动。

------

## 5.5 重要事件可靠展示

移动状态可以允许轻微延迟或丢失，但关键事件必须明确展示。

关键事件包括：

1. 玩家吞噬食物。
2. 玩家吞噬玩家。
3. 玩家分裂。
4. 玩家吐球。
5. 玩家死亡。
6. 玩家断线。
7. 玩家重连。
8. 游戏结束。
9. 结算结果。

MVP 阶段这些事件可以包含在快照中。后续可拆成独立事件消息。

# 6. 用户场景

## 6.1 玩家看到其他玩家移动

### 场景描述

玩家在对战页中看到自己和其他玩家持续移动。

### 流程

```text
服务端 Tick 更新玩家位置
  ↓
状态同步系统生成房间快照
  ↓
通过 WebSocket 推送给客户端
  ↓
客户端放入 SnapshotBuffer
  ↓
客户端按渲染帧率插值显示
```

### 产品要求

1. 移动展示尽量连续。
2. 其他玩家不能频繁瞬移。
3. 网络轻微波动时仍可接受。
4. 网络严重异常时需要有提示。

------

## 6.2 玩家吞噬食物

### 场景描述

玩家球体经过食物区域，服务端判定吞噬成功。

### 同步表现

1. 食物从客户端画面中消失。
2. 玩家质量增加。
3. 玩家球体变大。
4. 得分变化。
5. 可选展示吞噬特效。

------

## 6.3 玩家吞噬玩家

### 场景描述

大球吞噬小球，服务端判定成功。

### 同步表现

1. 被吞噬玩家球体消失或死亡。
2. 吞噬方质量增加。
3. 局内排行榜可能变化。
4. 客户端展示吞噬事件特效。
5. 被吞噬玩家进入死亡或复活流程。

------

## 6.4 玩家分裂

### 场景描述

玩家点击分裂后，服务端校验通过并生成多个球体。

### 同步表现

1. 当前玩家从一个球变为多个球。
2. 分裂方向与服务端结果一致。
3. 其他客户端也看到分裂结果。
4. 分裂产生的球体继续参与后续同步。

------

## 6.5 玩家断线重连

### 场景描述

玩家短暂断线后重新连接。

### 同步表现

1. 客户端重新建立 WebSocket。
2. 服务端校验重连身份。
3. 服务端下发当前完整房间快照。
4. 客户端清理本地旧状态。
5. 客户端使用最新快照恢复画面。

------

# 10. 同步模式设计

## 10.1 全量快照

全量快照指服务端每次下发客户端当前应该知道的完整状态。

MVP 阶段推荐使用。

优点：

1. 实现简单。
2. 客户端状态恢复容易。
3. 调试方便。
4. 断线重连友好。

缺点：

1. 包体较大。
2. 单局人数和对象数量增加后带宽压力较高。
3. 食物等对象过多时容易造成同步压力。

------

## 10.2 增量快照

增量快照指服务端只下发相对上一次快照发生变化的内容。

后续版本支持。

增量内容包括：

1. 新增对象。
2. 更新对象。
3. 删除对象。
4. 事件对象。

优点：

1. 减少包体。
2. 降低带宽。
3. 更适合百人房间。

缺点：

1. 客户端状态合并复杂。
2. 丢包或乱序时需要恢复机制。
3. 需要定期全量快照校正。

------

## 10.3 混合同步

推荐最终方案：

```text
周期全量快照 + 高频增量快照
```

例如：

| 消息       | 频率        | 说明         |
| ---------- | ----------- | ------------ |
| 增量快照   | 10 次 / 秒  | 同步高频变化 |
| 全量快照   | 1 次 / 5 秒 | 校正状态     |
| 事件消息   | 事件触发    | 同步关键事件 |
| 排行榜消息 | 1 次 / 秒   | 同步排名     |

------

# 12. 服务端同步流程

## 12.1 全量快照生成流程

```text
1. Room Tick 完成状态更新
2. 判断当前 Tick 是否需要广播快照
3. SnapshotSystem 读取 RoomState
4. 生成玩家状态列表
5. 生成食物状态列表
6. 读取 EventBuffer
7. 写入 seq、serverTime、tickSeq
8. MessageCodec 编码为 JSON
9. BroadcastSystem 推送给房间内玩家
10. 清理已下发事件
```

------

## 12.2 增量快照生成流程

后续版本支持。

```text
1. Tick 执行前记录状态版本
2. Tick 执行过程中记录对象变更
3. 生成 upserts 和 deletes
4. 附带事件列表
5. 标记 baseSeq
6. 发送 ROOM_DELTA
7. 客户端基于 baseSeq 合并状态
8. 如果 baseSeq 不连续，请求全量恢复
```

------

## 12.3 按玩家定制快照流程

接入 AOI 后支持。

```text
1. 生成房间权威状态
2. 遍历每个玩家
3. 根据玩家视野范围筛选对象
4. 生成该玩家可见快照
5. 推送给该玩家
```

MVP 阶段不做 AOI，所有玩家收到同一份房间快照。

------

# 13. 客户端同步流程

## 13.1 快照接收流程

```text
1. WebSocket 收到消息
2. MessageCodec 解析消息
3. 判断消息类型
4. 校验 seq 和 serverTime
5. 如果是旧快照则丢弃
6. 如果是新快照则写入 SnapshotBuffer
7. EntityManager 根据对象 ID 创建或更新实体
8. InterpolationSystem 负责渲染帧插值
```

------

## 13.2 客户端插值流程

```text
1. 客户端维护快照缓冲区
2. 当前渲染时间使用 serverTime - interpolationDelay
3. 在缓冲区中找到前后两个快照
4. 根据时间比例计算插值位置
5. 更新实体显示位置
6. 如果缺少后续快照，短时间内可外推或保持
```

推荐插值延迟：

```text
100ms ~ 200ms
```

------

## 13.3 对象生命周期处理

客户端根据快照处理对象：

| 情况             | 处理                     |
| ---------------- | ------------------------ |
| 快照中出现新对象 | 创建实体                 |
| 快照中对象仍存在 | 更新目标状态             |
| 快照中对象消失   | 隐藏或播放消失动画后回收 |
| 对象进入视野     | 创建或显示               |
| 对象离开视野     | 隐藏或回收               |
| 对象被吞噬       | 播放吞噬特效并移除       |

------

# 14. 序号与时间设计

## 14.1 消息序号 seq

每个服务端消息都带 seq。

用途：

1. 判断消息顺序。
2. 丢弃过期消息。
3. 发现丢失消息。
4. 后续支持增量同步 baseSeq。

规则：

```text
seq 单调递增
客户端只处理比 lastSeq 更新的快照
```

------

## 14.2 tickSeq

tickSeq 表示服务端房间 Tick 序号。

用途：

1. 定位快照产生于哪个 Tick。
2. 排查状态同步延迟。
3. 分析 Tick 和广播之间的关系。

------

## 14.3 serverTime

serverTime 表示服务端生成快照的时间。

用途：

1. 客户端插值。
2. 延迟估算。
3. 断线重连恢复。
4. 日志排查。

------

# 15. 同步频率设计

## 15.1 推荐频率

| 消息类型      | 频率            | 说明                   |
| ------------- | --------------- | ---------------------- |
| ROOM_SNAPSHOT | 10 次 / 秒      | MVP 全量快照           |
| ROOM_DELTA    | 10 ~ 20 次 / 秒 | 后续增量快照           |
| RANK_UPDATE   | 1 次 / 秒       | 局内排行榜             |
| HEARTBEAT     | 5 ~ 10 秒一次   | 心跳                   |
| EVENT         | 事件触发        | 后续独立事件消息       |
| FULL_RECOVER  | 按需            | 重连或状态不一致时下发 |

------

## 15.2 广播频率控制

广播频率不应直接等于客户端渲染帧率。

```text
服务端广播 10 次 / 秒
客户端渲染 60 帧 / 秒
客户端通过插值补齐中间帧
```

这样可以降低服务端和网络压力，同时保持画面平滑。

------

# 16. 带宽与包体设计

## 16.1 包体压力来源

单局 100 人时，包体压力主要来自：

1. 玩家球体数量。
2. 每个玩家分裂后的球体数量。
3. 食物数量。
4. 刺球数量。
5. 吐出物数量。
6. 快照广播频率。
7. 是否全量广播。

------

## 16.2 MVP 控制策略

MVP 阶段建议：

1. 控制食物数量。
2. 控制单玩家分身数量。
3. 快照频率先设为 10 次 / 秒。
4. 排行榜独立低频推送。
5. 不把不必要字段放进高频快照。
6. 对象字段尽量短且稳定。
7. 后续切换 Protobuf。

------

## 16.3 后续优化策略

完整版本建议：

1. AOI 过滤。
2. 增量同步。
3. Protobuf 二进制协议。
4. 食物按区域批量同步。
5. 大对象分批推送。
6. 事件消息独立化。
7. 定期全量校正。
8. 压缩或量化坐标字段。

------

# 17. AOI 接入设计

## 17.1 AOI 目标

AOI 用于减少每个客户端需要接收的对象数量。

原则：

```text
玩家只接收自己视野范围内的对象
```

------

## 17.2 MVP 与 AOI 的关系

MVP 阶段可以不做 AOI，先全房间广播。

但服务端快照结构需要预留 AOI 接入点。

```text
RoomState
  ↓
AOIFilter
  ↓
PlayerVisibleSnapshot
```

MVP 阶段 AOIFilter 可以直接返回全量对象。

------

## 17.3 AOI 后续方案

后续可采用网格方案：

1. 地图划分为多个网格。
2. 每个对象根据坐标归属网格。
3. 玩家根据视野半径查询周围网格。
4. 只同步附近对象。
5. 对象进入视野时发送新增。
6. 对象离开视野时发送删除。

------

# 18. 弱网处理设计

## 18.1 网络抖动

处理方式：

1. 客户端快照缓冲。
2. 插值延迟 100ms ~ 200ms。
3. 旧包丢弃。
4. 短时间缺包可保持最后状态。
5. 严重延迟时显示网络提示。

------

## 18.2 消息乱序

处理方式：

1. 使用 seq 判断新旧。
2. 旧 seq 消息直接丢弃。
3. 增量同步阶段需要判断 baseSeq 是否连续。
4. 不连续时请求全量恢复。

------

## 18.3 断线重连

处理方式：

1. 客户端断线后进入重连状态。
2. 重连成功后发送 RECONNECT。
3. 服务端校验玩家身份和房间状态。
4. 服务端下发 ROOM_RECOVER_SNAPSHOT。
5. 客户端清空本地房间状态。
6. 客户端基于恢复快照重新渲染。

------

# 26. 总结

状态同步系统是《吞噬细胞》实时对战体验的核心模块之一。它负责将 Game Server 的权威房间状态同步给客户端，并让客户端以平滑、稳定的方式展示出来。

核心链路如下：

```text
Game Server Tick
  ↓
生成权威 RoomState
  ↓
生成 ROOM_SNAPSHOT
  ↓
WebSocket 广播
  ↓
客户端 SnapshotBuffer
  ↓
客户端插值渲染
```

MVP 阶段应优先保证：

1. 全量快照可以稳定下发。
2. 客户端可以正确接收和渲染。
3. seq、serverTime、tickSeq 等基础字段齐全。
4. 快照频率和 Tick 频率解耦。
5. 断线重连后可以用全量快照恢复。
6. 关键事件可以随快照展示。
7. 后续能平滑演进到 AOI、增量同步和 Protobuf。

当前阶段不要过早追求复杂网络优化。先用全量快照跑通完整对战体验，再逐步引入增量同步、AOI 和协议压缩。
