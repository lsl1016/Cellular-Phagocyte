# 2. 设计背景

《吞噬细胞》是实时多人对战游戏，涉及多个关键链路：

```text
登录
  ↓
匹配
  ↓
房间
  ↓
WebSocket
  ↓
Game Server / Tick
  ↓
状态同步
  ↓
局内排行榜
  ↓
结算
  ↓
资产入账
  ↓
战绩保存
```

这些链路一旦出现问题，单靠接口返回错误码很难定位原因。

例如：

| 问题           | 需要日志定位的信息                                    |
| -------------- | ----------------------------------------------------- |
| 玩家匹配失败   | userId、matchId、mode、队列状态、失败原因             |
| 玩家进房失败   | roomId、serverId、enterToken、房间状态                |
| WebSocket 断开 | connectId、userId、roomId、断开原因                   |
| Tick 卡顿      | roomId、tickSeq、tickDurationMs、玩家数、对象数       |
| 状态不同步     | snapshotSeq、snapshotSize、clientSeq、延迟            |
| 结算失败       | roomId、userId、settlementId、事务状态                |
| 金币未到账     | bizId、assetType、beforeAmount、afterAmount、幂等状态 |
| 重连失败       | reconnectToken、roomId、deadline、失败原因            |

因此需要一个统一日志系统，用结构化日志串联全链路。

| 结算日志       | Settlement Service         | 结算、奖励、写库             |
| 资产日志       | Asset Service              | 金币经验变更、流水、幂等     |
| 排行榜日志     | Rank Service               | 榜单更新、查询、Redis 异常   |
| 任务日志       | Task Service               | 任务进度、奖励领取           |
| 系统日志       | 所有服务                   | 启动、关闭、配置加载、异常   |

| 类型     | 说明                                   |

| 性能日志 | Tick 耗时、快照大小、SQL 耗时          |
| 错误日志 | 异常、失败、超时                       |
| 安全日志 | Token 无效、非法操作、重复请求         |
| 审计日志 | 资产变化、奖励发放、封禁操作，后续支持 |

# 6. 日志级别设计

| 级别  | 使用场景                                           |
| ----- | -------------------------------------------------- |
| DEBUG | 本地调试、详细状态、临时排查                       |
| INFO  | 正常业务流程，如匹配成功、入房成功、结算成功       |
| WARN  | 可恢复异常，如重连失败一次、重复请求、参数边界异常 |
| ERROR | 不可忽略错误，如结算失败、资产入账失败、房间异常   |
| FATAL | 服务无法启动或必须退出，慎用                       |

| ------------- | ------------------------ |
| local         | DEBUG                    |
| dev           | DEBUG / INFO             |
| test          | INFO                     |
| prod          | INFO                     |
| prod 故障排查 | 临时调为 DEBUG，谨慎使用 |

# 8. TraceId 设计

## 8.1 TraceId 作用

traceId 用于串联一次完整链路。

例如开始匹配：

```text
客户端点击开始
  ↓
API Server
  ↓
Match Server
  ↓
Room Service
  ↓
Game Server
```

这些服务的日志都应该带同一个 traceId。

------

## 8.2 TraceId 生成规则

入口服务负责生成 traceId。

入口包括：

1. HTTP 请求进入 API Server。
2. WebSocket 连接建立。
3. Game Server 内部定时任务。
4. 结算异步任务。
5. 排行榜更新任务。

如果客户端传入 traceId，可以接收，但需要服务端重新校验或覆盖，避免异常值污染日志。

------

## 8.3 TraceId 传播

HTTP 传播：

```http
X-Trace-Id: trace_xxx
```

WebSocket 消息中携带：

```json
{
  "type": "MOVE",
  "seq": 1001,
  "traceId": "trace_xxx",
  "data": {}
}
```

内部服务调用时继续传递：

```text
API Server → Match Server → Room Service
```

# 10. 日志输出设计

## 10.1 stdout 输出

Docker 部署下，所有服务必须输出到 stdout。

原因：

1. Docker 原生支持日志收集。
2. `docker logs` 可直接查看。
3. 1Panel 等面板可直接检索容器日志。
4. 后续日志采集 Agent 可以采集 stdout。

------

## 10.2 文件输出

单机部署和本地开发可同时输出到文件。

推荐目录：

```text
/logs
  ├── api-server.log
  ├── match-server.log
  ├── game-server.log
  ├── settlement-service.log
  ├── asset-service.log
  └── error.log
```

------

## 10.3 错误日志单独输出

ERROR 级别日志可以额外写入：

```text
/logs/error.log
```

好处：

1. 快速定位错误。
2. 方便告警采集。
3. 减少从大量 INFO 中筛选的成本。

------

# 11. 日志滚动策略

如果写文件，需要避免日志文件无限增长。

推荐策略：

| 配置             | 建议值    |
| ---------------- | --------- |
| 单文件最大大小   | 100MB     |
| 最大保留文件数   | 10        |
| 最大保留天数     | 7 ~ 30 天 |
| 是否压缩历史日志 | 是        |
| error 日志保留   | 30 天     |

# 12. 日志脱敏设计

## 12.1 不能直接输出的内容

日志中不应输出：

```text
完整 accessToken
完整 reconnectToken
密码
手机号
邮箱
支付信息
真实 IP，按策略处理
设备唯一标识明文，按策略处理
```

------

## 12.2 Token 脱敏

错误示例：

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI..."
}
```

推荐：

```json
{
  "accessTokenHash": "token_hash_xxx"
}
```

或者：

```json
{
  "accessToken": "eyJhbGci...****"
}
```

------

## 12.3 昵称处理

昵称可以写日志，但后续如果接入公开检索平台，需要注意敏感词和隐私策略。

# 13. 日志采样设计

Game Server 日志量可能非常大，尤其是 Tick、输入、快照、食物吞噬。

## 13.1 建议完整记录的日志

必须完整记录：

```text

房间结束
结算成功
结算失败
资产变更
WebSocket 重连失败

```

------

## 13.2 建议采样的日志

可以采样：

```text
玩家吃食物

Tick 正常执行
排行榜正常刷新
```

------

## 13.3 慢操作必须记录


# 19. Go 服务实现建议

## 19.1 日志库选择

推荐优先级：

| 日志库  | 说明                |
| ------- | ------------------- |
| zap     | 性能好，结构化成熟  |
| zerolog | 极致轻量，JSON 友好 |
| slog    | Go 标准库，简单稳定 |

MVP 推荐：

```text
slog 或 zap
```

如果想少依赖第三方库：

```text
slog
```

如果更关注性能：

```text
zap
```

------

## 19.2 日志封装

建议封装统一 logger 包。

```text
pkg/logger
  ├── logger.go
  ├── context.go
  ├── fields.go
  └── middleware.go
```

职责：

1. 初始化日志。
2. 注入 traceId。
3. 封装公共字段。
4. 提供 HTTP middleware。
5. 提供 WebSocket 连接日志工具。
6. 提供业务字段快捷方法。

------

## 19.3 日志调用示例

注意使用结构化字段，不要字符串拼接。

```go
logger.Info(ctx, "match enqueue success",
    "event", "match_enqueue",
    "userId", userID,
    "matchId", matchID,
    "mode", mode,
)
```

错误日志：

```go
logger.Error(ctx, "settlement failed",
    "event", "settlement_failed",
    "roomId", roomID,
    "userId", userID,
    "errorCode", errCode,
    "error", err.Error(),
)
```

格式化输出时也保持占位符风格：

```go
logger.Info(ctx, "tick duration:%d", durationMs)
```

不过更推荐结构化字段：

```go
logger.Warn(ctx, "room tick slow",
    "event", "room_tick_slow",
    "roomId", roomID,
    "tickSeq", tickSeq,
    "durationMs", durationMs,
)
```

# 21. WebSocket 日志中间件

WebSocket 连接需要记录：

1. 连接建立。
2. 认证成功。
3. 认证失败。
4. 消息解析失败。
5. 输入频率异常。
6. 连接断开。
7. 重连成功。
8. 连接替换。

每条连接生成 connectId：

```text

```

后续所有连接日志带上：

```text
connectId
userId
roomId
serverId
```

# 26. 总结

日志系统是《吞噬细胞》后端稳定性和问题排查的基础模块。它不直接参与玩法，但会贯穿登录、匹配、房间、对战、同步、结算、资产、排行榜、任务等全链路。

核心设计是：

```text
统一 JSON 结构化日志
  ↓
统一 traceId / userId / roomId / bizId
  ↓
关键业务节点打日志
  ↓
慢操作和错误重点记录
  ↓
stdout + 文件输出
  ↓
后续接入 Loki / ELK / Grafana
```

MVP 阶段优先做好：

1. 统一日志格式。
2. HTTP 请求日志。
3. WebSocket 连接日志。
4. 匹配、房间、结算、资产关键日志。
5. 慢 Tick 日志。
6. ERROR 日志单独输出。
7. Docker 环境可查看日志。
8. 按 userId、roomId、bizId 能快速检索问题。

当前阶段不用急着搭完整 ELK 或 Loki。先把日志字段设计好、关键链路打全，后续接入日志平台会非常顺。
