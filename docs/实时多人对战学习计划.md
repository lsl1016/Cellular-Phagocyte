把「球球大作战」当成一个非常适合学习**实时多人游戏服务器**的案例，因为它不像 FPS 那么极端复杂，但又包含了实时同步、房间、匹配、排行榜、结算、断线重连、反作弊等核心问题。

我建议你先不要一上来就学“完整游戏架构”，而是按一局游戏的生命周期来学：

```text
进入游戏
  ↓
匹配 / 分配房间
  ↓
加载地图与玩家
  ↓
实时移动与同步
  ↓
玩家吞噬 / 分裂 / 吐球 / 碰撞
  ↓
状态广播
  ↓
排行榜实时更新
  ↓
掉线 / 重连 / 退出
  ↓
游戏结束
  ↓
结算 / 奖励 / 战绩保存
```

下面先给你规划一版值得学习的知识地图。

------

# 1. 匹配进入游戏：Matchmaking

这是玩家从大厅进入一局游戏的第一步。

你要重点学习：

| 学习点           | 说明                                   |
| ---------------- | -------------------------------------- |
| 匹配队列         | 玩家点击开始后进入等待队列             |
| 匹配规则         | 按段位、等级、地区、延迟、玩法模式匹配 |
| 超时扩大匹配范围 | 等太久就放宽条件                       |
| 房间分配         | 匹配成功后把玩家分配到某个游戏房间     |
| 热点控制         | 防止大量玩家同时进一个房间导致压力过大 |
| 机器人补位       | 人数不够时用 Bot 填充                  |

可以先从最简单的规则开始：

```text
玩家点击开始
  ↓
进入匹配队列
  ↓
队列人数达到 N 人
  ↓
创建房间
  ↓
把 N 个玩家加入房间
  ↓
通知客户端进入游戏
```

后面再扩展：

```text
按模式匹配
按段位匹配
按地区匹配
按延迟匹配
超时降级匹配
```

这一块可以重点学：

```text
Redis 队列
内存队列
定时扫描匹配
房间服务
玩家状态机
```

------

# 2. 房间与游戏实例：Room / Game Server

匹配成功后，玩家不是直接“进入游戏”，而是进入一个**游戏房间实例**。

你要学习：

| 学习点       | 说明                                |
| ------------ | ----------------------------------- |
| 房间生命周期 | 创建、运行、结束、销毁              |
| 房间状态     | WAITING、LOADING、RUNNING、FINISHED |
| 玩家列表     | 当前房间有哪些玩家                  |
| 地图状态     | 食物、刺球、玩家位置、质量          |
| Tick 循环    | 服务端定时推进游戏逻辑              |
| 房间隔离     | 每个房间独立计算，避免互相影响      |

一个房间可以理解成：

```go
type Room struct {
    ID        string
    Players   map[string]*Player
    Foods     map[string]*Food
    Viruses   map[string]*Virus
    State     RoomState
    StartTime time.Time
}
```

房间状态流转大概是：

```text
CREATED
  ↓
WAITING
  ↓
LOADING
  ↓
RUNNING
  ↓
SETTLING
  ↓
FINISHED
  ↓
DESTROYED
```

你要重点理解一个问题：

> 实时游戏里，真正的核心不是接口 CRUD，而是“游戏循环”。

也就是：

```text
每隔 50ms / 100ms 执行一次：
1. 收集玩家输入
2. 更新玩家位置
3. 处理碰撞
4. 处理吞噬
5. 更新排行榜
6. 广播最新状态
```

------

# 3. 网络通信：HTTP、WebSocket、UDP 的取舍

实时游戏和普通 Web 项目最大的区别就是通信模型。

普通 Web 项目通常是：

```text
客户端请求
  ↓
服务端响应
```

但多人实时游戏是：

```text
客户端持续发送输入
服务端持续广播状态
```

你要重点学习：

| 通信方式  | 适合场景                         |
| --------- | -------------------------------- |
| HTTP      | 登录、获取配置、查询战绩、排行榜 |
| WebSocket | 实时对战、房间消息、状态同步     |
| UDP / KCP | 更高实时性的动作游戏             |
| TCP       | 稳定但可能有延迟堆积             |
| Protobuf  | 二进制协议，减少包体积           |
| JSON      | 开发简单，但性能一般             |

对于你学习阶段，建议先用：

```text
HTTP + WebSocket + JSON
```

等你理解完整流程后，再升级为：

```text
HTTP + WebSocket/KCP + Protobuf
```

球球这类游戏不一定要一开始就上 UDP。因为它不是毫秒级射击命中判定，WebSocket 足够用来做 MVP。

# 4. 实时同步：Online Sync

这是最值得深入的一块。

你要学习的不是“怎么把位置发给别人”，而是：

> 服务端和多个客户端之间，如何保持同一个游戏世界的状态一致。

核心问题包括：

| 问题                           | 说明                       |
| ------------------------------ | -------------------------- |
| 谁来决定玩家位置？             | 客户端决定还是服务端决定   |
| 客户端发什么？                 | 发坐标，还是发操作输入     |
| 服务端广播什么？               | 广播全量状态，还是增量状态 |
| 网络延迟怎么办？               | 客户端预测、插值、延迟补偿 |
| 丢包怎么办？                   | 状态快照、序列号、重传     |
| 不同客户端看到的不一致怎么办？ | 服务端权威状态             |

建议你按三个阶段学。

------

## 阶段 1：客户端上传坐标，服务端转发

最简单：

```text
客户端 A 发送：
{
  "x": 100,
  "y": 200
}

服务端广播给其他玩家：
{
  "playerId": "A",
  "x": 100,
  "y": 200
}
```

优点：简单。

缺点：容易作弊。客户端想去哪就去哪。

------

## 阶段 2：客户端上传操作，服务端计算坐标

更合理：

```text
客户端发送：
{
  "direction": 45,
  "speed": 1
}
```

服务端根据方向、速度、质量、地图边界计算位置：

```text
newX = oldX + velocityX * deltaTime
newY = oldY + velocityY * deltaTime
```

然后服务端广播：

```json
{
  "players": [
    {
      "id": "p1",
      "x": 100,
      "y": 200,
      "mass": 35
    }
  ]
}
```

这个模式更接近真实多人游戏。

------

## 阶段 3：服务端权威 + 客户端预测

最终比较成熟的模式是：

```text
客户端立即预测自己的移动
  ↓
服务端收到输入后计算权威结果
  ↓
服务端返回权威状态
  ↓
客户端修正本地状态
```

这样玩家操作会更顺滑，同时又不容易作弊。

你后面可以重点学习：

```text
客户端预测
服务端权威
插值渲染
状态快照
输入序列号
延迟补偿
```

# 5. Tick 机制：实时游戏的心跳

实时游戏服务端通常不是来一个请求处理一次，而是有固定 Tick。

例如：

```text
20 Tick / 秒：每 50ms 更新一次
10 Tick / 秒：每 100ms 更新一次
```

每个 Tick 做这些事：

```text
读取玩家输入
更新玩家位置
处理碰撞检测
处理吞噬逻辑
生成状态快照
广播给客户端
```

一个简化版 Tick 流程：

```text
Room Tick
  ↓
读取输入队列
  ↓
移动玩家
  ↓
检测碰撞
  ↓
处理吞噬
  ↓
刷新食物
  ↓
更新排行榜
  ↓
广播状态
```

这块你要重点理解：

| 概念           | 说明                   |
| -------------- | ---------------------- |
| Tick Rate      | 服务端每秒更新多少次   |
| Delta Time     | 两次 Tick 之间的时间差 |
| Input Buffer   | 玩家输入缓冲区         |
| Snapshot       | 某一刻的游戏状态快照   |
| Broadcast Rate | 服务端广播频率         |

注意：Tick 频率和广播频率可以不一样。

例如：

```text
服务端逻辑 Tick：20 次 / 秒
状态广播：10 次 / 秒
排行榜广播：1 次 / 秒
```

这样可以减少网络压力。

# 6. 玩家移动、质量、速度模型

球球类游戏有一个非常适合学习的规则：

> 球越大，质量越大，速度越慢。

你可以设计一个简单模型：

```text
radius = sqrt(mass)
speed = baseSpeed / sqrt(mass)
```

玩家吞掉食物后：

```text
mass += food.mass
```

吞掉其他玩家后：

```text
mass += target.mass * 0.8
```

然后重新计算：

```text
半径
速度
视野范围
排行榜分数
```

这里适合学习：

```text
游戏数值设计
物理简化模型
碰撞检测
服务端状态更新
```

# 7. 碰撞检测与吞噬判定

这是球球类游戏的核心玩法。

你要学习：

| 学习点       | 说明                 |
| ------------ | -------------------- |
| 圆形碰撞检测 | 两个球是否接触       |
| 吞噬条件     | 大球是否能吃小球     |
| 距离计算     | 判断两个圆心距离     |
| 空间分区     | 优化大量对象碰撞检测 |
| 边界限制     | 玩家不能移动到地图外 |

最基础的圆形碰撞：

```text
distance(centerA, centerB) <= radiusA + radiusB
```

吞噬判定可以是：

```text
massA > massB * 1.2
并且
distance(centerA, centerB) < radiusA
```

一开始可以暴力遍历：

```text
所有玩家两两检测
所有玩家和食物检测
```

后面再优化：

```text
网格分区
四叉树
AOI 区域同步
```

# 8. AOI：视野范围与局部同步

多人游戏不能把全地图所有对象都发给每个玩家，否则网络量会爆炸。

所以需要 AOI：

```text
Area Of Interest
玩家感兴趣区域
```

也就是：

```text
玩家只接收自己视野范围内的对象
```

例如玩家 A 在地图左上角，就没必要收到右下角玩家的位置。

你要学习：

| 学习点       | 说明                       |
| ------------ | -------------------------- |
| 视野范围     | 玩家能看到多大区域         |
| 九宫格 AOI   | 把地图切成网格             |
| 附近对象查询 | 只同步附近玩家、食物、刺球 |
| 进入视野事件 | 对象进入玩家视野           |
| 离开视野事件 | 对象离开玩家视野           |
| 减少广播数据 | 不给所有人发全量地图       |

同步方式从低到高：

```text
全房间广播
  ↓
按玩家视野过滤
  ↓
网格 AOI
  ↓
增量同步
```

这一块非常值得学，因为它不只适用于游戏，也适用于 IM 在线状态、地图协同、实时看板等业务。

------

# 9. 在线排行榜：实时排名与结算排名

球球类游戏有两个排行榜：

```text
局内实时排行榜
全服排行榜 / 历史排行榜
```

局内排行榜通常基于：

```text
当前质量 mass
当前分数 score
吞噬数量 killCount
存活时间 aliveTime
```

局内排行榜可以在房间内存中维护：

```text
每秒排序一次
广播 Top 10
```

例如：

```text
Room 内：
players 按 mass 排序
取前 10 名
广播给所有玩家
```

全服排行榜可以用 Redis Sorted Set：

```text
ZADD leaderboard score userId
ZREVRANGE leaderboard 0 99 WITHSCORES
```

你要区分：

| 类型       | 存储位置        | 更新频率       |
| ---------- | --------------- | -------------- |
| 局内排行榜 | 房间内存        | 高频，1 秒一次 |
| 日榜       | Redis / DB      | 中频           |
| 周榜       | Redis / DB      | 中频           |
| 历史战绩   | MySQL / MongoDB | 游戏结束后写入 |

# 10. 分裂、吐球、技能操作

球球大作战里还有一些操作：

```text
分裂
吐球
合体
加速
吃刺球
```

这些操作非常适合学习“客户端输入事件”和“服务端技能逻辑”。

例如分裂：

```text
客户端发送：
{
  "type": "SPLIT",
  "direction": 90
}
```

服务端处理：

```text
检查质量是否足够
检查冷却时间
生成一个新的球体
给新球体一个初速度
广播分裂事件
```

你要学习：

| 学习点     | 说明                           |
| ---------- | ------------------------------ |
| 操作事件   | MOVE、SPLIT、EJECT、BOOST      |
| 冷却时间   | 防止技能无限触发               |
| 服务端校验 | 客户端不能自己说“我分裂成功了” |
| 状态变化   | 一个玩家可能控制多个球         |
| 广播事件   | 其他玩家也要看到分裂效果       |

这块很适合做成事件模型：

```text
InputEvent
  ↓
GameLogic
  ↓
StateChange
  ↓
BroadcastEvent
```

# 11. 断线、重连、退出

实时游戏一定要考虑网络不稳定。

你要学习：

| 场景       | 处理方式                 |
| ---------- | ------------------------ |
| 短暂断线   | 保留玩家状态几秒         |
| 超时未重连 | 变成 AI 托管或移除       |
| 主动退出   | 从房间移除，进入结算     |
| App 切后台 | 暂停输入，但角色继续存在 |
| 重连成功   | 下发当前游戏快照         |

重连流程可以是：

```text
WebSocket 断开
  ↓
房间标记玩家 disconnected
  ↓
保留状态 30 秒
  ↓
玩家重新连接
  ↓
根据 userId + roomId 找回房间
  ↓
下发当前快照
  ↓
继续游戏
```

这里会涉及：

```text
连接状态
玩家状态
房间状态
断线计时器
快照恢复
```

# 12. 反作弊：服务端权威

实时游戏里，客户端是不可信的。

你要学习：

| 作弊方式 | 防御方式                     |
| -------- | ---------------------------- |
| 修改坐标 | 客户端只发方向，服务端算位置 |
| 修改质量 | 质量只能由服务端计算         |
| 加速移动 | 服务端校验最大速度           |
| 秒吃别人 | 服务端做吞噬判定             |
| 篡改结算 | 服务端生成结算结果           |
| 重放请求 | 加序列号、时间戳、Token      |

基本原则：

```text
客户端只负责输入和展示
服务端负责计算和裁决
```

也就是：

```text
客户端可以说：“我要往右移动”
客户端不能说：“我已经移动到 x=9999”
客户端可以说：“我要分裂”
客户端不能说：“我已经吃掉了玩家 B”
```

# 13. 游戏结算：Settlement

一局结束后，需要做结算。

结算内容包括：

```text
最终排名
最终质量
吞噬玩家数
吞噬食物数
存活时间
获得金币
获得经验
段位变化
战绩记录
任务进度
排行榜积分
```

结算流程：

```text
游戏结束
  ↓
冻结房间状态
  ↓
计算玩家排名
  ↓
计算奖励
  ↓
写入战绩
  ↓
更新用户资产
  ↓
更新排行榜
  ↓
通知客户端结算结果
  ↓
销毁房间
```

这里要重点学习：

| 学习点       | 说明                         |
| ------------ | ---------------------------- |
| 幂等结算     | 防止重复结算导致奖励重复发放 |
| 异步写库     | 避免结算时阻塞游戏线程       |
| 战绩表       | 保存每局游戏结果             |
| 奖励计算     | 金币、经验、段位分           |
| 排行榜更新   | Redis ZSet                   |
| 任务进度更新 | 每日任务、成就系统           |

结算一定要做幂等，例如：

```text
roomId + userId 唯一结算记录
```

防止同一局重复发奖励。

# 15. 推荐你最终形成的技术模块

可以把整个系统拆成这些模块：

```text
用户服务 User Service
```

# 16. 从匹配到结算的完整链路

你后面可以围绕这条链路逐个拆：

```text
1. 玩家点击开始游戏
2. 客户端请求进入匹配
3. 服务端校验登录态、模式、版本
4. 玩家进入匹配队列
5. 匹配服务找到合适玩家
6. 创建房间或选择已有房间
7. 通知玩家进入房间
8. 客户端建立 WebSocket 连接
9. 玩家加载资源并上报 ready
10. 房间进入 RUNNING 状态
11. 服务端启动 Tick 循环
12. 客户端持续发送输入
13. 服务端计算移动、碰撞、吞噬
14. 服务端广播状态快照
15. 客户端插值渲染其他玩家
16. 房间定时更新局内排行榜
17. 玩家断线则保留状态，支持重连
18. 达到结束条件后冻结房间
19. 服务端计算最终排名
20. 结算服务发放奖励
21. 写入战绩、资产、排行榜
22. 通知客户端展示结算页
23. 销毁房间，释放资源
```
