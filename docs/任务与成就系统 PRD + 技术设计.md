# 第一部分：任务与成就系统 PRD

## 2. 模块背景

《吞噬细胞》的核心循环是：

```text
进入大厅 → 匹配 → 对战 → 结算 → 战绩 → 再来一局
```

这个循环能够支撑基础玩法，但如果玩家只依赖单局输赢，长期目标会比较单薄。任务与成就系统用于补充长期成长目标，让玩家在每局对战之外，也能获得持续反馈。

任务系统主要解决：

```text
今天我要做什么？
完成后能获得什么奖励？
还差多少进度？
```

成就系统主要解决：

```text
我长期达成了哪些里程碑？
我有哪些值得展示的记录？
我还有哪些目标可以追求？
```

任务偏短期、周期性、可重复；成就偏长期、一次性、里程碑。

------

## 3. 模块目标

### 3.1 产品目标

| 目标         | 说明                                       |
| ------------ | ------------------------------------------ |
| 提供每日目标 | 玩家每天登录后有明确目标                   |
| 提升留存     | 通过每日任务、周任务提升回访               |
| 强化成长反馈 | 玩家完成任务后获得金币、经验等奖励         |
| 增强成就感   | 长期成就记录玩家的重要里程碑               |
| 引导核心玩法 | 任务引导玩家参与匹配、吞噬、进入前十等行为 |
| 支持新手引导 | 通过成长任务引导玩家理解基础玩法           |
| 支持奖励闭环 | 任务奖励接入资产系统，保证可追踪           |
| 支持后续运营 | 后续可扩展活动任务、赛季任务、限时任务     |

### 3.2 技术目标

| 目标               | 说明                                 |
| ------------------ | ------------------------------------ |
| 配置化任务         | 任务规则尽量配置化，避免写死         |
| 事件驱动更新       | 通过结算事件、登录事件等更新任务进度 |
| 支持多任务类型     | 每日任务、成长任务、成就任务         |
| 支持奖励领取       | 任务完成后玩家主动领取奖励           |

| 进度可查询         | 客户端可查询任务列表和进度           |

## 4. 模块定位

任务与成就系统位于结算系统之后、资产系统之前。

```text
结算系统
  ↓ 产生对局结果事件
任务与成就系统
  ↓ 更新进度 / 标记完成
资产系统
  ↓ 发放奖励
客户端任务页 / 成就页
```

任务系统不直接参与实时对战。
它读取对局结算结果、用户行为事件，然后更新任务进度。

------

## 5. 核心设计原则

## 5.1 任务进度由服务端计算

客户端不能直接提交任务完成状态。

客户端不能提交：

```text
我完成了每日任务
我吞噬了 10 个玩家
我已经获得成就
```

客户端只能查询任务状态和请求领取奖励。

任务进度必须由服务端根据可信事件更新。

可信事件包括：

1. 登录事件。
2. 结算事件。
3. 战绩结果。
4. 资产发放结果。
5. 排行榜结果，后续支持。
6. 活动行为事件，后续支持。

------

## 5.2 任务完成与奖励领取分离

任务达到条件后，状态变为可领取。

```text
进行中 → 可领取 → 已领取
```

这样可以让玩家主动点击领取，增强反馈感。

也可以后续支持自动领取，但 MVP 推荐手动领取。

------

## 5.3 任务和成就分层设计

| 类型     | 特点                 | 示例                 |
| -------- | -------------------- | -------------------- |
| 每日任务 | 每天重置，可重复完成 | 今日完成 3 局        |
| 周任务   | 每周重置，目标稍大   | 本周进入前十 10 次   |
| 成长任务 | 一次性或阶段性       | 完成第一局游戏       |
| 成就     | 长期里程碑           | 累计吞噬 1000 名玩家 |

MVP 阶段建议先做：

```text
每日任务 + 成长任务 + 成就
```

周任务可以后续支持。

------

## 5.4 奖励通过资产系统发放

任务系统不直接修改用户资产。

正确链路：

```text
任务系统判断可领取
  ↓
调用 Asset Service
  ↓
资产系统写余额和流水
  ↓
任务系统标记已领取
```

这样资产变更统一收口，便于幂等、审计和排查。

# 6. 用户场景

## 6.1 查看每日任务

### 场景描述

玩家进入大厅，点击任务按钮，查看今日任务。

### 展示内容

1. 任务名称。
2. 任务描述。
3. 当前进度。
4. 目标进度。
5. 奖励内容。
6. 任务状态。
7. 领取按钮。

示例：

```text
今日完成 3 局：2 / 3
奖励：金币 x100，经验 x50
```

------

## 6.2 完成任务并领取奖励

### 场景描述

玩家完成一局游戏后，系统更新任务进度。某个任务达到完成条件，玩家在任务页点击领取奖励。

### 用户流程

```text
完成一局对战
  ↓
结算系统生成结果
  ↓
任务系统更新进度
  ↓
任务状态变为可领取
  ↓
玩家点击领取
  ↓
资产系统发放奖励
  ↓
任务状态变为已领取
```

------

## 6.3 新手成长任务

### 场景描述

新玩家刚进入游戏，通过成长任务学习游戏基础流程。

### 示例任务

1. 完成第一局对战。
2. 第一次吞噬食物。
3. 第一次吞噬玩家。
4. 第一次进入前十。
5. 第一次获得第一名。
6. 查看一次排行榜。
7. 查看一次战绩。

------

## 6.4 成就达成

### 场景描述

玩家累计吞噬玩家数达到 100，系统解锁成就。

### 产品表现

1. 对局结算后弹出成就达成提示。
2. 成就页显示已达成。
3. 成就奖励可领取，按配置决定。
4. 成就长期保留。

------

## 6.5 每日任务重置

### 场景描述

新的一天开始，玩家每日任务进度重置。

### 产品表现

1. 今日任务重新生成。
2. 昨日未领取奖励按规则处理。
3. 客户端展示新任务列表。
4. 今日任务进度从 0 开始。

MVP 建议：

```text
每日任务到期后，未领取奖励失效
```

后续可支持补领。

# 8. 任务类型设计

## 8.1 每日任务

每日任务每天重置。

示例：

| 任务            | 条件             | 奖励              |
| --------------- | ---------------- | ----------------- |
| 完成 1 局对战   | finish_game >= 1 | 金币 50           |
| 完成 3 局对战   | finish_game >= 3 | 金币 100，经验 50 |
| 吞噬 5 名玩家   | eat_player >= 5  | 金币 120          |
| 吞噬 100 个食物 | eat_food >= 100  | 经验 80           |
| 进入前 10 一次  | rank_top10 >= 1  | 金币 150          |

------

## 8.2 成长任务

成长任务用于新手引导，一般一次性完成。

示例：

| 任务             | 条件                   | 奖励               |
| ---------------- | ---------------------- | ------------------ |
| 完成第一局游戏   | total_games >= 1       | 金币 100           |
| 第一次进入前十   | top10_count >= 1       | 金币 150           |
| 第一次获得第一名 | first_place_count >= 1 | 金币 300，经验 200 |
| 累计获得 1000 分 | best_score >= 1000     | 经验 100           |
| 查看一次排行榜   | view_rank_page >= 1    | 金币 30            |

------

## 8.3 成就任务

成就任务是长期里程碑。

示例：

| 成就       | 条件                  | 奖励      |
| ---------- | --------------------- | --------- |
| 初出茅庐   | 完成 10 局            | 金币 200  |
| 吞噬猎手   | 累计吞噬 100 名玩家   | 金币 500  |
| 食物收割机 | 累计吞噬 10000 个食物 | 金币 500  |
| 百战玩家   | 完成 100 局           | 经验 1000 |
| 冠军之路   | 获得 10 次第一名      | 金币 1000 |
| 巅峰质量   | 单局最大质量达到 5000 | 经验 800  |

# 9. 任务状态设计

## 9.1 任务状态

| 状态        | 说明             |
| ----------- | ---------------- |
| LOCKED      | 未解锁，后续支持 |
| IN_PROGRESS | 进行中           |
| COMPLETED   | 已完成，可领取   |
| CLAIMED     | 已领取           |
| EXPIRED     | 已过期           |
| DISABLED    | 已停用           |

------

## 9.2 状态流转

每日任务：

```text
IN_PROGRESS
  ↓ 达成条件
COMPLETED
  ↓ 领取奖励
CLAIMED
  ↓ 到期
结束
```

未完成每日任务：

```text
IN_PROGRESS
  ↓ 到期
EXPIRED
```

成长任务 / 成就：

```text
IN_PROGRESS
  ↓ 达成条件
COMPLETED
  ↓ 领取奖励
CLAIMED
```

# 13. 任务条件设计

| 条件类型    | 说明               | 示例              |
| ----------- | ------------------ | ----------------- |
| FINISH_GAME | 完成对局           | 完成 3 局         |
| EAT_PLAYER  | 吞噬玩家           | 吞噬 5 名玩家     |
| EAT_FOOD    | 吞噬食物           | 吞噬 100 个食物   |
| RANK_TOP_N  | 进入指定名次       | 进入前 10         |
| FIRST_PLACE | 获得第一名         | 获得第 1 名       |
| FINAL_SCORE | 单局得分           | 单局得分达到 3000 |
| MAX_MASS    | 单局最大质量       | 最大质量达到 5000 |
| LOGIN       | 登录               | 今日登录          |
| VIEW_PAGE   | 查看页面，后续支持 | 查看排行榜        |

------

## 13.2 条件计算方式

| 类型     | 计算方式                       |
| -------- | ------------------------------ |
| 累计型   | 每次事件增加进度               |
| 最大值型 | 如果当前值大于历史进度，则更新 |
| 布尔型   | 达成后直接完成                 |
| 次数型   | 满足条件时 +1                  |

示例：

```text
完成 3 局：累计型
单局最高分达到 3000：最大值型
获得第 1 名：次数型
查看排行榜：布尔型
```


------

## 14.2 user_task_progress

用户任务进度表。

| 字段         | 类型     | 说明                                        |
| ------------ | -------- | ------------------------------------------- |
| id           | bigint   | 主键                                        |
| user_id      | varchar  | 用户 ID                                     |
| task_id      | varchar  | 任务 ID                                     |
| task_type    | varchar  | 任务类型                                    |
| period_key   | varchar  | 周期标识，例如 20260628                     |
| progress     | bigint   | 当前进度                                    |
| target       | bigint   | 目标进度                                    |
| status       | varchar  | IN_PROGRESS / COMPLETED / CLAIMED / EXPIRED |
| completed_at | datetime | 完成时间                                    |
| claimed_at   | datetime | 领取时间                                    |
| created_at   | datetime | 创建时间                                    |
| updated_at   | datetime | 更新时间                                    |

唯一索引：

```text
uniq_user_task_period(user_id, task_id, period_key)
```

说明：

1. 每日任务 period_key 为日期。
2. 成长任务 period_key 可以固定为 `PERMANENT`。
3. 成就任务 period_key 可以固定为 `PERMANENT`。

------

## 14.3 user_achievement_records

| 字段           | 类型     | 说明                              |

# 16. 任务进度更新流程

## 16.1 结算事件更新任务

```text
1. 结算系统产生 GAME_SETTLED 事件
2. TaskEventConsumer 接收事件
3. 检查 eventId 是否已处理
4. 加载用户当前任务配置
5. 查询或初始化 user_task_progress
6. 根据事件内容匹配任务条件
7. 更新任务 progress
8. 如果 progress >= target，状态变为 COMPLETED
9. 写入任务事件处理日志
10. 删除任务列表缓存和红点缓存
```

------

## 16.2 每日任务初始化

玩家查询任务列表时：

```text
1. 获取今日 periodKey
2. 查询今日任务配置
3. 查询 user_task_progress
4. 对缺失任务创建默认进度
5. 返回任务列表
```

这种方式称为懒初始化。

优点：

1. 不需要每天给所有用户批量创建任务。
2. 只有活跃用户才生成任务进度。
3. 实现简单。

------

## 16.3 成长任务初始化

成长任务 periodKey 固定为：

```text
PERMANENT
```

玩家首次查询时初始化，之后长期保留。

------

## 16.4 成就初始化

成就也可以懒初始化。

```text
玩家首次打开成就页
  ↓
初始化所有启用成就
```

也可以在事件触发时初始化对应成就。

MVP 推荐：

```text
查询时懒初始化 + 事件触发时补充初始化
```

------

# 17. 奖励领取流程

## 17.1 领取任务奖励

```text
1. 客户端点击领取
2. 调用 POST /api/tasks/{taskId}/claim
3. 服务端校验登录态
4. 查询 user_task_progress
5. 校验任务状态是否 COMPLETED
6. 校验是否已领取
7. 生成 bizId
8. 调用 Asset Service 发放奖励
9. 写入 task_reward_logs
10. 更新任务状态为 CLAIMED
11. 删除任务缓存和红点缓存
12. 返回奖励结果
```

------

## 17.2 bizId 设计

任务奖励业务 ID：

```text
task:{taskId}:{periodKey}:{userId}
```

示例：

```text
task:daily_finish_3_games:20260628:10001
```

资产系统使用该 bizId 做幂等。

------

## 17.3 重复领取处理

如果客户端重复点击领取：

1. 查询任务状态。
2. 如果已经 CLAIMED，返回已领取结果。
3. 不重复调用资产发放。
4. 如果资产已发放但任务状态未更新，通过 task_reward_logs 或 asset_change_logs 恢复状态。

# 20. 异常处理

## 20.1 任务配置不存在

处理：

1. 返回任务不存在。
2. 客户端刷新任务列表。
3. 服务端记录配置异常日志。

------

## 20.2 任务未完成就领取

处理：

1. 拒绝领取。
2. 返回当前进度。
3. 客户端刷新任务状态。

------

## 20.3 任务已领取重复领取

处理：

1. 返回已领取。
2. 不重复发奖励。
3. 可返回历史奖励结果。

------

## 20.4 资产发放失败

处理：

1. 不标记任务为 CLAIMED。
2. 记录失败日志。
3. 客户端提示稍后重试。
4. 玩家可以再次点击领取。
5. 如果资产已成功但任务状态未更新，通过幂等恢复。

------

## 20.5 事件重复消费

处理：

1. 通过 eventId 幂等。
2. 已处理事件直接忽略。
3. 不重复增加进度。

# 24. 安全与校验

## 24.1 查询校验

需要校验：

1. 用户是否登录。
2. taskType 是否支持。
3. periodKey 是否合法。
4. 任务配置是否启用。
5. 用户状态是否正常。

------

## 24.2 领取校验

领取奖励前校验：

1. 用户是否登录。
2. 任务是否存在。
3. 任务是否属于当前用户。
4. 任务是否已完成。
5. 任务是否已领取。
6. 任务是否已过期。
7. 奖励配置是否合法。
8. 资产系统是否发放成功。

------

## 24.3 反作弊原则

| 风险               | 防护                             |
| ------------------ | -------------------------------- |
| 客户端伪造任务完成 | 任务进度由服务端事件更新         |
| 客户端重复领取奖励 | taskId + periodKey + userId 幂等 |
| 客户端伪造奖励数量 | 奖励按服务端配置                 |
| 重复结算事件刷进度 | eventId 幂等                     |
| 修改本地任务状态   | 每次从服务端查询任务状态         |
| 绕过任务条件领取   | 服务端校验状态必须 COMPLETED     |

# 28. 总结

任务与成就系统是《吞噬细胞》中增强长期目标、提升留存和强化成长反馈的重要模块。它不参与实时对战判定，而是基于结算、登录、页面行为等可信事件更新进度，并通过资产系统发放奖励。

核心链路如下：

```text
玩家完成对局
  ↓
结算系统产生 GAME_SETTLED 事件
  ↓
任务系统更新每日任务 / 成长任务 / 成就进度
  ↓
任务状态变为可领取
  ↓
玩家点击领取
  ↓
资产系统发放奖励
  ↓
任务状态变为已领取
```

MVP 阶段应优先保证：

1. 每日任务可以展示。
2. 成长任务可以展示。
3. 成就可以展示。
4. 结算后任务进度可以更新。
5. 任务完成后可以领取奖励。
6. 奖励通过资产系统发放。
7. 重复事件不会重复增加进度。
8. 重复领取不会重复发奖。
9. 大厅可以展示任务红点。

当前阶段不要过早引入赛季通行证、复杂活动任务和运营后台。先把“有任务可做、有进度反馈、有奖励可领、奖励不重复发”这条基础链路做稳定，任务与成就系统就能支撑长期成长体验。
