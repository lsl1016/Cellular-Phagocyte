# 第一部分：战绩系统 PRD

## 2. 模块背景

《吞噬细胞》每一局游戏结束后，结算系统会生成玩家的最终排名、最终得分、吞噬数量、存活时间、奖励结果等数据。

战绩系统负责将这些结算后的数据组织成可查询、可展示的历史记录，让玩家可以查看自己的历史对局表现。

战绩系统解决以下问题：

1. 玩家如何查看最近对局。
2. 玩家如何查看某一局详细表现。
3. 玩家如何查看个人最佳成绩。
4. 玩家如何查看累计表现统计。
5. 玩家断线后如何找回最近一局结算结果。
6. 后续如何支撑个人主页、成就、任务、排行榜等功能。

------

## 3. 模块目标

### 3.1 产品目标

| 目标             | 说明                                         |
| ---------------- | -------------------------------------------- |
| 查看历史对局     | 玩家可以查看最近参与过的对局                 |
| 查看对局详情     | 玩家可以查看某一局排名、得分、吞噬数、奖励等 |
| 展示个人成长     | 玩家可以看到累计局数、最高分、最好名次等     |
| 支持最近结算找回 | 玩家错过结算页后，可以重新查看最近一局       |
| 支持个人最佳     | 展示最高分、最高质量、最多吞噬等记录         |
| 支持后续扩展     | 为个人主页、任务、成就、排行榜提供数据基础   |

### 3.2 技术目标

| 目标         | 说明                                |
| ------------ | ----------------------------------- |
| 数据来源可靠 | 战绩数据来源于结算系统写入的数据    |
| 查询稳定     | 历史战绩列表需要分页查询            |
| 避免大查询   | 不一次性拉取大量历史数据            |
| 数据可追溯   | 每条战绩能关联 roomId、settlementId |
| 支持缓存     | 最近战绩和个人概览可缓存            |
| 权限隔离     | 玩家只能查看自己有权限查看的战绩    |
| 可扩展统计   | 后续支持更多维度聚合统计            |

------

## 4. 模块定位

战绩系统处于结算系统之后。

```text
Game Server
  ↓
结算系统
  ↓
game_records / game_player_results / settlement_records
  ↓
战绩系统
  ↓
客户端战绩页 / 对局详情页 / 个人概览
```

战绩系统主要是查询型系统，不负责实时对战，也不负责奖励发放。

------

## 5. 核心设计原则

## 5.1 战绩以结算结果为准

战绩系统不重新计算对局结果。

它读取结算系统已经写入的数据：

1. 对局主记录。
2. 玩家对局结果。
3. 玩家结算记录。
4. 奖励结果。
5. 资产流水，必要时查询。

------

## 5.2 列表轻量，详情完整

战绩列表页只展示摘要信息，避免数据过重。

列表展示：

```text
对局时间、模式、排名、得分、奖励、结果状态
```

详情页展示：

```text
最大质量、吞噬玩家数、吞噬食物数、存活时间、奖励明细、同局排名等
```

------

## 5.3 支持分页

历史战绩必须分页查询。

推荐：

```text
每页 10 ~ 20 条
```

不建议一次返回全部历史记录。

------

## 5.4 用户只能查看自己的战绩

默认情况下，玩家只能查看自己的历史战绩。

后续如果支持查看他人主页，需要单独定义公开字段和隐私规则。

# 11. 数据来源设计

战绩系统主要读取以下表：

1. `game_records`
2. `game_player_results`
3. `settlement_records`
4. `asset_change_logs`，可选
5. `user_assets`，仅用于展示当前资产，非战绩核心数据

核心原则：

```text
战绩表现数据来自 game_player_results
奖励数据来自 settlement_records
对局基础信息来自 game_records
```

------

# 12. 数据库表设计

## 12.1 game_records

对局主表，由结算系统写入。

| 字段             | 类型     | 说明           |
| ---------------- | -------- | -------------- |
| id               | bigint   | 主键           |
| room_id          | varchar  | 房间 ID        |
| match_id         | varchar  | 匹配 ID        |
| mode             | varchar  | 游戏模式       |
| server_id        | varchar  | Game Server ID |
| total_players    | int      | 总玩家数       |
| start_time       | datetime | 对局开始时间   |
| end_time         | datetime | 对局结束时间   |
| duration_seconds | int      | 对局时长       |
| status           | varchar  | 对局状态       |
| created_at       | datetime | 创建时间       |
| updated_at       | datetime | 更新时间       |

索引建议：

```text
uniq_room_id(room_id)
idx_end_time(end_time)
idx_mode_end_time(mode, end_time)
```

------

## 12.2 game_player_results

玩家对局结果表，由结算系统写入。

| 字段             | 类型     | 说明           |
| ---------------- | -------- | -------------- |
| id               | bigint   | 主键           |
| room_id          | varchar  | 房间 ID        |
| user_id          | varchar  | 用户 ID        |
| nickname         | varchar  | 昵称快照       |
| rank             | int      | 最终排名       |
| final_score      | int      | 最终得分       |
| max_mass         | int      | 最大质量       |
| eat_player_count | int      | 吞噬玩家数     |
| eat_food_count   | int      | 吞噬食物数     |
| alive_seconds    | int      | 存活时间       |
| alive            | boolean  | 是否存活到最后 |
| created_at       | datetime | 创建时间       |
| updated_at       | datetime | 更新时间       |

索引建议：

```text
uniq_room_user(room_id, user_id)
idx_user_created(user_id, created_at)
idx_user_score(user_id, final_score)
idx_user_rank(user_id, rank)
```

------

# 14. 查询流程设计

## 14.1 战绩列表查询流程

```text
1. 客户端请求 /api/records
2. API Server 校验登录态
3. 获取当前 userId
4. 查询 game_player_results 中该用户记录
5. 关联 game_records 获取模式、时间、总人数
6. 关联 settlement_records 获取奖励和状态
7. 按 endTime 倒序返回分页结果
```

------

## 14.2 战绩详情查询流程

```text
1. 客户端请求 /api/records/{roomId}
2. API Server 校验登录态
3. 查询 game_player_results
4. 校验 userId 是否匹配当前用户
5. 查询 game_records
6. 查询 settlement_records
7. 组装详情数据
8. 返回客户端
```

------

## 14.3 个人统计查询流程

MVP 可实时聚合：

```text
1. 查询当前用户全部或最近 N 条战绩
2. 聚合总局数、最好排名、最高分等
3. 返回 summary
```

如果数据量增大：

```text
结算时增量更新 user_record_stats
查询时直接读取 user_record_stats
```

推荐最终方案：

```text
结算时增量更新统计表
查询时读取统计表
```

# 15. 缓存设计

## 15.1 最近战绩缓存

Key：

```text
record:latest:{userId}
```

用途：

1. 大厅快速展示最近一局。
2. 最近结算提示。
3. 减少频繁查库。

过期时间：

```text
10 ~ 30 分钟
```

------

## 15.2 个人统计缓存

Key：

```text
record:summary:{userId}
```

用途：

1. 个人主页快速展示。
2. 战绩页顶部概览。
3. 降低聚合查询压力。

过期时间：

```text
5 ~ 10 分钟
```

更新方式：

1. 查询时缓存。
2. 结算完成后主动删除或更新缓存。
3. 后续可用事件驱动更新。

# 17. 与其他系统关系

## 17.1 与结算系统

结算系统写入数据，战绩系统读取数据。

```text
Settlement Service 写入
  ↓
Record Service 查询
```

战绩系统不修改结算结果。

------

## 17.2 与用户资产系统

战绩系统可以展示本局奖励，但不直接更新用户资产。

资产变化由结算系统完成。

------

## 17.3 与排行榜系统

后续全服排行榜可以使用战绩数据：

1. 历史最高分。
2. 总吞噬玩家数。
3. 第一名次数。
4. 累计积分。

但排行榜系统应有自己的统计或缓存，不建议每次从历史战绩全量聚合。

------

## 17.4 与任务系统

后续任务系统可使用战绩结果更新任务进度：

1. 完成一局游戏。
2. 吞噬 N 个玩家。
3. 进入前 10。
4. 获得第 1 名。
5. 单局达到指定得分。

任务系统应由结算事件驱动，不由战绩查询触发。

# 18. 异常处理

## 18.1 战绩为空

处理：

1. 返回空列表。
2. 客户端展示空状态。
3. 提供“开始游戏”按钮。

------

## 18.2 结算中记录

如果 settlement_records 状态为 PROCESSING：

1. 列表展示“结算中”。
2. 奖励字段可展示为 `--`。
3. 详情页展示“结算处理中，请稍后查看”。
4. 客户端可稍后刷新。

------

## 18.3 结算失败记录

如果状态为 FAILED：

1. 列表展示“结算异常”。
2. 详情页展示失败提示。
3. 后续支持重试或补偿。
4. 不建议直接隐藏失败记录。

------

## 18.4 对局记录缺失

如果查询到玩家结果，但主对局记录缺失：

1. 返回部分数据。
2. 记录异常日志。
3. 客户端展示“部分信息暂不可用”。
4. 后续数据修复。

# 22. 性能设计

## 22.1 性能压力来源

战绩系统压力主要来自：

1. 玩家频繁打开战绩页。
2. 历史战绩数据增长。
3. 个人统计聚合查询。
4. 大厅最近战绩查询。
5. 后续个人主页访问。

------

## 22.2 MVP 性能策略

MVP 阶段：

1. 战绩列表分页查询。
2. 按 userId + createdAt 建索引。
3. 最近战绩使用 Redis 缓存。
4. 个人统计可以先实时聚合。
5. 控制 pageSize 最大值。

------

## 22.3 完整版本优化

后续建议：

1. 增加 user_record_stats 聚合表。
2. 结算完成后增量更新统计。
3. 列表查询只读必要字段。
4. 冷数据归档，后续支持。
5. 热门玩家主页缓存。
6. 历史战绩按月分表，后续数据量大时考虑。

# 26. 总结

战绩系统是《吞噬细胞》中承接结算结果、展示玩家长期表现的重要模块。它不负责实时对战，也不负责奖励发放，而是负责把结算后的结果稳定、清晰地展示给玩家。

核心链路如下：

```text
结算系统写入结果
  ↓
战绩系统查询数据
  ↓
战绩列表展示历史对局
  ↓
战绩详情展示单局表现
  ↓
个人统计展示长期成长
```

MVP 阶段应优先保证：

1. 战绩列表可以查询。
2. 单局详情可以查看。
3. 最近结算可以找回。
4. 个人基础统计可以展示。
5. 查询有权限控制。
6. 查询有分页和索引。
7. 战绩数据以结算结果为准。
