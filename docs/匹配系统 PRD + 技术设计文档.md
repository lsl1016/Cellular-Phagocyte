# 第一部分：匹配系统 PRD

## 2. 模块背景

匹配系统负责将点击“开始游戏”的玩家加入匹配队列，并在满足开局条件后，为玩家分配游戏房间和 Game Server。

匹配系统是玩家从大厅进入实时对战的关键链路。它连接了客户端大厅、服务端匹配队列、房间创建、Game Server 分配和 WebSocket 入房流程。

匹配系统需要解决以下问题：

1. 玩家点击开始后如何进入匹配队列。
2. 如何判断哪些玩家可以进入同一局。
3. 人数不足时如何处理。
4. 匹配成功后如何创建房间。
5. 如何返回客户端入房信息。
6. 如何处理取消匹配、匹配超时、重复匹配、断线等异常情况。

------

## 3. 模块目标

### 3.1 产品目标

| 目标               | 说明                                                |
| ------------------ | --------------------------------------------------- |
| 快速进入对局       | 玩家点击开始后应尽快进入匹配流程                    |
| 匹配状态清晰       | 客户端需要明确展示当前匹配进度                      |
| 支持单局多人       | 目标支持单局最多 100 人                             |
| 支持超时处理       | 等待过久时可放宽条件或允许提前开局                  |
| 支持取消匹配       | 玩家可主动取消匹配并返回大厅                        |
| 避免重复入队       | 同一玩家不能重复进入多个匹配队列                    |
| 匹配成功后稳定入房 | 匹配成功后应返回 roomId、serverId、wsUrl 等入房信息 |

### 3.2 技术目标

| 目标           | 说明                                                   |
| -------------- | ------------------------------------------------------ |
| 匹配队列可靠   | 使用 Redis 维护匹配队列和玩家匹配状态                  |
| 状态可追踪     | 玩家匹配状态需要可查询、可恢复                         |
| 支持水平扩展   | 匹配服务后续可支持多实例部署                           |
| 防止重复匹配   | 同一玩家同一时间只能参与一个匹配流程                   |
| 支持幂等请求   | 客户端重复点击或重试不应造成异常                       |
| 与房间系统解耦 | 匹配服务只负责匹配和请求创建房间，不负责房间内实时对战 |

## 4. 用户场景

## 4.1 正常匹配进入游戏

### 场景描述

玩家在大厅点击“开始游戏”，进入匹配中状态。服务端将玩家加入匹配队列，当匹配到足够玩家后创建房间，并返回客户端入房信息。

### 用户流程

```text
玩家进入大厅
  ↓
点击开始游戏
  ↓
进入匹配中页面
  ↓
服务端加入匹配队列
  ↓
等待匹配成功
  ↓
服务端创建房间并分配 Game Server
  ↓
客户端收到 roomId / wsUrl
  ↓
客户端建立 WebSocket 连接
  ↓
进入对局加载阶段
```

------

## 4.2 玩家取消匹配

### 场景描述

玩家进入匹配中后，尚未匹配成功时点击“取消匹配”。

### 处理规则

1. 客户端发送取消匹配请求。
2. 服务端校验玩家是否处于匹配中。
3. 如果仍在队列中，则从队列移除。
4. 玩家状态恢复为大厅空闲状态。
5. 客户端返回大厅或停留在大厅页。

------

## 4.3 匹配超时

### 场景描述

玩家等待时间超过预期，但仍未匹配成功。

### 处理策略

匹配系统可以按阶段处理：

| 等待时长   | 策略                   |
| ---------- | ---------------------- |
| 0 ~ 10 秒  | 按标准规则匹配         |
| 10 ~ 20 秒 | 放宽匹配条件           |
| 20 ~ 30 秒 | 允许较少人数开局       |
| 超过 30 秒 | 提示继续等待或取消匹配 |

MVP 阶段可以简化为：

```text
人数达到最低开局人数即可开局
超过最大等待时间仍不足最低人数则匹配失败
```

------

## 4.4 重复点击开始游戏

### 场景描述

玩家短时间内多次点击“开始游戏”，或者客户端重试开始匹配请求。

### 处理规则

1. 服务端根据 userId 查询玩家当前匹配状态。
2. 如果玩家已在匹配中，则返回当前匹配状态。
3. 不重复加入队列。
4. 客户端继续展示匹配中页面。

------

## 4.5 匹配成功后客户端断开

### 场景描述

玩家匹配成功后，还未建立 WebSocket 连接就断开或退出。

### 处理规则

1. 服务端保留短时间入房资格。
2. 客户端在有效期内可重新请求入房信息。
3. 超过有效期未进入房间，房间系统可将玩家移除。
4. 如果房间人数不足，可补入其他玩家或机器人，后续支持。

## 7. 匹配规则设计

## 7.1 MVP 匹配规则

MVP 阶段规则保持简单：

| 规则项         | 说明                     |
| -------------- | ------------------------ |
| 匹配维度       | mode                     |
| 队列维度       | 按模式维护队列           |
| 最大人数       | 100 人                   |
| 最低开局人数   | 可配置，建议 10 ~ 30 人  |
| 标准开局人数   | 可配置，建议 30 ~ 100 人 |
| 最大等待时间   | 可配置，建议 30 秒       |
| 匹配方式       | 队列先进先出             |
| 是否机器人补位 | MVP 可不支持             |

MVP 匹配逻辑：

```text
玩家进入 classic 队列
  ↓
匹配服务周期扫描队列
  ↓
如果队列人数 >= 标准开局人数
    创建完整房间
否则如果等待时间达到最大等待时间且人数 >= 最低开局人数
    创建低人数房间
否则
    继续等待
```

------

## 7.2 扩展匹配规则

后续版本可以引入以下规则：

| 规则       | 说明                                |
| ---------- | ----------------------------------- |
| 段位       | 优先匹配相近段位玩家                |
| 等级       | 防止新手与高等级玩家差距过大        |
| 延迟       | 优先匹配同区域低延迟玩家            |
| 地区       | 按区域分服或分区匹配                |
| 等待时间   | 等待越久，规则越宽松                |
| 机器人补位 | 人数不足时加入机器人 （P0，高优先） |
| 黑名单     | 避免恶意玩家频繁进入同局            |
|            |                                     |

## 8. 玩家匹配状态

## 8.1 状态定义

| 状态          | 说明                 |
| ------------- | -------------------- |
| IDLE          | 空闲，未匹配         |
| MATCHING      | 匹配中               |
| MATCHED       | 匹配成功，已分配房间 |
| ENTERING_ROOM | 正在入房             |
| IN_ROOM       | 已进入房间           |
| CANCELED      | 已取消匹配           |
| TIMEOUT       | 匹配超时             |
| FAILED        | 匹配失败             |

------

## 8.2 状态流转

```text
IDLE
  ↓ 点击开始匹配
MATCHING
  ↓ 匹配成功
MATCHED
  ↓ 客户端开始连接 Game Server
ENTERING_ROOM
  ↓ WebSocket 认证成功
IN_ROOM
```

异常流转：

```text
MATCHING
  ↓ 玩家取消
CANCELED
  ↓ 返回大厅
IDLE
MATCHING
  ↓ 等待超时
TIMEOUT
  ↓ 返回大厅或重新匹配
IDLE / MATCHING
MATCHING / MATCHED
  ↓ 服务异常
FAILED
  ↓ 返回大厅或重试
IDLE / MATCHING
```

# 第二部分：匹配系统技术设计

## 12. 总体架构

## 12.1 模块关系

匹配系统涉及以下模块：

```text
Cocos Client
  ↓ HTTP
API Server
  ↓
Match Server
  ↓
Redis
  ↓
Room Coordinator
  ↓
Game Server
```

各模块职责如下：

| 模块             | 职责                                     |
| ---------------- | ---------------------------------------- |
| Cocos Client     | 发起开始匹配、取消匹配、查询匹配状态     |
| API Server       | 鉴权、参数校验、转发匹配请求             |
| Match Server     | 管理匹配队列、执行匹配规则、生成匹配结果 |
| Redis            | 存储匹配队列、玩家匹配状态、匹配结果     |
| Room Coordinator | 创建房间、分配 Game Server               |
| Game Server      | 承载房间实例，等待客户端 WebSocket 入房  |

------

## 12.2 匹配服务边界

匹配服务负责：

```text
1. 接收玩家加入匹配请求
2. 维护匹配队列
3. 管理玩家匹配状态
4. 定时扫描队列
5. 根据规则生成匹配批次
6. 请求房间服务创建房间
7. 保存匹配成功结果
8. 支持取消匹配
9. 支持状态查询
```

匹配服务不负责：

```text
1. 房间内移动同步
2. 游戏 Tick 循环
3. 玩家碰撞判定
4. 局内排行榜计算
5. 最终结算计算
6. 客户端 WebSocket 长连接维护
```

------

## 13. 核心流程设计

## 13.1 开始匹配流程

```text
1. 客户端点击开始游戏
2. 客户端调用开始匹配接口
3. API Server 校验 token
4. API Server 校验玩家是否允许匹配
5. Match Server 查询玩家当前匹配状态
6. 如果玩家已经在匹配中，直接返回当前状态
7. 如果玩家空闲，将玩家写入匹配队列
8. 写入玩家匹配状态
9. 返回匹配中状态
10. 客户端进入匹配页
```

------

## 13.2 匹配扫描流程

匹配服务后台周期性扫描匹配队列。

```text
1. Match Server 定时扫描队列
2. 按 mode 读取匹配队列
3. 获取队列中玩家数量
4. 判断是否满足标准开局人数
5. 如果满足，则取出一批玩家
6. 如果不满足，则判断等待时间是否超过阈值
7. 如果超过阈值且满足最低开局人数，则取出一批玩家
8. 生成 matchId
9. 请求 Room Coordinator 创建房间
10. 房间创建成功后，写入匹配结果
11. 更新玩家状态为 MATCHED
```

------

## 13.3 匹配成功流程

```text
1. Match Server 生成匹配批次
2. 调用 Room Coordinator 创建房间
3. Room Coordinator 分配 Game Server
4. Game Server 创建房间实例
5. Room Coordinator 返回 roomId、serverId、wsUrl
6. Match Server 写入每个玩家的匹配结果
7. 客户端轮询匹配状态或接收推送
8. 客户端拿到入房信息
9. 客户端建立 WebSocket 连接
```

------

## 13.4 取消匹配流程

```text
1. 客户端点击取消匹配
2. 调用取消匹配接口
3. API Server 校验 token
4. Match Server 查询玩家匹配状态
5. 如果玩家处于 MATCHING，则从队列移除
6. 更新玩家状态为 CANCELED
7. 返回取消成功
8. 客户端返回大厅
```

特殊情况：

| 情况             | 处理                       |
| ---------------- | -------------------------- |
| 玩家已经 MATCHED | 不允许取消，返回匹配已成功 |
| 玩家已经 IN_ROOM | 不允许取消，提示已进入房间 |
| 玩家不在队列     | 返回当前状态               |
| 重复取消         | 幂等返回取消成功或当前状态 |

------

## 13.5 查询匹配状态流程

```text
1. 客户端定时查询匹配状态
2. API Server 校验 token
3. Match Server 查询玩家匹配状态
4. 如果 MATCHING，返回等待时间、当前阶段
5. 如果 MATCHED，返回 roomId、serverId、wsUrl、enterToken
6. 如果 TIMEOUT / FAILED，返回失败原因
7. 客户端根据状态跳转页面
```

## 14. 接口设计

## 14.1 开始匹配接口

### 请求

```http
POST /api/match/start
```

### 请求参数

```json
{
  "mode": "classic",
  "clientVersion": "1.0.0",
  "region": "default"
}
```

### 字段说明

| 字段          | 类型   | 必填 | 说明       |
| ------------- | ------ | ---- | ---------- |
| mode          | string | 是   | 游戏模式   |
| clientVersion | string | 是   | 客户端版本 |
| region        | string | 否   | 区域       |

### 响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "matchId": "m_10001",
    "status": "MATCHING",
    "estimatedWaitSeconds": 15,
    "serverTime": 1710000000000
  }
}
```

------

### 请求参数

### 响应

## 17. 幂等与并发控制

## 17.1 防止重复开始匹配

处理方式：

1. 以 userId 查询 `match:player:{userId}`。
2. 如果状态为 MATCHING，直接返回已有 matchId。
3. 如果状态为 MATCHED，返回入房信息。
4. 如果状态为 IDLE / CANCELED / TIMEOUT / FAILED，允许重新匹配。

------

## 17.2 防止多个匹配服务重复消费队列

如果 Match Server 后续多实例部署，需要避免多个实例同时取出同一批玩家。

可采用：

```text
Redis 分布式锁
```

锁 Key：

```text
match:lock:{mode}
```

处理方式：

1. 扫描队列前尝试获取锁。
2. 获取锁成功后执行批次匹配。
3. 匹配完成释放锁。
4. 获取锁失败的实例跳过本轮扫描。

------

## 17.3 防止取消与匹配成功并发冲突

可能出现：

```text
玩家点击取消匹配
同时匹配服务已经将玩家匹配成功
```

处理规则：

| 当前状态      | 取消处理                 |
| ------------- | ------------------------ |
| MATCHING      | 允许取消                 |
| MATCHED       | 不允许取消，返回匹配成功 |
| ENTERING_ROOM | 不允许取消               |
| IN_ROOM       | 不允许取消               |

------

## 21. 安全与校验

## 21.1 开始匹配校验

开始匹配前需要校验：

1. 用户是否登录。
2. Token 是否有效。
3. 客户端版本是否支持。
4. 游戏模式是否存在。
5. 玩家是否已在匹配中。
6. 玩家是否已在房间中。
7. 玩家是否被封禁，后续支持。
8. 玩家是否满足模式进入条件，后续支持。

------

## 21.2 入房校验

匹配成功后，客户端建立 WebSocket 连接时需要校验：

1. userId 是否一致。
2. roomId 是否存在。
3. enterToken 是否有效。
4. enterToken 是否过期。
5. 玩家是否属于该房间。
6. 玩家是否已重复连接。

------

## 22. 可扩展设计

## 22.1 机器人补位

后续可支持机器人补位：

触发条件：

1. 队列等待时间超过阈值。
2. 当前人数达到最低开局人数。
3. 房间未达到标准人数。

处理方式：

```text
真实玩家 + 机器人玩家 = 房间玩家列表
```

注意：

1. 机器人需要标记 bot=true。
2. 机器人不应参与真实排行榜。
3. 机器人结算规则需要单独处理。

------

## 22.2 超时扩圈

扩圈规则可以基于等待时间变化：

| 等待时间   | 匹配条件                   |
| ---------- | -------------------------- |
| 0 ~ 10 秒  | 同模式、相近段位、同区域   |
| 10 ~ 20 秒 | 放宽段位                   |
| 20 ~ 30 秒 | 放宽区域                   |
| 30 秒以上  | 允许机器人补位或低人数开局 |

------

## 22.3 多 GameServer 分配

Room Coordinator 分配 Game Server 时可以考虑：

1. 当前房间数量。
2. 当前在线连接数。
3. CPU / 内存负载。
4. 区域就近。
5. Game Server 健康状态。

MVP 阶段可以使用简单策略：

```text
选择当前房间数最少的 Game Server
```

## 25. 总结

匹配系统是游戏中连接大厅与实时对战的核心模块。MVP 阶段应优先实现简单、稳定、可验证的匹配闭环：

```text
开始匹配
  ↓
加入队列
  ↓
队列扫描
  ↓
匹配成功
  ↓
创建房间
  ↓
返回入房信息
  ↓
客户端连接 Game Server
```

当前阶段不需要过早引入复杂段位匹配、机器人补位和多区域调度，应优先保证：

1. 状态清晰。
2. 流程可靠。
3. 不重复入队。
4. 可取消。
5. 可查询。
6. 匹配成功后可稳定入房。

后续可围绕匹配质量、等待时间、机器人补位、Game Server 负载分配和多实例并发控制进行逐步增强。
